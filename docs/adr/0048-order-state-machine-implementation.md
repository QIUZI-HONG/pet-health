# 订单状态机与号源并发的实现细节

实现切片：[#77](https://github.com/QIUZI-HONG/pet-health/issues/77) / [#107](https://github.com/QIUZI-HONG/pet-health/issues/107) /
[#109](https://github.com/QIUZI-HONG/pet-health/issues/109)（订单 / 三道照片墙 / 核销）。
上位决策是 [ADR-0038](0038-order-redeem-rights-points.md)（四态与双侧取消、6 位核销码、号源并发）
与 [ADR-0040](0040-reports-kb-citations-realtime-photo-wall.md) 第四节（三道照片墙 + 后端硬校验）、
[ADR-0036](0036-money-semantics-offline.md)（钱在门店付）、
[ADR-0034](0034-service-catalog-and-pricing.md) 第五节（区间校验只有一处实现）。
**本 ADR 只记「怎么落的」，不重开上面那几条已经裁决过的规则。**

契约里那批待澄清由 **ADR-0049 分两批拍板**（八条），本文把定稿口径落在实现上的位置一并写明；
拍板见 ADR-0049，本文只记落点，避免两处各说一遍。

落地位置：`server/ph-order/**`（api / domain / mapper / service / web）+ 迁移 `V28`–`V30`
（`db/undo/U28`–`U30`）+ DTO 在 `ph-api` 的 `com.pethealth.api.order`。

## 一、状态迁移：每条迁移就是一条带源状态的条件更新

四态（`0 待接单 / 1 已预约 / 2 履约中 / 3 已完成 / 4 已取消`）的**全部落点**在
`ServiceOrderMapper`，每个动作一条 `UPDATE ... WHERE id = ? AND status = <源状态>`，
受影响行数为 0 就是 **40900**。service 层从不 `setStatus` + `updateById`——
那会把「原子条件更新」退化成「先查后写」，两个并发请求会双双通过
（[ADR-0044](0044-coupon-pool-implementation.md) 在券额度上踩过的坑，核销的并发双击是同一形状）。

几条具体口径：

- **接单即承诺**：`0 → 1` 之后用户同名的「取消」不再是取消，而是**取消申请**
  （`cancel_request_status = 1`，订单状态不变）。门店同意 `→ 4`；拒绝必填理由、订单留在 `1`；
- **核销 `1 → 2`**：原子条件更新，重复核销 **40900**（不是幂等成功）；
- **报工 `2 → 3`**：先判三道照片墙，再推进（见第三节）；
- **「履约中」不可取消**：`status IN (0,1)` 才在取消语句的 WHERE 里，`2/3/4` 一律 40900；
- **进入终态（3 / 4）时把 `redeem_code_active` 置空**：唯一键只加在这一列上
  （见第四节），否则 6 位码位会被历史订单吃光。

## 二、号源并发：一条带容量的条件更新 + 独立事务懒建行

`appointment_slot` 按 `(provider_id, service_id, slot_date, start_time)` 一行，
`booked_count < capacity` 才 `+1`。**粒度 30 分钟一格、每格默认容量 1**（ADR-0049 §六）：
服务者在营业时间内按格开放，「已满」以格为单位判，「某格容量 &gt; 1」留作服务者可配项（本期不做）。
网格在 `SlotGrid`（纯计算，只依赖营业时间），容量在行上，占用与释放都是条件更新
（`booked_count > 0` 才 `-1`），随取消一起回滚。

**踩过的两条坑**（都不是推演，是集成测试里实测到的，写在这里免得下一个人再试）：

1. **「先 UPDATE，没改到再 INSERT，再重试 UPDATE」→ MySQL 经典死锁**：
   失败的 INSERT 在唯一键上留下共享锁，随后重试的 UPDATE 要升级成排他锁，
   多个并发请求互相等对方的共享锁。4 个并发请求抢同一时段时，有一个拿到 **50000**
   （`DeadlockLoserDataAccessException`），而 ADR-0038 要的是 40900；
2. **一条 `INSERT ... ON DUPLICATE KEY UPDATE` → 判不出成败**：它对「已存在的行被写成原值」
   本该返回 0 受影响行，但 Connector/J 默认带 `CLIENT_FOUND_ROWS`（`useAffectedRows=false`），
   于是这一档也返回 1——实测 4 个并发请求**全部**拿到「占到」，超卖 4 倍。

**最终形态**：懒建行是一条独立的 `INSERT IGNORE`（`booked_count = 0`，**不占用**），
跑在**独立事务**里（`SlotRowWriter`，`REQUIRES_NEW`），它的锁在条件更新之前就已释放；
条件更新永远只面对「已经存在的行」。建行的那张纸若因外层事务回滚而留下，
留下的也只是「一个还没被占的时段」，不会变成幽灵占用（占用的 `+1` 随外层回滚）。
顺序：`tryOccupy → 行不存在则 ensureRow → 再 tryOccupy → 仍为 0 即 40900`。

**顺带一条判据两处读者**：MyBatis 按注解决定 `SqlCommandType`，而 MyBatis-Plus 的
`BlockAttackInnerInterceptor` 会**按注解去解析**语句——把 INSERT 写成 `@Update` 时它按 UPDATE
解析 INSERT 语法，直接抛 `UnsupportedOperationException`（实测：下单 100% 报 50000）。
所以 `insertIfAbsent` / `upsertSlot` 必须是 `@Insert`。代码里留了注释。

## 三、报工硬校验与「报工即固化」

「三个槽位各至少一张照片才允许报工」是**服务端**的判据（ADR-0040 第四节 / 交付文档 2.5）：

- 计数在 `order_photo_slot.photo_count`，与照片行在同一个事务里写；
  **判据读这个计数，不数 JSON 数组、也不信前端传来的长度**；
- `OrderPhotoWallView.reportable` / `missing_slots` 由服务端算出来（`OrderPhotoWallService`），
  报工被拒时 `message` **点名缺哪一道**（`三道照片墙还缺：取宠对比，每道至少一张照片才能报工`）；
- PUT 槽位是**整体替换**（`file_ids` 是全量集合，空数组 = 清空）。顺序刻意是
  **先删本槽位旧行、再判新 id**：反过来会把「原样重新提交」判成「这张图已挂在另一个槽位」；
  两步在同一个事务里，校验失败时删除一起回滚；
- **照片归属订单**：`order_photo` 上的 `uk_file_id` 让「一张图挂两个订单」在数据库层面不可能发生；
  应用侧再判一次是为了给明确的答复（40400 / 40001）而不是一个 50000。
  另外补了一条契约没写、但属于「不属于本订单」的判据：**照片必须是这只宠物的**
  （`file_object.pet_id` 与订单宠物不一致 → 40400；照片没登记宠物时放行）。

**报工提交即固化**（ADR-0049 §一，项目所有者拍板）：报工之后照片与备注都不再可改，
所以要改只能走**运营干预**。落点与理由是：

- 拒绝用 **40901 `ORDER_FINALIZED`**，不是 40900：40900 在这一族里有两层意思
  （「还没到能写的状态」与「已经封存」），前端得靠 message 猜。分开之后语义唯一：
  40900 = 现在还不能写（待接单 / 已预约 / 已取消），40901 = 已经封存；
- `message` 里明说「要修正只能走运营干预」——**运营干预是这条规则的必要配套**：
  没有它，固化就等于「错了也没法救」。它落在 **admin 域**（admin.yaml 目前没有这个接口），
  属**下一个写入者**，并要求留痕：谁 / 何时 / 理由 / 前后版本。本切片刻意不做这个入口
  （订单域没有运营写路径，做了会绕过 ADR-0037 的角色矩阵）。

## 四、核销码与订单号

**核销码**（ADR-0038 第二节）：

- **6 位数字**（`%06d`，可读出的码，不是安全凭证），存 `redeem_code`（永久，可查可追）+
  `redeem_code_active`（唯一键加在这一列，进入终态置空）；
- 为什么两列：6 位只有 100 万种，历史订单一直占着码位迟早会把码位吃光；
  MySQL 的唯一键不约束 NULL，所以「终态让位」是一条干净的规则；
- **核销码随订单有效**（ADR-0049 §三）：**不另设码过期**——订单没进终态，码就能用；
  订单进终态（完成 / 取消）时从唯一键上让位，码本身留在 `redeem_code` 里可查可追；
- 生成时撞唯一键（`DuplicateKeyException`）就换一个重来，最多 6 次；
- **可见性**由服务端判：状态 ∈ {已预约, 履约中} **且**已到预约时间才在 C 端详情里下发
  （`OrderViews.visibleRedeemCode`）；**服务者侧永不下发**（门店凭用户出示的码定位订单，
  不知道码本身，也就更不可能被记下来复用）；
- **定位三个入口**（服务者侧列表的 `keyword`）：订单号按包含匹配、完整手机号与 6 位码按精确匹配，
  三者并集（门店只会输入一个关键字，让平台猜它是什么，比让门店先选「按什么搜」更省事）。

**订单号**：`PH` + 业务日 + 当日序号（`PH20261001001`，ADR-0049 §五）。
`PH` 是 pet-health，**不沿用交付文档的 `TL`**（来历不明）。生成在 `OrderNoGenerator`：

- **正确性在数据库唯一键**（`order.uk_order_no`），撞了就换一个号重试；
  **不做**「先查当天最大序号再加一」——那是并发下必然重号的写法（D9 / D19 踩过同类）；
- 唯一的数据库读是**给当天的内存计数器播种**（当天已有订单数）：种子偏低只会多几次重试，
  不会让号重复；顺序超 999 时号变长（`PH202610011000`）而不是下不出单，
  要不要扩位留给运营决定（见待澄清）。

## 五、手机号：脱敏展示、等值查询、查询留痕

（ADR-0049 §二）

- **展示一律脱敏**（`138****8888`）：服务者侧的列表与详情都走 `OrderParties.phoneOf`
  （值来自 ph-account 给的脱敏值），订单自己不存手机号，也不存它的快照
  ——订单不该留一个会过期的联系人快照，门店要打的是**此刻**能打通的号码；
- **核销允许按完整号等值查询**：`keyword` 是 11 位且以 1 开头时，才交给 ph-account
  按 **HMAC 查找列**（`user.phone_hash`）比对（ADR-0013）；**不把号码解密出来逐个比**，
  也不把完整号回显给任何人（响应里只有脱敏值，见第四节）；
- **查询计入审计**：`OrderService.applyKeywordFilter` 在走手机号这条路径时留一条
  `operator + traceId + 脱敏号 + 是否命中` 的日志（**明文永不进日志**）。
  落成 `audit_log` 那一行需要 ph-account 的写侧接口（`audit_log` 是它的表，ADR-0006），
  本切片报为「需要协调」（见待澄清）。

## 六、时效与锁：券锁 30 分钟、按读时判断

（ADR-0049 §三）

- **券锁 30 分钟**：下单锁券（`coupon.locked_at`）到点即视为释放，**按读时判断**
  （比较 `locked_at + 30min` 与当前时刻），不把正确性押在定时任务上——
  与 ADR-0044 的券过期释放同一个做法。**这一段在 ph-privilege 的读路径里**
  （`check` / 列表 / 锁定），本模块不碰 `coupon` 表；本切片做到的是：
- **取消释放**（本模块的职责）：订单取消 / 同意取消 → `CouponApi.release(couponId, orderId)`，
  它是一条带 `locked_order_id` 条件更新，所以**放不到别人的锁**，重复放也不会误放；
- **无主锁的兜底**（本模块能产生锁的路径只有下单一条，逐条数过）：
  ① 用户取消 / 门店取消 / 同意取消 → 释放；② 核销 → 券转「已核销」（不再占锁）；
  ③ 报工 → 已完成（券早已核销）；④ 订单一直停在「待接单」→ 锁到时由**读时规则**放行，
  本模块的 `coupon_id` 只是引用，取消时那次 `release` 因为条件不成立而变成 no-op（安全）。
  唯一需要留意的张力写在待澄清里（锁过期后券可能被别人锁走，而本单核销会因此拿到 80001）。

## 七、服务者单方取消：允许 + 必填理由 + 通知 + 考核留痕

（ADR-0049 §七）

- **允许**：`待接单 / 已预约` 都能取消（`status IN (0,1)`），`履约中` 与终态仍然 40900；
- **理由必填**：`OrderService.cancelByProvider` 先校验（空 / 空白 → **40001**）。
  注意契约把这一条的 `reason` 写成**可选**（交付文档只对「拒绝取消申请」强制理由），
  而定稿口径要求必填——**按契约优先的纪律，规则落在服务层，没有改契约的 `required`**
  （改了会让 `ContractDtoDrift` 的 REQUIRED_NOT_DECLARED 变红）。**契约侧需要补一句说明**（见待澄清）；
- **通知用户**：同事务内调 ph-reminder 的 `BusinessMessageApi.notify`（业务通知，`kind=2`、
  `type=7 订单`），去重键 `order-cancelled-{orderId}`，正文带上理由；
- **计入考核过程分**：本模块只**留痕**（`cancel_reason` + `cancelled_by = 2`），
  并把「服务者单方取消数」暴露成 `OrderStatsApi.countCancelledByProvider`；
  过程分怎么算在考核那一波（ADR-0039 §三已同步修订）；
- 契约把它的 `reason` 写成可选这件事，按 ADR-0047 报给契约写入者，不就地改契约。

## 八、本期不做派工

（ADR-0049 §四）订单里**没有** `technician_id`，也没有指派动作与界面；
接单后由服务者管理员自行安排技师。权限矩阵里「派工」的位置保留（ADR-0037），
实现落在服务者后台的下一波。本模块的接口一个都不涉及技师。

## 九、给考核的只读统计（`OrderStatsApi`）

`ph-order` 的 `api` 包（`com.pethealth.order.api.OrderStatsApi`，实现 `OrderStatsService`）
给下一波的考核 F022 四个数：某状态单量、服务者单方取消数、接单响应时长、平均服务时长
（**核销 → 报工**，两个时刻都取服务端记的）。三条口径先钉死：日期区间按**预约日期**、
**计数回 0、均值回 `null`**、单方取消只看 `cancelled_by = 2`。

## Consequences

- **跨模块适配器未接线**（5 个，本次交付未接线，与 ADR-0044 / ADR-0046 的「需要协调」同一形态）：
  `ProviderAccessApi`（既有）、`ProviderServiceQueryApi`（服务项 + 营业时间）、
  `UserQueryApi`（预约人资料 + 手机号等值查询）、`PetFactsApi`（宠物昵称与物种）、
  `CouponFactsApi`（券卡片）。它们都在 `ph-api` 里定义、都由**提供方模块**补一个薄适配器
  （转给已有的 service/mapper，不需要新写查询逻辑）。集成测试里用等价 stub 覆盖
  （`OrderTestSupport.StubCrossModuleApis`，读同一批表），未被接线的调用在线上会**明确报错**
  而不是静默按「查不到」处理。**已接线**的两条：`FileQueryApi`（ph-file，本次新增并实现）、
  `BusinessMessageApi`（ph-reminder，本次新增并实现）。
- 迁移 `V28`–`V30` 的回滚代价写在 `db/undo/U28`–`U30` 里：U29（删订单）代价最高
  （交易与履约的唯一记录），U30 只丢挂载关系、照片文件本身不删。
- 基线里剩下的 8 行是 **C 端增长链路**（积分中心 / 兑换 / 邀请码与邀请中心）：
  数据在 ph-privilege，由持有它的那条路线实现（`/invites/attribution` 那一对已由接线切片清偿）。

## 待澄清

1. **40901 需要契约补一行**：`contract/common.yaml` 的 `x-error-codes` 目前没有 40901
   （ADR-0049 §一定了「要有明确的业务错误码」，但码值本身没有契约位置）。
   按 ADR-0047 由契约写入者补（本切片不就地改契约）。
2. **服务者取消的 reason 必填 vs 契约写成可选**：定稿口径要求必填（ADR-0049 §七），
   契约（provider.yaml 的 `/orders/{order_id}/cancel`）现在写的是「可选」。
   本切片落在服务层（40001），**契约的描述与 required 需要契约写入者同步**。
3. **券锁过期后的张力**（需要 ph-privilege 那一侧确认）：券锁 30 分钟按读时判断之后，
  一张「被某单锁着、但锁已过期」的券可以被别人锁走；本单随后核销就会拿到 80001。
   建议 ph-privilege 的核销路径把「锁已过期但订单还在履约」当成「券仍归这一单」
   （ADR-0049 §三「核销码随订单有效」是同一个精神）。本模块不改它的表与代码。
4. **手机号查询的审计落点**：本切片留的是日志（operator / traceId / 脱敏号 / 是否命中）。
   要落成 `audit_log` 的一行，需要 ph-account 提供一个写侧接口（或把审计收到一处）。
   另外「门店要不要看完整号码」这条基础口径仍未定（ADR-0049 只定了「不回显」）。
5. **照片的「不属于本店」判不了**：契约写「file_id 不属于本店与本订单 → 40400」，
   但 `file_object` 没有订单 / 门店字段（ADR-0020 的文件模型只有 owner + biz_type + pet）。
   本实现用「biz_type=care + 未挂在别的订单 + 是这只宠物的照片」替代，
   归属的权威判据在订单侧。要不要给文件加「服务者归属」属另一张票。
6. **订单号序号扩位**：超过 999 单/天时号会变长（`PH202610011000`）。
   要不要扩到 4 位、或按门店分段，由运营与甲方定；改一处常量即可。
7. **超时提醒与异常看板未实现**：ADR-0038 第一节要求「预约时间过了没核销 → 提醒服务者；
   超 24 小时标记异常进看板」，属提醒与考核切片。本切片**没有**任何自动取消的定时任务
   （ADR-0038 明确不要），也没有对账任务（契约里没有对账接口）。
8. **考核用的日期口径**：`OrderStatsApi` 按「预约日期」统计。若考核要按「下单日」或
   「完成日」算，改一处 SQL 即可——**待考核那一波确认**。
