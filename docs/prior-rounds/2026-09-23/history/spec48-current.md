## Problem Statement

**宠物主人今天没有任何自助入口。** 已交付的一期是服务者端与运营端两个后台：用户与宠物由运营代录、健康记录由运营录入、预约只能由运营或服务者建单。这对平台的产品定位（「AI 自助 → 远程人工 → 匹配服务者」三级问题解决路径）是根本性缺口——**第一级「AI 自助」没有入口，第三级「匹配服务者」也只能后台代客下单**，而验收方式恰恰是「模拟真实用户使用场景」，没有用户端就无从谈起。

宠物主人想要的其实很朴素：掏出手机就能记录自家宠物的健康，随手问一句「它今天吐了两次要紧吗」，查得到有谁能提供服务、并且直接约上。

两条现实约束决定了形态：**微信小程序对个人主体不可行**（宠物类目、AI 问答、支付三条支柱全在禁区），所以入口是 **Web + H5**（一套响应式前端，手机与电脑同一个地址）；**本轮不接真实支付**（无企业主体），交易止于「预约成立」。

## Solution

一套响应式 C 端 + 后端新增的 C 端接口模块。用户拿手机打开链接就能走完这五步：注册 → 建档 → 打卡 → 问 AI → 约服务。

- **自助账号**：手机号 + 密码注册登录（演示档不做短信验证，手机号是登录标识）；登录态 30 天，改密/注销立即让旧登录失效；注册须勾选《用户协议》《隐私政策》；随时可注销，注销后数据按留存策略处理。
- **宠物与健康档案**：建宠物档案（含疫苗与驱虫四个日期）、每日 5 项打卡（体重/饮食/排泄/行为/卫生）、健康评分与 6 个分项、体重趋势折线与打卡完成度柱状（近 30 天）、记录时间轴、多宠物切换。
- **AI 管家**：聊天式界面；单轮分析给出风险三色（绿/黄/红）+ 可能原因 + 行动建议；**每条回答带 AI 生成标识**；红色等级置顶「就医准备清单」；每日 3 次配额，用完给「明天再来」的友好提示。
- **消息中心**：自家宠物的健康预警（体重连续下降、饮水/排泄异常、疫苗/驱虫临期）与预约状态变化，未读角标。
- **服务与预约**：浏览已通过审核的服务者与其服务项、按日期看号源余量、提交预约（可填地址与备注）、我的预约与取消（必填理由）。
- **后台侧的必要改动**：运营端能分辨自助注册的用户、可为其重置密码、多一个埋点统计页（四类事件的次数与转化）。
- **交付形态**：C 端独立容器 + 新端口，**本机与局域网即可演示**（云主机采购推迟，独立容器与新端口的设计不变）；演示账号（有历史数据）与现场注册两条路径都保留；配套操作手册、需求对照表与源码提交包。

## User Stories

**注册与登录**

1. 作为宠物主人，我想用手机号和密码注册账号，这样我不需要等运营替我录入。
2. 作为宠物主人，我想登录后 30 天内不用重新登录，这样日常打开就能用。
3. 作为宠物主人，我想在注册前看到并勾选《用户协议》与《隐私政策》，这样我知道收集了哪些数据、用来做什么、存多久。
4. 作为宠物主人，我忘记密码时想看到「如何找回」的明确说明，而不是卡在登录页。
5. 作为宠物主人，我改密码后想让其他设备上的登录立即失效，这样账号更安全。
6. 作为宠物主人，我想能注销账号，并在注销前被清楚地告知后果（数据删除不可恢复）。
7. 作为宠物主人，我未登录访问任何页面时应被引导到登录页，而不是看到空白页或报错。

**宠物档案**

8. 作为宠物主人，我想创建宠物档案（名称、物种、品种、年龄、体重、头像、慢性病标签、疫苗与驱虫日期），这样 AI 与评分才有上下文。
9. 作为宠物主人，我想编辑宠物资料（比如体重涨了、疫苗打过了），这样档案与事实一致。
10. 作为宠物主人，我想在几只宠物之间切换，这样多宠家庭记录不混。
11. 作为宠物主人，我还没有宠物时想看到引导，而不是一个空荡荡的首页。

**打卡与健康档案**

12. 作为宠物主人，我想在首页一眼看到今日 5 项任务与完成进度，这样我知道今天还差什么。
13. 作为宠物主人，我想每项打卡三秒内完成（体重输入、其余选择 + 可选备注），这样我能坚持每天记。
14. 作为宠物主人，我同一天重复提交同一项时希望是「补充/合并」而不是多出一条记录。
15. 作为宠物主人，我想看到连续打卡天数，这样有坚持的反馈。
16. 作为宠物主人，我想在档案页看到健康评分与 6 个分项（打卡 5 项 + 防疫），这样我知道分数从哪来。
17. 作为宠物主人，我想看到体重趋势折线（近 30 天），这样能看出变化方向。
18. 作为宠物主人，我想看到打卡完成度柱状（近 30 天），这样看得出自己记录得勤不勤。
19. 作为宠物主人，我想按时间倒序翻看历史记录。
20. 作为宠物主人，我想改掉今天填错的记录，评分与连续天数随之重算。
21. 作为宠物主人，历史记录不可改（如实呈现），我理解这是为了让数据可信。

**AI 管家**

22. 作为宠物主人，我想用文字描述症状并得到风险等级、可能原因与行动建议，这样小问题不必跑医院。
23. 作为宠物主人，我想上传患处照片提问（客户端压缩后上传），这样说不清的地方能看图。
24. 作为宠物主人，我想在每条回答下看到「本回答由 AI 生成，仅供参考，不构成诊断」的标识，并且复制时标识跟着走。
25. 作为宠物主人，当风险等级是红色时，我想看到置顶的「就医准备清单」并一键复制，这样去医院时能说清楚。
26. 作为宠物主人，我想知道今天还剩几次提问机会。
27. 作为宠物主人，我用完每日 3 次后想看到「明天再来」的提示（而不是引导付费——本版本没有付费）。
28. 作为宠物主人，我想回看历史咨询记录与当时的结论。
29. 作为宠物主人，AI 超时或失败时我想看到「稍后重试」，而不是一直转圈或白屏。

**消息中心**

30. 作为宠物主人，我想收到自家宠物的健康预警（体重连续下降、饮水或排泄异常、疫苗或驱虫临期），这样异常能被主动发现。
31. 作为宠物主人，我想收到预约状态变化的消息（确认、开始服务、完成、取消），这样不用一直去翻预约。
32. 作为宠物主人，我想看到未读角标，并在查看后归零。
33. 作为宠物主人，我想点开预警看到触发依据（指标、阈值、实际值），这样我知道它凭什么提醒我。

**服务与预约**

34. 作为宠物主人，我想浏览服务者（类型、名称、简介），这样我能找到能提供服务的人。
35. 作为宠物主人，我想看服务者详情与其服务项（名称、时长、价格），这样我能比较。
36. 作为宠物主人，我想按日期查看号源余量，这样我能挑合适的时间。
37. 作为宠物主人，我想提交预约（选自己的宠物、填地址与备注、看到金额），这样服务就被约上了。
38. 作为宠物主人，我想在「我的预约」里看到状态与完整流转，这样我知道进行到哪一步。
39. 作为宠物主人，我想取消预约（必填理由），这样临时有事不必硬撑。
40. 作为宠物主人，号源已满或已关闭时我想看到明确提示，而不是一个报错。
41. 作为宠物主人，超出可约窗口或已过去的时段我不应选到。

**我的**

42. 作为宠物主人，我想在「我的」里找到宠物管理、我的预约、消息、AI 记录与账号安全的入口。
43. 作为宠物主人，我想能退出登录。
44. 作为宠物主人，我想在协议页里找到联系方式，遇到问题知道找谁。

**跨角色（后台/服务者侧的联动）**

45. 作为运营，我想在用户列表里分辨出自助注册的用户，并能为其重置密码（无短信通道下的唯一找回方式）。
46. 作为运营，我想在一个统计页上看到四类埋点事件（注册、打卡、AI 咨询、建预约）的次数与转化，这样能看到用户实际在做什么。
47. 作为服务者，我想按一期既有流程接到 C 端用户下的预约并确认、开始、核销。
48. 作为运营，我想在用户注销后看到其数据按留存策略被处理（健康数据删除、手机号脱敏），这样合规要求落地。

**合规与交付（平台视角，但同样要被实现）**

49. 作为平台，我需要在每条 AI 回答上展示合规标识且不可被折叠/截断，这样满足生成式 AI 内容标识的显式标识要求。
50. 作为平台，我需要网络日志留存 ≥ 6 个月、AI 咨询记录 12 个月到期清理，这样同时满足法定期限与「最短必要」。
51. 作为平台，我需要注册与登录有最小限流，避免脚本批量刷号。
52. 作为平台，我需要演示前一键重置到干净数据，这样演示可复现。
53. 作为平台，我需要每日备份并演练过恢复步骤，这样演示环境出问题能救回来。
54. 作为公司验收方，我想按需求对照表逐条核对「已实现 / 有差异 / 出局」，这样验收不用靠口头解释。

## Implementation Decisions

**模块与边界**

- 后端新增 C 端业务模块，全部接口在 `/api/v1/app/**` 下，**复用既有服务层与业务规则**（宠物、健康记录、评分、AI 分级、号源、预约、订单），不另写一套。与既有的「服务者自助 vs 运营管理」两个入口同构。
- 前端新建**独立工程**（Vue 3 + Vite + Vant 4），与后台工程分开；**一套响应式**：移动优先，桌面宽度自适应，不另做桌面版式。底部 4 Tab：首页 / 档案 / AI 管家 / 我的，二级页按需进入。视觉沿用交付文档第三卷的色彩与字号。
- 不引入 BFF；C 端直接调后端接口（与后台同一个同域反代模式）。

**鉴权与会话（ADR-0011）**

- JWT 新增角色 `USER`，`sub` 为 C 端用户 id；`/app/auth/**` 公开，其余 `/app/**` 需 `USER`；**不开放匿名浏览**。既有 P/O 端点不受影响。
- C 端登录态 **30 天**（后台维持 8 小时）；用户表增加**失效版本号**，改密 / 注销 / 全端登出时递增，旧 token 立即失效。
- 注册/登录按 IP 最小限流（超限 429）；密码策略与登录失败锁定沿用一期实现。
- **手机号是登录标识，不是已核验凭证**（演示档无短信通道）；返回与展示一律脱敏。

**数据契约变更**

- 用户表：加密码摘要、消息已读时间、失效版本号；手机号唯一（NULL 不冲突）；来源枚举新增 `SELF`（与代录 `PROXY` 相对）。注释需同步更正（原文写「一期一律 PROXY」）。
- 新增埋点表 `app_event`（用户 id、事件类型、目标 id、发生时间、少量明细），事件四类：注册 / 打卡 / AI 咨询 / 建预约。**与审计日志分家**（ADR-0012）。
- 迁移走既有 Flyway 流程，按 DDL 修订史纪律升版本。

**AI 与配额**

- 单轮分析（输出风险等级 + 可能原因 + 行动建议），**不引入会话概念**；图片输入沿用一期的文件存储，**客户端预压到约 1300×1300 等效像素**后再上传。
- 合规标识：每条回答固定文案「本回答由 AI 生成，仅供参考，不构成诊断；如症状紧急请立即就医。」（研究已确认满足显式标识要素）；对话页另有常驻界面标识；**标识不可折叠、不可截断、复制时随行带出**（ADR-0012 与研究结论）。红色等级附「就医准备清单」。
- 配额：每人每日 3 次，**只计自助发起的咨询**（代录不占用户额度）；超限 429 + 固定文案「今日 3 次已用完，明天再来」，不做升级/邀请引导。
- 失败与超时：沿用一期「提交成功、稍后通知 / 可重试」的降级语义，界面给「稍后重试」。

**消息中心**

- 派生消息流：合并「自家宠物的健康预警」与「我的预约状态流转」按时间倒序分页；**不新建消息表**；未读数用用户表上的「消息已读时间」单列支撑，查看后归零。

**预约与订单**

- 完全沿用一期规则：14 天可约窗口、只校时间冲突（允许同宠物重复约同一服务项）、取消必填理由、不扣费；建单同步建订单、无支付状态。
- 上门类服务的地址默认取用户默认地址，下单页可覆盖；**预约备注**（既有字段）作为用户向服务者主动告知的通道——本版本不做「授权服务者查看健康档案」。

**合规与运维（ADR-0012 / ADR-0013）**

- 协议勾选、账号注销、手机号脱敏三件套；留存策略：网络日志 ≥ 6 个月、AI 咨询记录 12 个月到期删除/匿名化（**落地为定时清理任务**）、健康数据保留至注销、第三方模型委托处理记录 ≥ 3 年。
- 最小运维包：每日数据库备份（保留 7 天，恢复步骤经演练）、后端日志落卷、健康检查端点外部探活。不做监控平台。
- 成本控制：靠每日配额 + 未配置密钥时走规则兜底；**不做代码熔断**。

**部署与交付**

- C 端独立容器 + 新端口，后台 80 端口形态不动；**云主机采购推迟**，本轮先做到本机 + 局域网可演示（独立容器设计不变，上云待采购后执行）。
- 埋点统计页放运营端（只读）。
- 交付物：操作手册（含 C 端章节与手机视口截图）、需求对照表（交付文档八卷逐条标「已实现 / 有差异 / 出局」）、源码提交包（脚本生成，含 `DELIVERY.md`；不开公开仓库）。

**纪律**

- **契约先行**：先把 C 端接口冻结进接口契约文档（端点、字段、状态码、错误码、审计动作），前后端实现会话都按它写。
- **每票一分支**（`t/<票号>-slug`），完成前跑四套验证，通过后合回 `main`。
- 数据范围**服务端强制**，越权 403；金额是字符串；枚举大写；时间带时区；一律使用 `CONTEXT.md` 的术语。

## Testing Decisions

**什么算好测试**：只测**外部行为**——接口的输入输出与页面渲染结果；不测实现细节（不 mock 内部协作对象、不断言私有方法）。测试要能在重构后依然通过。

**接缝（本轮不新增接缝）**：

- **后端唯一主接缝**：起真 MySQL、通过 HTTP 打控制器（一期 76 个测试就是这个接缝与其夹具约定）。
- **UI 接缝**：真渲染断言——把页面开起来，断言关键元素与内容出现、未登录落到登录页、后端不可用时有提示而非白屏；**dev 与构建产物两条路径都跑**（一期教训：曾有「dist 正常、dev 白屏」）。

**要覆盖的关键行为**（各票的验收项里还有更细的）：

- 越权：他人宠物/记录/预约/咨询一律 403；未登录 401。
- 配额：当日第 4 次咨询 429，次日恢复；运营代录不占用户额度。
- 会话：改密/注销后旧 token 立即 401；新 token 正常。
- 注销：注销后不能登录、健康数据删除、手机号已脱敏。
- 号源：并发建单不超卖（一期既有测试的延续）；满号/已关闭返回业务错误而非 500。
- 打卡：同日合并；改当日记录后评分与连续天数重算；新宠物历史记录不足 3 条时体重偏离项不参与计分（一期规则回归）。
- 消息：两类来源合并按时间倒序；未读数随查看归零。
- 埋点：四类事件在对应路径真实落库。
- 限流：脚本连打注册/登录触发 429，正常用户不受影响。
- UI：4 Tab 与各二级页真渲染有内容；AI 标识在渲染结果里存在且未被截断。

**先例**：一期的后端 API 测试、端到端冒烟脚本、UI 联调真渲染脚本、前端构建——C 端把这四套都扩一份；**不追覆盖率数字**（ADR-0013）。

## Out of Scope

- 微信小程序与 APP 客户端（个人主体不可行）；微信 OAuth、JS-SDK、订阅消息推送。
- 真实支付、订阅/优惠券/邀请裂变（模块 D）、在线兽医转人工付费。
- 社区、商城、宠物用品推荐、服务评价与商家排名。
- 短信验证码；域名与 HTTPS（演示档用 IP + HTTP，风险记录在 ADR-0013）；ICP 备案与算法备案（上线档事项）。
- 授权服务者查看健康档案的机制、地图/定位/附近医院推荐、8 类主动提醒（天气/疫情等）。
- 性能压测（500 并发）、单测覆盖率门槛、灰度发布。
