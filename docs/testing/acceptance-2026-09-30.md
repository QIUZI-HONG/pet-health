## 一、结论摘要

**交付文档的 27 项功能：完整完成 14 项、部分完成 13 项、缺失 0 项**，另有 2 个附项已裁决不做。

第十、十一两节的增量把最后两项「缺失」也补齐了。

- **完成（18）**：F001 F003 F004 F005 F006 F009 F010 F011 F012 F013 F015 F016 F017 F019 F020 F021 F022 F027
- **部分完成（9）**：F002 F007 F008 F014 F018 F023 F024 F025 F026
- **缺失（0）**
- **已裁决不做**：微信登录与短信验证码（ADR-0027）、视频理解输入（ADR-0004）
- **支付链**：💳 待甲方澄清（ADR-0002 / 0036：钱在门店付，平台不经手资金）

**契约 160/160 全部有实现**（第十节补 `/providers` 两条、第十一节加目录浏览与推荐 4 条、
第十二节加症状映射 3 条与转人工 2 条）。
剩下的缺口只有一处是「量大」的，其余是界面与口径：

1. **C 端只剩一处界面**：**知识库浏览**（F024/F025）——需要给知识层开一个 C 端只读出口
   （现在只有 AI 服务能读 `knowledge_*`，这是一个小切片）。社区与 AI 管家页的三处缺口都已补上（第十三节）。
2. **服务者侧的照片墙与报工**（F023 的最后一段）：前置是「服务者令牌能否用文件直传接口」未定；
3. **两处口径**已在第十二节裁决：转人工与共享奖励都实现了机制，**区域保护只定了口径**
   （`region_code` 尚无人写入，缺的是业务输入而不是代码）。

工程质量仍在同阶段项目的上游：真实 MySQL/Redis 上的接口测试、契约单一源头 + **DTO 漂移静态校验**

## 五、本轮重构记录（分层 / 命名 / 异常 / 去重 / 注释）

原则与上一轮相同：**只做行为不变的重构，每一处都由三套测试兜底**；动不到的地方写明理由。
下面每一条都在重构后重跑了三套测试。

### 5.1 分层与模块边界

| 改动 | 为什么 |
| --- | --- |
| **新增模块边界护栏** `boot/architecture/ModuleBoundary`（+ `ModuleBoundaryTest`，3 个用例） | 「模块间只能走接口或领域事件」（ADR-0006）原先**没有执行者**——`@MapperScan` 扫的是 `com.pethealth` 全域，任何模块的 `*Mapper` 在任何地方都能注入，「不许碰别人的内部」全靠自觉。现在它是一条会在 CI 红的断言：跨模块 import 只能落在对方的 `api` 或 `event` 包。真树零违规（13 模块 / 441 文件 / 1275 条跨包 import） |
| 收口 4 处跨模块「内部」引用：`AccountService` 不再引 `privilege.domain.InviteRelation`、`BaselineRights` 不再引 `privilege.domain.RightsGrant`、`AssessmentFactSource` 不再引 `order.domain.OrderStatus`、`CheckInPointsListener` 不再引 `privilege.domain.PointBehavior` | 引对方的 `domain` 等于把两个模块焊死，日后拆服务时无从下手。改法是让**拥有方在 `api` 包上给出名字**（`InviteAttributionApi.STATUS_ATTRIBUTED_PENDING`、`RightsApi.SOURCE_*`、`OrderStatsApi.STATUS_*`、`PointsApi.BEHAVIOR_*`，都绑定到本模块 domain 里的唯一定义，不复制第二份），消费方只依赖接口面 |
| 抽取 `boot/support/RepoRoot`（「仓库根在哪」） | 这条判据原先只在 `ContractDtoDriftTest` 里有一份；新增的边界护栏也要读源码树，于是**抽出来两边共用**，而不是写第二份。两处判据**必须**指向同一个目录——否则同一台机器上「契约测试过了、边界测试没过」会非常难查 |

> **没有改** `@MapperScan` 的全局扫描：按模块拆注解**并不能**拦住跨模块注入（bean 依然存在），
> 那是装饰性改动；真正的执行者是上面的护栏。理由写在这里，避免下一轮又有人想「顺手拆一下」。

### 5.2 统一命名与异常口径

| 改动 | 原先 |
| --- | --- |
| 删掉 **10 个**私有 `requireAdmin()`（`ph-privilege` ×4、`ph-provider` ×4、`ph-ai` ×1、`ph-catalog` ×1），统一到 `CurrentUser.requireAdmin()`，61 处调用点显式限定 | 同一个「运营域门禁」有 10 份定义（`static long` / `void` 两种签名、注释各写一份），语义完全相同。收口后「运营接口的门禁」只有一个定义，且它的 Javadoc 明确写着**只校验登录域、不校验角色**（角色细分待 ADR-0035）——原先这个重要限定只在个别类的注释里 |
| 删掉 **5 个**私有 `blankToNull`（`ph-privilege` ×4、`ph-order` ×1），10 处调用改走 `common/util/Text.trimToNull` | 与 `Text` 类自己的 Javadoc 冲突：那个类写明了「这个形状原先在三处各写一份」并把它收口，结果 privilege/order 里又长出五份。语义逐字相同（`null`/纯空白 → `null`） |
| `ReportPayloads.read` 的 `catch (JsonProcessingException) → null` 补 WARN 日志 | 返回 null 是对的（列表页少一段正文好过整页 500），但**不能无声**：触发条件是「库里那行的 payload 坏了或过时」，而它对用户的表现只是「这份报告少了一段」——不记日志则没有任何地方能发现有一行数据已经读不出来（docs/conventions.md 禁止吞异常；同一形状的 `JsonFields.read` 一直是记日志的） |
| 修正一处禁用词：`AssessmentTestSupport` 的注释「某个门**店铺**…」→「某个**服务者**…」 | `CONTEXT.md` 的 _Avoid_ 词表里没有「店铺」，而「店铺」是禁用的「商家」语族的同义词。这是全仓最后一处命中（见 7.3） |
| `ErrorCode` 里 80001/80002/90001 的注释：从「**没有任何代码路径产出它们**，券池与定价两个模块现在都是骨架」改为实际产出路径 | 券池（#110）与标准目录定价（#75）落地之后，那句注释反过来成了误导：它叮嘱读者「别按有产生的思路读这三个码」，而它们**正在被产出**（券锁冲突、定价越界）。与上一轮修的三处同属「注释与实现相反」——这类缺陷的危害是让后来者绕开正确的路径 |

> **核过、判定为「不用改」的两处**（避免下一轮重复劳动）：`ContentReviewService` 的
> `throw new IllegalStateException("不可达：内容类型 …")` 与 `OrderPhotoSlot.slotName` 的
> `IllegalArgumentException`——前者的入参已经过 `ContentType.of(int)`（不认识的码返 40001），
> 后者只被库里查出的槽位调用，两处都是**真不可达**的兜底，抛原始异常比强行套 `BusinessException` 更诚实。

### 5.3 消除重复逻辑

| 改动 | 原先 |
| --- | --- |

## 九、本轮发现但**未修**的问题（交下一轮裁决）

> 第十、十一节的增量解决了其中的第 4 条一半（等级进排序）；其余几条的现状在各自条目里标注。

1. **幂等键的语义与契约不一致（建议优先）**——契约对 `Idempotency-Key` 的说明是
   「同一逻辑写操作重试时保持不变」（`contract/common.yaml:70`），而 C 端五个调用点都在
   *请求真正发出时*才生成键（`OrderCreateView.placeOrder` 等），于是「点了一次、响应丢了、
   再点一次」会带**不同的键**，服务端当成两次操作——**下单与积分兑换这两处可能重复写**。
   请求层的自动重试不受影响（同一请求对象，键不变）。**修法**：键在打开表单时生成、
   成功后重置；提交失败（非业务错误）时保持同一个键。
   已在 `packages/shared/src/http/idempotency.ts` 的 Javadoc 里记下这处差距（避免注释与实现相反）。
2. **条款页在登录前打不开**——`apps/c-web/src/views/LegalView.vue:42` 用 `<SessionGate>` 包住了
   三份条款，而 `LoginView` 上就有「用户协议 / 隐私政策」链接，未登录点进去只会看到
   「条款与账号操作需要先登录」。交付文档 2.5 与合规常识都要求协议**注册前可读**
   （否则「同意」没有依据）。**修法**：条款页按 code 分成公开可读（隐私政策 / 用户协议 /
   AI 免责）与需登录（导出/注销）两组，或让 `SessionGate` 支持只读内容。
3. **被邀请人侧奖励（F016）**——见第六节第 4 项，需要一条 ADR 先裁决「做还是不做」。
4. 🟡 **一半已解决、一半待裁决**：`provider.level` 与 `assessment_monthly_score.recommend_priority`
   原先算出来但**没有任何消费方**（全局 grep 零消费点）——「等级决定 AI 推荐优先级」因此只是数据、
   不是行为。**第十一节把这一半做了**：两条列表按等级优先排序。另一半「区域保护」**仍然缺**，
   而且它不是漏了代码：交付文档只说「等级决定区域保护」，没写规则（半径？每区域配额？超限怎么处置？），
   编一套规则比留着这个缺口更糟——需要一条裁决。

口径不是新定的：**ADR-0050 第二节早就裁决「F011 先做规则版」**（理由：模型版给不出可信的理由，
而规则版的理由是数据）。这一节只是把它实现出来。

| 层 | 落点 | 为什么在这一层 |
| --- | --- | --- |
| 症状识别 | `ai/app/knowledge.py` 的 `match_symptoms` + `POST /internal/symptom-match` | 受控词典（`knowledge_node` 的 name + alias）只有 AI 服务能读（ADR-0009）；口语别名（「拉稀」「没精神」）由它归一，业务侧不必维护第二份口语表 |
| 症状 → 项目 | 新表 `catalog_symptom_rule`（迁移 V36 + 回滚 U36，18 条种子） | 这是**运营会调的业务可调项**（ADR-0010 的三层配置）：新项目上线、项目改名、某条映射不合适——入库才不用发版。症状词用规范名；**只映射医疗类项目**（把症状映到洗护/用品等于在疼痛上做推销） |
| 编排与理由 | `ph-ai` 的 `ServiceRecommendationService`（ph-ai → ph-catalog 单向依赖，不成环） | 症状识别在 AI 侧、映射在目录侧，编排与「那句给人看的理由」只能在这两者之上的第三处 |

四条刻意的取舍：

- **不落 AI 留痕、不占 AI 免费额度**：它是「找服务」不是「咨询」，免费额度的账是 `ai_consult`
  的当日行数（ADR-0024）——有专门用例盯着「这条接口跑完 `ai_consult` 一行都不多」；
- **三种「没有推荐」在契约里是三个字段、界面上说三句不同的话**：认不出症状（换个说法）、
  AI 侧不可用（稍后再试）、认出了但运营没配推荐（直接看目录）。揉成一句「暂无推荐」会让用户
  分不清该改描述还是该等；
- **`notice` 由服务端拼**（免责声明；红色时含「立即就医」）：安全文案只有一个来源，
  前端不许自己写一句「建议就医」；
- **过期的映射跳过而不是报错**：映射被停用、或项目被停用（典型的时间差）都只跳过那一条并记日志——
  静默跳过比把空项目名摆给用户好，但**不能无声**。

### 11.3 等级进排序（F022 的另一半）

- 两条列表（`/providers` 与 `/catalog/items/{code}/providers`）的排序改为
  **等级优先（战略 > 优选 > 基础）→ 评分降序 → id 升序**，契约里两段排序说明同步改了；
- 等级来自考核（`provider.level`，ADR-0052 第三节），所以这就是交付文档 2.3 的
  「等级决定 AI 推荐优先级」——此前这两个字段**算出来了但没有任何消费方**（第九节第 4 条记的缺口）；
- **「没有月度成绩的新店」`level` 是默认的「基础」（1）**：等级只分三档，新店不被特殊对待
  （既不优待也不惩罚），要往上走只能靠考核结果；
- **区域保护仍然没做**，而且它不是「漏了代码」：交付文档只说「等级决定区域保护」，
  没写规则（半径？每区域配额？超限怎么处置？）。编一套规则比留着这个缺口更糟——它需要一条裁决。

## 十二、增量三：两处口径裁决 + 转人工 + 后台页面（2026-09-30 追加）

第九节把两处口径挂成「交下一轮裁决」，用户要求这一轮直接处理。**裁决如下**（每条都写了为什么、
代价与前置条件；它们是可推翻的——推翻时改一处即可）：

### 12.1 转人工（F006 的出口）

**裁决：转人工 = 登记一条工单交给平台运营跟进**（用户在消息中心收到「已受理」，运营回复后再收到一条）。

- **不接支付**：交付文档写「39 元/次」，而本项目钱在门店付、平台不经手资金（ADR-0036），
  没有线上收费路径。要做收费，先得说清收款主体（平台收？还是门店收？）——那是另一条决策。
- **不直接派给服务者**：派给谁需要一套匹配规则（就近？接诊能力？排班？），
  在规则定下来之前，运营先接住、人工判断后再转给合适的门店（线下动作）。
- 落地：迁移 V37 `human_consult_request`（`consult_id` 唯一即幂等键）+ 两条接口
  （C 端 `POST /pets/{pet_id}/ai-consults/{consult_id}/transfer`、运营
  `GET|PUT /admin/ai/human-consults`）+ 两处站内消息。
- **代价写在明处**：这是一条**人工链路**，「预计 2 小时内回复」是运营承诺、不是系统保证；
  工单积压只能靠队列可见性（待处理在前、先到先处理）来暴露。

### 12.2 被邀请人侧奖励（F016 缺的那一半）

**裁决：机制落地、奖励物配置化、默认不发。**

- 新增行为码 `INVITE_INVITEE`（V38），**分值 0 = 记行为不发分**（与种子里 `AI_ADVICE` / `SHARE`
  同一编码）——运营在积分配置里定值之后才会真的发。理由与 ADR-0046 第五节同一条纪律：
  「发多少、发什么」是产品决策，代码不替它拍板；而**没有这个行为码，运营连拍的入口都没有**。
- **发放时机与邀请人同期**（24 小时观察窗结束、关系判定有效那一刻），不是注册即发或建档即发：
  注册即发会让批量刷号当晚就领到奖励，而观察窗（ADR-0039 第三层）正是为拦住它设计的；
  同期发放也让两侧奖励在账上是一件事。
- 幂等：`sourceRef = invitee:{关系id}`（与邀请人的 `invite:{关系id}` 各自成键）。
- **没做的**：券形态。交付文档写的是「20 元洗护券」，而券形态要选模板、要算成本归属
  （ADR-0037 的券池自己有一套责任划分）。积分形态先把机制跑通；要改券，是给这张表加一种奖励物类型。

### 12.3 区域保护（F022 的另一半）

**裁决：本轮不实现机制，只定口径与前置条件。**

- **为什么不做机制**：`provider.region_code` 目前**没有任何代码写入**（全局只有 setter）——
  在一个恒为 NULL 的字段上做配额是死代码，而且会给人「已经有区域保护」的错觉。
- **口径（建议，待确认）**：区域保护 = **审核期的软约束**：同一 `region_code` + 同一 `type` 的
  存量正常门店数超过配置阈值时，运营的审核页给出提示（**不硬拦**——硬拦会把供给卡死，
  而平台在早期更需要供给）。C 端展示**不做**区域隔离：等级优先排序已经体现了优先级。
- **前置条件**：`region_code` 的录入入口（入驻申请里填，或门店设置里补），以及「谁定阈值」
  （建议按城市给运营一个可配的默认值 + 单店例外）。
- 一句话：**这条不是漏了代码，是缺一个业务输入**。补上录入入口 + 一条确认之后，实现量很小
  （一个存量计数接口 + 审核页一句提示）。

### 12.4 症状映射的运营界面（F011 的可调项）

`catalog_symptom_rule` 已入库（ADR-0010 的那一层），本轮把它的**运营 CRUD 补齐**：
契约 3 条路径（`/catalog/symptom-rules` 的列表 / 新增 / 修改），实现落在 ph-catalog
（`SymptomRuleService` 的运营侧方法 + `AdminCatalogController` 的三个端点）。
两道校验都是「早失败比躺着好」：**项目必须存在且启用**（指向停用项的映射永远不会生效）、
**同一（症状，项目）只能有一条**（唯一键兜底 + 人话的 40900）。

## 十三、增量四：两个后台的 16 个页面 + C 端社区（2026-09-30 追加）

第十三节是这批里**量最大**的一块：两个后台的 16 个占位页全部换成真实页面，C 端补上社区。

### 13.1 服务者后台 9 页（`apps/provider-web`）

概览 / 订单 / 核销 / 券 / 考核 / 客户 / 看板 / 营销 / 结算，全部接真实接口。
三处值得单独说：

- **核销「先查后核」**：核销码只用于定位订单，核销接口本身没有请求体、码也不回给门店——
  与契约一致（码是用户的到店凭证，不是门店的收款凭据）；
- **结算中心是对账视图**（券对账含恒等式核对 + 订单流水），页面明写「**没有余额，也没有提现**」
  （ADR-0036：平台不经手资金）；
- **缺口如实写在页面上**：无订单统计接口（今日计数按「五状态各读一次信封 total」派生，
  周/月区间做不了——只有单日查询）、无独立核销记录接口、**报工没接**（前置的三道照片墙要先直传文件域，
  而服务者令牌能否用 `app.yaml` 的直传接口未定）、无客户接口（按订单看到店记录）、
  无服务者侧邀请接口（拉新只读考核明细）。**一个假按钮都没造**。

### 13.2 运营后台 7 页（`apps/admin-web`）

券池 / 补贴券 / 用户 / 内容审核 / 看板 / 考核规则 / 系统配置。三处：

- **补贴券窗口**：契约里没有「窗口」实体（无起止时间字段），页面写明「窗口 = 发放上限 + 模板启停」，
  不摆一个填了没处存的表单；
- **考核规则**的写入口按 `isSuperAdmin` 渲染（配置类动作只归超管，ADR-0037；角色体系未落地时
  按既有实现处理并在注释里写明）；
- **系统配置是只读视图**，并说明为什么（可写项分散在各自模块页；AI 运营页还没有承载页）。

### 13.3 C 端社区（F020 的界面）

一页两 Tab：**同款宠友圈**（经验卡片：物种/品种/病种筛选、点赞、匿名、「只看我发的」）+
**问答互助**（提问 / 回答 / 采纳）。四条口径：

- **匿名**：卡片只渲染契约给的匿名视图，作者身份一个字段都不出现（有用例断言会话昵称不出现）；
- **发帖要权益 `community.post`**：40300 与 40100 分开——前者如实说明「发布内容需要邀请好友或打卡解锁」
  并给三个入口（邀请 / 打卡 / 我的权益），**不是错误态、不给重试**；后者引导登录；
- **入口放首页而不放左栏**：ADR-0041 定的是「社区嵌入首页与档案，不做独立 Tab」——
  路由是次级页，左栏不动；
- **慢病社群后置**（ADR-0050 §一：缺内容流与种子，先做就是空壳），页面上如实说明。

### 13.4 顺手修掉的一个既有缺陷

运营后台的「目录项与区间」「目录外提案」两个面板**首屏不加载**：打开 `/admin/catalog` 时它们是空态
且不发请求，要等用户改筛选才出数据。两行 `void xxx.load()` 修掉（列表面板就该打开即有内容）。

## 十四、增量五：知识库的只读出口（F024 / F025，**后端完成、页面未做**）

知识条目此前只有 AI 咨询能引用（`AiConsultView.citations`），用户看不到「平台到底知道什么」。
这一段把知识层**只读地**开给 C 端：**后端已通、有测试；C 端页面还没做**（如实记在这里）。

| 层 | 落点 | 说明 |
| --- | --- | --- |
| AI 服务 | `POST /internal/knowledge/browse`（`knowledge.browse`） | 按分类 / 关键词分页，或按编号取单条。**与检索是两件事**：检索回答「这次咨询该引用什么」（排序、安全门、关系层召回），浏览回答「知识库里有什么」——所以浏览不做打分、不做禁忌过滤（安全门管的是「不要把禁忌项推荐给这个物种」，而浏览是用户自己翻）。中文匹配仍走同一套 ngram 短语（「犬瘟」能命中「犬瘟热」），同一张表不该有两种搜索行为 |
| C 端契约 | `GET /api/v1/app/knowledge/entries` + `/knowledge/entries/{code}`（一张 `KnowledgeEntryView`） | **需要登录**：与社区同属内容面（权限矩阵里游客只给「浏览服务 / 商家」）；条目要展示复核状态，是「给人看的内容」而不是「找服务」。**列表不下发正文**（点进去才有）；不可读的编号一律 40400 |
| Java | `AiServiceClient.browseKnowledge` + `KnowledgeBrowseService` + `AppKnowledgeController` | 只做透传与字段收口：`risk_hint`（green/yellow/red）翻成 C 端统一口径 1/2/3，信心度这类内部字段不下发 |

**一条安全底线写在契约与 DTO 上**：`review_status` 是**必填**字段，且必须展示——平台的知识条目多数是
`pending_review`（工程按公开兽医共识起草、待合作兽医复核，ADR-0025 第二节），
把待复核说成已复核是 ADR-0033 明令禁止的。

验证：AI 侧 3 条（分类浏览带分类名与总数、关键词与检索同一套 ngram、读不到知识库降级不抛）+
Java 侧 4 条（列表不给正文但给复核状态、详情带正文与来源、不可读编号 40400、需要登录与参数边界、
降级回空列表）。

**这一段没做**：C 端知识库浏览页（F024/F025 的界面）——后端已经可用（接口可直接调），
页面是下一步。这一段之后，F024/F025 的状态仍是 🟡。
