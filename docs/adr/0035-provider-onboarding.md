# 服务者入驻：单人审核、驳回重提不新建记录、资质到期软处理

服务者的准入与资质管理（切片 [#104](https://github.com/QIUZI-HONG/pet-health/issues/104)），
依据交付文档 BPM-4、2.2、2.4 与 7.2 的 `merchant` 表（术语改名 `provider`），
以及地图上的决策票 [#78](https://github.com/QIUZI-HONG/pet-health/issues/78)（入驻与审核）、
[#59](https://github.com/QIUZI-HONG/pet-health/issues/59) / [#60](https://github.com/QIUZI-HONG/pet-health/issues/60)
（后台边界与权限矩阵）。

**本 ADR 的前六条是 2026-09-29 项目所有者对 #78 的裁决**，其余是实现时按交付文档推出来的。

## 决定

**1. 审核流程：单人审核。** 服务者提交申请（按类型提交不同材料：医院要执业许可、
训犬要认证、寄养/喂养要实名）→ 运营**单人**审核 → 通过 / 驳回。
不做「初审 + 复审」双人流程：交付文档没要求（09-22 那版规划把它列为待定项 D9），
而双人会立刻带来「两级都驳回怎么办、复审能不能直接通过」这些没答案的问题。

**2. 驳回可重提，且不新建服务者记录。** 申请即建一条待审核的 `provider`；
被驳回后改**同一份申请单**再提交（`submit_count` 加一，于是「被退回过几次」查得到）。
一个账号同时只能有一份申请单：`POST` 在已有申请时一律 40900 并告诉他去改那一份——
允许新建的话，一次驳回就会在库里留下一个永远不会被使用的空壳服务者。

**3. 审核流水 append-only。** 每一次提交、重提、通过、驳回都写 `provider_review_log`
（谁 / 何时 / 结论 / 理由）。申请单上的 `reject_reason` 只保留**最后一次**结论——
驳回后重提会把上一次覆盖掉，而那正是最需要留痕的一次（ADR-0028 对审计的同一取舍）。
三类审核共用这一张表（入驻 / 上架 / 提案），它们的结构完全同构。

**4. 审核通过的那一刻绑定账号。** 申请人成为该服务者的**管理员**
（`provider_user`，唯一键 `(provider_id, user_id)`）。**技师是管理员的权限子集，不是第二套账号体系**：
同一人兼任时只留一条 `role=1` 的记录；本切片的门禁只认管理员（技师的动作范围由
[#87](https://github.com/QIUZI-HONG/pet-health/issues/87) 定：接单、报工、三道照片墙）。

**5. 唯一性：同一营业执照 / 身份证只允许一个「有效状态」的服务者**——
有效状态指「待审核」或「正常」；**被驳回或已冻结的记录不占名额**，
否则一个人被误拒一次就再也开不了店，而纠正一次错误的审核本来就该是可能的。
这条在**应用层**校验，不建数据库唯一索引：MySQL 没有「部分唯一索引」，
硬把 `cert_no_hash` 建成全表唯一会让「被驳回的那份也不能再提交」成为事实，与上面冲突。
校验走 HMAC 查找列（ADR-0013：密文没有保序性，等值比较只能用 HMAC）；
只认营业执照与身份证——执业许可证、健康证按人或按门店发，多点执业是正常现象。

**6. 资质有效期：`valid_until` + 到期软处理。**
- **到期前 30 天**：进入续期提醒窗口（交付文档要求）。真实投递要走消息中心与提醒体系
  （ph-reminder），本切片在 `QualificationExpiryJob` 里扫出来并记 WARN——**没有新造通道**；
  对接见下面的「需要协调」。
- **过期后**：该服务者的**资质全部过期**时，**自动下架他的全部在架服务项**，
  但**不注销服务者**——历史订单、档案与客户关系都留着；补交材料后即可恢复上架。
  只判「有没有一份没过期的材料」，与上架门禁用的是同一个判断
  （`ProviderAccess.hasValidQualification`），两处不能各写一套。
- 档下架**逐条留流水**（`action=下架`、`actor_id=0` 表示系统写入）：
  「谁下的架」在服务者看来是个突发事件，必须查得出来是系统按规则做的。

**7. 补交材料即可恢复上架。** `PUT /profile/qualifications` 整体替换材料（新材料状态为待审核），
上架门禁只看「有没有一份没过期的材料」，不等运营复核——「补交」这个动作本身就是他重新作出的承诺。
**材料本身的复核流程（谁看、多久看、驳回后怎么办）未定**，列入待澄清。

**8. 门店信息变更不需要重新审核。** 交付文档没要求；本切片不自行加一道。
若日后要加，触发点已经唯一（`ProviderProfileService.update`），加一个状态即可。

**9. 驳回的服务者不能直接「解冻」为正常**：必须重新提交申请并审核通过。
否则一次驳回就等于白拒，而「被驳回的记录不占唯一性名额」这条规则也建立在
「驳回与冻结必须经由审核流程复位」之上。

**10. 清退 = 冻结（禁止新订单与新上架）+ 保留历史订单与档案 + 已预约订单转「取消」**
（不是退款：ADR-0036 已定平台无资金流，退款退化为线下动作）。
本切片只实现「冻结 / 解冻」与「禁止新上架」这一半：**已上架的服务项不自动下架**——
冻结与下架是两个动作，焊死会让解冻时也恢复不了原状；C 端浏览与下单必须按服务者状态过滤
（那属于订单侧）。「已预约订单转取消」归订单模块（#77）。

**11. 敏感字段一律密文 + 脱敏出。** 门店联系电话、资质证件号都按 ADR-0013 处理：
AES-256-GCM 密文 + HMAC 查找列，接口只返回脱敏值（`138****1111`、`9133****1234`）。
列表接口不解密（除了运营审核队列需要联系电话联系人，那是「审核必需」的例外，
且仍只给脱敏值）。

## Considered Options

- **初审 + 复审双人审核**：见决定 1。将来若监管或投诉压力要求双人，加一级状态即可，
  表结构不用动（`provider_review_log` 已经能记多级结论）。
- **驳回后新建一份申请单**：会让「被退回过几次」散在多个服务者记录里，
  还会留下空壳 `provider`。否决。
- **资质过期自动注销服务者**：会把历史订单、客户关系与档案一起切断，
  与交付文档 2.4「保留历史订单与档案」的方向相反。选「下架不等于清退」。
- **给「资质过期」单独加一个 `provider.status`**：状态会变成五个，
  而「资质过期」与「运营冻结」的后续处置完全不同（一个补交即恢复、一个要人解冻），
  合成一个状态会让两者在数据上长得一样。改为**由材料与上架门禁推导**，不落状态。
- **建一套服务者后台账号体系（独立表 + 独立登录）**：交付文档 2.2 把技师与管理员放在同一张
  权限矩阵里，说明它们共享账号；独立一套会立刻产生「同一个人既是用又是技师」的双份身份。
  选「绑定现有账号 id」，后台登录入口留给账号体系切片（见「需要协调」）。
- **数据库唯一索引保证营业执照唯一**：见决定 5。

## Consequences

- **「还没通过审核」是有状态的**：申请中 / 已驳回的账号**没有** `provider_user` 绑定，
  于是门店类接口读 40400、写 40300（消息里说清是「审核中」还是「已被驳回」）。
  审核进度与门店快照走 `/onboarding/applications/{application_id}`（详情里带着 `provider`）。
  前端不该在通过审核前去调门店接口。
- **服务者后台的账号体系与角色体系尚未落地**：本切片的 `provider_user.user_id` 与 C 端
  `user.id` 同域（测试直接给该 id 签 `provider` 域令牌）。这不是设计，是**待补的缺口**，
  见「需要协调」。
- **冻结不下架存量服务项**：C 端可能短暂看到「已冻结服务者的服务项」，直到订单侧按
  服务者状态过滤。这条代价写在这里而不是藏着。
- **审核没有通知**：本项目没有推送通道，服务者要自己回来看看（消息中心在 #99 的范围里，
  服务者侧的消息投递未实现）。
- **资质过期的批算是定时任务**，测试直接调 `sweep()`（唯一一处偏离 ADR-0014 的
  「只测 HTTP 缝」，理由写在 `QualificationExpiryTest` 的类注释里）。

## 待澄清

- **资质材料的具体清单**：F012 只说「按类型动态生成」（医院要执业许可、训犬要认证、
  寄养/喂养要实名+背景审核），没给逐项清单，也没说哪些**必须带证件号**
  （唯一性校验只对填了证件号的材料生效）。这份清单要甲方或法务确认。
- **资质材料的复核流程**：补交材料后谁看、多久看、驳回后是否再次自动下架，未定。
  本切片按「补交即恢复上架」实现（见决定 7）。
- **一个人能否同时是两家服务者的管理员**：本切片按「绑定取最早一条」处理，
  没有做多店校验。连锁门店是真实场景，规则要与 #59 / #60 一起定。
- **清退的订单处置**：已预约订单转取消需要订单模块（#77）配合，本切片只做冻结。
- **区域保护与目录的关系**：见 ADR-0034 的待澄清。
- **资质过期的提醒文案与频次**：与 #99 的提醒体系一起定（红色不可关闭那一套不适用于这里）。

## 需要协调（本切片做不到的部分）

按 AGENTS.md 的硬约束，以下都要改别的模块，**本切片停在这里并记录下来**：

1. **`audit_log`（ADR-0028）**：运营的审核与处置动作应当进账号域的操作审计表。
   `AuditRecorder` 在 ph-account，没有对外接口，本切片不能调它，改用
   `provider_review_log` 承担「审核流水」的职责（那张表本来也是交付文档要求的）。
   对接建议：ph-account 暴露一个 `AuditApi.record(action, targetType, targetId, detail)` 接口。
2. **资质到期提醒**：按决定 6，提醒要走 ph-reminder 的消息体系，
   需要一个「给服务者写一条站内提醒」的接口（现有的 `message` 是账号级、面向 C 端的）。
   在那之前，`QualificationExpiryJob` 只记 WARN。
3. **服务者后台 / 运营后台的登录入口与角色声明（ADR-0037）**：
   交付文档 2.2 与 ADR-0037 把「入驻审核」划给平台运营、「清退」与「目录项删除」划给超级管理员，
   而现有 JWT 只带登录域（`app` / `provider` / `admin`）、不带角色，
   本切片因此**判别不出运营与超管**，对所有 admin 域身份一视同仁。
   要落地矩阵需要在账号体系里加角色（或在 JWT 里加 `roles` 声明）。
4. **C 端浏览服务者与服务项**：`contract/app.yaml` 与 `/api/v1/app/**` 不在本切片的改动范围，
   浏览接口留到下一波；届时「服务者状态 + 服务项状态 + 资质未过期」三个条件都要参与过滤。
