# 权益引擎的实现口径：实时判定、来源优先、到期只回收那一条

实现 [ADR-0038](0038-order-redeem-rights-points.md) 第三节（权益码表 + 实时判定 + 来源优先）的切片（#112）。
契约在 `contract/admin.yaml` 的 `/rights/**`，代码在 `ph-privilege`（`RightsEngine` + `RightsAdminService`），迁移 V25。

对象与来源定义在 ADR-0038 里，本文只写实现决策与它引出的取舍。

## 一、判定是实时的，不缓存（决定）

`RightsApi.evaluate(userId)` 每次查库：两张小表（`rights_code` 全表 + 该用户的 `rights_grant`），
两个索引，没有缓存的必要。

**否决「缓存判定结果」**：权益决定功能能不能用，缓存漂移的代价不对称——
用户看不到自己的权益、也不知道为什么，**无法自救**；而缓存的收益在这个体量上等于零。
这一条与「列表缓存 5 分钟」（docs/conventions.md）不冲突：那是展示数据，这是功能开关。

## 二、来源优先级 = `source` 的数值升序，且不比较到期时间（决定）

```
订阅(1) > 邀请(2) > 打卡(3) > 运营补偿(4)
每个码取「当前生效」的授予里 source 最小的那一条
```

举例把语义钉死：用户有一条邀请来的永久权益，又订了一个月订阅——

- 正确：他有两条记录，判定取订阅（当前最高优先级）；月底订阅被回收后，**邀请那条仍在**；
- 错误（按到期时间取）：判定会说「他拥有永久权益」，于是订阅到期后回收流程不知道该收哪一条，
  两个来源的信息就丢了。

这是 ADR-0038 第三节的原话，实现上就是 `evaluate` 里那一行 `grant.getSource() < current.getSource()`。

## 三、每条来源各写一条授予，到期只回收该来源那一条（决定）

- 表结构：`rights_grant` 一行 = 一个码 + 一个来源 + 一个到期时间；
  `(user_id, code, source, source_ref)` 唯一；
- 到期回收（`RightsExpiryJob`，每天 00:40）是一条**条件更新**：
  `WHERE status = 1 AND expire_at IS NOT NULL AND expire_at < now`。

  「订阅到期不触碰邀请得的永久权益」在实现上**不是靠逐条判断来源**，而是靠条件本身——
  邀请那条没有 `expire_at`，条件更新根本不会命中它。这是最省事也最不容易写错的写法：
  判据写在 SQL 的条件里，而不是写在某个循环的 if 里。

- 判定也不等回收：`isEffectiveAt(now)` 按时间实时算，所以**批算没跑也不会有人用到一个过期的权益**，
  批算只做状态收尾（让「当前有多少条在生效」数得清）。

## 四、码表可扩，但扩码 ≠ 长出新能力（决定）

运营可以在后台加码（`POST /admin/rights/codes`），但**新码在判定侧默认不生效**——
能力要有模块按它写判定。这条必须显式否掉「加一行数据就多一项功能」的期待，
否则第一个新码就会以「加了码但没效果」的形式变成故障。

因此：码表维护的接口文案里写了这句话（契约里也写着），ADR 里再钉一次。

## 五、`care.mode` 不在码表里（决定，照抄 ADR-0032 / ADR-0038）

专项照护模式按医学事实（7 岁 / 慢病）自动开启，属「照护事实」，不属「可授予的能力」。
本切片用一条**哨兵用例**把它钉住（`RightsEngineTest.careModeIsNotARightsCode`）：
码表恰好是四个码，`care.mode` 不在其中。这样将来有人想把它加进来，测试会先红。

## 六、运营侧给了「手动授予」与「回收一条」两个口子（决定）

- 手动授予的典型用途是**订阅**：ADR-0036 之后订阅没有支付载体，只能线下签约 + 后台标记
  （#71 另议）；第二个用途是客诉补偿（`source=4`，理由写进备注）；
- 「回收一条」（`DELETE /rights/grants/{grant_id}`）是顶层资源的删除口径：
  重复回收 / 删别人的一律 **40400**（docs/conventions.md），
  因为这条记录「不存在」与「已经回收过了」对外是同一件事；
- **没有「补一条历史权益」的入口**：授予只对将来生效，不追溯（补发是运营显式动作，
  不是系统偷偷补的数据）。

## 待澄清（需要拍板）

1. **`quota.ai.bonus` 的额度口径**：码表里它有名字（「额外咨询额度」），但「额外多少条」没有依据。
   实现上它是给 ph-ai 判定用的布尔值；要变成「+N 次」需要一张额度表或一个约定（属 #71 / #80 的后续）；
2. **谁负责判定各码**：本切片只提供判定结果，不提供能力。四项能力的落地分别归
   ph-ai（`ai.unlimited` / `quota.ai.bonus`）、ph-record（`report.full`）、ph-content（`community.post`），
   这些接线点**不在本切片**，需要在各自切片里调 `RightsApi.isEffective`；
3. **订阅的录入方式**：当前是运营手动授予（后台标记有效期）。若将来有支付载体（#71），
   订阅要有自己的表与自动续期逻辑，本引擎这层不用改（来源已经是枚举里的一项）；
4. **打卡来源的到期口径**：本切片的实现按「当月有效」，但 ADR-0038 只写了「打卡阶梯（当月）」，
   没有说「当月」是自然月还是「最近 30 天」。实现选了自然月（`grant` 时由调用方给出到期时间），
   打卡模块接进来时要与产品确认。

## Consequences

- 交付文档把权益四项能力与「专项照护模式」并列，**本切片按 ADR-0032 只实现前四项**，
  照护模式仍是自动开启的照护事实——这一条要与验收方说明；
- 权益与积分是**两套账**（ADR-0038 第四节）：本引擎不记分、积分不发权益，
  同一个行为可以同时推进两边，但奖励物不重复（见 [ADR-0046](0046-invite-and-points.md)）；
- 判定视图（`GET /admin/rights/users/{user_id}`）是客服排查的唯一入口，
  它走的就是各模块共用的那份判定——**任何模块自己拼一套规则都会让客服与用户看到两个答案**。
