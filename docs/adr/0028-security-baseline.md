# 安全底线：统一限流、操作审计、写接口幂等

交付文档 6.3 的十三条安全方案里，**越权（40400 口径）与字段级加密已分别落在
[ADR-0011](0011-persistence-and-migrations.md)/[ADR-0013](0013-field-encryption.md)**。
本条补齐剩下三道在代码里**零落点**的机制，并明确哪些首期不做。

## Considered Options

### 限流放在哪

- **网关**：交付文档 6.1 画了网关层，但 [ADR-0003](0003-lean-middleware.md) 已经把它去掉——没有网关可放。
- **每个接口自己判**：#81 明确反对，理由是会漏（新接口没人记得加）。
- **一个过滤器 + 路径规则表**（选它）：规则走配置（`app.rate-limit.rules`），新增接口时改配置不改代码；
  阈值是**技术参数**（改要重启），按 [ADR-0010](0010-ai-config-layering.md) 不进库。

计数用 **Redis 固定窗口**（`INCR` + 首次 `EXPIRE`，与 `LoginThrottle` 同一手法，不引 Lua）。
**计数键按规则分开**（键里带规则前缀）：不同规则各有各的预算，否则匿名流量会花掉留给登录的那 30 次；
且各规则的 `window` 可以不同，共用一个键时先来的那条 window 会主导整个键的寿命。

**限流器自己故障时一律放行**（Redis 不可用 → 记 WARN 并放行）。限流是防滥用，不是鉴权；
让它把整个 API 拖成 500，代价远大于「这一小段时间没限流」。这与「红线词表读不到就不放行」是两件事——
那一层失效会漏掉急症，这一层失效只是少了一道防刷。计数器没有 TTL 时自愈补一个，
否则那个主体会被永久限流。

**匹配必须用归一化路径**：容器给的 `getRequestURI()` 是**未解码**的，而路由按解码后的路径走，
拿原始 URI 做前缀匹配会被 `/%61pi/...` 这类编码绕开——实测过，能进控制器却匹配不到规则，
等于限流不存在。所以限流与鉴权都走 `RequestPaths`（Spring 自己的 `UrlPathHelper`），与路由同源。
不选滑动窗口与令牌桶：限流的目标是**防刷**而不是精确整形，固定窗口实现最简、行为最可解释，
代价是窗口边界可能出现双倍突发——这个代价写在下面。

**主体怎么定**：已登录按 `user_id`，未登录按来源 IP。**不读 `X-Forwarded-For`**——
那个头是客户端可伪造的，一旦信任它，任何人都能靠改一个头把自己伪装成新来源，限流等于没有。
等 [ADR-0003] 之后的部署方案（#66）定了反向代理，再加一个「可信代理」开关，
只在请求确实来自白名单内的代理时才采信该头。

**但接口限流的兜底规则照样管到 AI 接口**（600/分钟/主体）：那是**传输层防刷**，
与「今天还能问几次」的业务配额是两把尺子。别把 600 当成额度——它是「一分钟内打超过 600 次就一定是脚本」的下限。

**AI 咨询的业务配额不走这里**：[ADR-0024](0024-quota-care-community-tracking-packages.md) 定了
AI 每日额度「只计数不拦截、由界面劝说」，与限流的「到量即拒」是两种语义，不要把两者合并。

### 审计日志怎么落

记什么（首期）：`register` / `login_success` / `login_failed` / `account_export` /
`account_deactivate`。即**账号安全事件**与**敏感数据访问**两类。

- 不记「谁看了自己的宠物」这类常规读：量大、无合规价值，且与 ADR-0011 的列级留痕（`updated_by`/`trace_id`）重叠。
- 管理员的写操作要记，但**管理端接口还不存在**（#118），届时扩展动作码即可。

**不记 PII 明文**：登录失败的 `subject_ref` 存手机号的 HMAC（不可还原），
用途是「串出同一个号被撞了多少次」；原始手机号、昵称、症状描述一律不落审计表。

**必须独立事务**（`REQUIRES_NEW`）：登录失败会抛异常，业务事务注定回滚——
审计若是跟着它走，那正是最该留下记录的一次操作反而什么都没留下。

写入失败**只记 ERROR、不阻断业务**：审计是观测手段，让用户登不上不是它的正确代价。

这一层**可度量**：失败会累加 `ph.security.audit.write_failed`（见 `SecurityMetrics`），
在 `/actuator/prometheus` 上取得到。机制自身的四个指标是——
`ph.security.rate_limit.rejected`（带 `rule` 标签）、`ph.security.idempotency.replayed`、
`ph.security.idempotency.conflict`（带 `reason` 标签）、`ph.security.audit.write_failed`。

**但「告警」还没做**（面板与告警规则属 #88 / #121，指标名在 #88 定清单前是暂定的）：
今天指标在那里，**没有人会被告知**。所以出问题时仍然要有人去看——只是从「翻日志」
变成「看面板」。在告警接上之前，不要把它当成有监控的安全网。

**「事实」与「尝试」分开记**：`recordOutcome`（注册成功、登录成功、导出、注销）挂在事务**提交之后**
才写——审计若抢在提交前落库而事务随后回滚，就会留下「说发生了、其实没发生」的假记录，
而审计的全部价值在于可信，**假记录比缺记录更糟**；`recordAttempt`（登录失败）**立即写**，
不随业务事务回滚，因为「有人撞我的号」正是要留证据的那一次。

### 写接口幂等怎么做

交付文档 13.2 要求「接口幂等」，`docs/conventions.md` 此前把它挂在 #81 上没有结论。

结论：**`Idempotency-Key` 请求头 + Redis 存首次响应**（键 = 调用方 + 方法 + 路径 + 该头），
只对写方法生效。重复提交同一个键时直接回放首次的响应，不再执行。

- 不选「只靠唯一索引兜底」：那只能覆盖插入类操作，且失败时给的是冲突而不是**同一个答案**——
  调用方重试后拿不到第一次的结果，正是幂等要解决的问题。
- 不选「前端禁用按钮」（现状）：那是体验，不是协议保证；换标签页、断网重试都会绕过去。

实现时定下来的五条边界（原文没写，补在这里，改动前先读 `IdempotencyFilter` 的类注释）：

1. **可选**：不带这个头的请求行为完全不变。幂等由客户端主动声明，不是给所有写请求套一层。
2. **只处理 `Content-Type: application/json`**：算请求指纹要先把请求体读进内存，
   而上传接口是 10MB 的字节流——拿内存换一个不需要的功能不值。上传的重复提交由上传凭证管（ADR-0020）。
3. **5xx 不持久化**（按 IETF `Idempotency-Key` 草案）：瞬时故障若被记下来，
   会在 TTL 内「粘住」，客户端怎么重试都拿到同一个失败。所以 5xx 与「链子抛异常」都**释放键**；
   2xx 与 4xx 回放（4xx 是确定性结论，且 AI 咨询这类**可能已经花过钱**的写操作宁可回放也不重跑）。
4. **在途返回 40900**：上一次还没跑完时同键再来，直接告诉它「处理中」，不排队等待。
   **在途标记的 TTL 单独压短（60 秒）**，不用配置里那 10 分钟：一个卡住或被杀掉的请求
   不该让同一个键的重试堵满整个窗口。
5. **同键换请求体返回 40001**：指纹（方法 + 路径 + 请求体摘要）不一致就拒掉——
   否则客户端拿旧键发新请求会拿回上一次的答案，「看起来成功、内容不是这次的」，比报错危险。
   **这种用法刻意不释放键**：释放等于允许那次「不同的请求」去执行，而它本来就该失败——用户要换一个键。
6. **写入与释放都校验归属令牌**：认领（`SETNX`）是原子的，但**认领之后的收尾不是**。
   执行时间超过在途 TTL 时，另一个请求会认领并写好结果；此时先那个请求的收尾若盲写就会**覆盖**正确结果、
   若盲删就会**删掉**它。两者都让同一个键执行两次，正好毁掉这个功能的全部承诺。所以每次认领生成一个令牌，
   写入/删除都走 Lua **比对令牌后才动手**，不属于自己的记录一律不动。
7. **两处静默放弃幂等**（调用方以为幂等、其实不是，所以都记日志）：
   客户端给的键超过 200 字符；响应体超过 256 KiB。前者基本是程序 bug，后者是不拿内存换一个不必要的功能。

**幂等键在 Redis 不可用时怎么办**：**放行（不做幂等）**，与限流同样的取舍——
让一次缓存故障把写接口整体打成 500 的代价更大。但要认清代价的方向不同：
限流失效只是少一道防刷，**幂流失效是可能重复执行一次副作用**（AI 咨询会多花一次钱）。
这里有第二个理由支持放行：本仓的写接口多数自身幂等（打卡是 upsert、注销幂等、已读可重复、落定有唯一键兜底），
幂等键是给**不幂等**的那些（建宠物、AI 咨询、发券）加的保险；保险失效时业务本身不会崩，只是可能重复一次。
调用方拿到的是正常 200，**没有任何信号**说明这次没幂等——这是刻意的（不让内部故障泄漏给客户端），
但要靠日志告警发现（`幂等键不可用` 为 WARN 级）。

**状态**：三道机制（限流、审计、幂等键）均已落地。

## Consequences

- **阈值有两处**：`application.yml`（源头，运维改这里）与 `RateLimitProperties` 的 Java 兜底默认值
  （配置整个缺失时的退路，值刻意与 yml 一致）。两者不同步时以 yml 为准。
- **限流的代码放在 ph-account**，而同样横切的 `TraceIdFilter` / `CurrentUser` / `ClientIp` 在 ph-common。
  这是有意的：账号域是安全机制的归属模块（限流、令牌、审计都在这里）。若将来服务者/运营后台也要各自的
  限流规则，再把这一套整体挪到 ph-common（届时 ph-common 要加 Redis 依赖）。
- **固定窗口的双倍突发**：窗口边界前后各打满一次，瞬时流量可达阈值的 2 倍。防刷够用，不做整形。
- **对外可见的两处**：超限返回 `42900`（交付文档 8.2 的「请求过于频繁」）并带 `Retry-After` 秒数头，
  两者都写进了 `contract/common.yaml`。**但登录失败锁定的那个 42900 目前不带这个头**（由
  `LoginThrottle` 抛出、走异常处理器，没有设响应头的位置），只在那句 `message` 里说了要等多久。
- **未登录调用方的幂等键在共享出口下会串键空间**：`CallerKey` 对未登录请求回落到 IP，
  所以同一个 NAT 后面的两个人共享键空间——一个人可以「占住」某个键让另一个人拿到 40900，
  且对**匿名可写**的接口（注册、登录）同键同体还会拿回对方的响应。
  这是「不登录就无法区分调用方」的固有代价。缓解方向是让需要幂等的写接口都要求登录（本仓绝大多数已经如此）。
- **重放响应体里的 `request_id` 是第一次那个**，而响应头 `X-Request-Id` 是本次的：
  这是「回放首次结果」的必然含义（那才是同一次逻辑请求的答案），排查时以响应头的 traceId 为准。
- **未登录接口按 IP 限流在共享出口下会误伤**（公司 NAT、家庭）——所以未登录接口的阈值要给宽，
  登录/注册这类真正的防刷点另用更严的规则 + `LoginThrottle` 的账号维度兜底。
- 审计表**只增不改**（append-only），不参与软删除：审计行的价值来自「不可否认」，
  能删就等于没有。它也因此**不随账号注销而删除**——`subject_ref` 是 HMAC。
- 但 **append-only 是约定，不是类型保证**：`AuditLogMapper` 继承 `BaseMapper`，`updateById` / `deleteById`
  在类型上可用。本仓不写代码去调它们，而 `U13` 的 `DROP TABLE` 是 ADR-0011「迁移必须可逆」要求的逃生口——
  「不可删」指的是**业务运行期**，不含回滚脚本。
- **`subject_ref` 是可重识别的稳定假名**：它与 `user.phone_hash` 是同一个 HMAC，拿审计行 join 用户表
  就能还原到人。「不可还原」是相对密钥而言；要不可关联就得用独立盐，但那样会丢掉
  「串出同一个号被撞几次」的用途。当前取舍：**要可追责，接受这个关联性**。
- 保留期**暂不设自动清理**：删除策略应当从合规文本（#74 / #120）倒推，
  不由工程随手定一个数字。在那之前按「与账号数据同寿命」处理。
- 本条**不覆盖**：病毒扫描与鉴黄（外部服务，有成本，与 #84 的边界另议）、
  CSP（要等 #66 定静态资源与 API 是否同源）、日志聚合选型（#88）、
  以及 P95/错误率告警（#88 / #121）。
