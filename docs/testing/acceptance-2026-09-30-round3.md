## 一、结论摘要

**交付文档的 27 项功能：完整完成 12 项、部分完成 15 项、缺失 0 项**，另有 2 个附项与 2 个半项已裁决不做。

- **完成（12）**：F001 F002 F003 F006 F008 F009 F010 F011 F012 F013 F014 F027
- **部分完成（15）**：F004 F005 F007 F015 F016 F017 F018 F019 F020 F021 F022 F023 F024 F025 F026
- **缺失（0）**
- **已裁决不做**：微信登录与短信验证码（ADR-0027）、视频理解输入（ADR-0004）、
  提醒的「天气 / 疫情」两类（ADR-0019）、以「行为」为主线的独立改善报告（ADR-0031）
- **支付链**：💳 待甲方澄清（ADR-0002 / 0036：钱在门店付，平台不经手资金）

与上一轮（完整 13 / 部分 14）相比**完成数少 1 项**，但**逐项看是四个方向都有变化**，没有一项是「功能退步」：

**A. 有一批缺口在上一轮落笔后被补掉了（本报告从 🟡 升为 ✅ 或删去该缺口）**

1. **两个后台的登录入口**（上一轮的头号缺口）现在已经落地：`ConsoleAuthController` 的六条
   `/provider|admin/auth/{login,refresh,logout}`（契约 168 个路径里新增的 6 条就是它）、
   生产代码按域签发 PROVIDER / ADMIN 令牌（`ConsoleAuthService` → `AccountService.issueTokens`）、
   两端各有一个真登录页（`apps/{provider,admin}-web/src/views/LoginView.vue`）与顶栏入口，
   并有 `ConsoleLoginTest`（6 例）与 `ConsoleAdminAdmissionTest`（3 例，含 admin 名单 fail-closed）。
   **20 个页面「实现了但到不了」这句话在当前树上不再成立。**
2. **F027 条款页公开可读**：`LegalView.vue` 已去掉闸门、后端把两条 compliance GET 放进公开读白名单，
   登录页上的「用户协议 / 隐私政策」现在点得开（合规缺陷关闭）→ F027 升 ✅。
3. **F026 的两条业务消息**：券过期提醒（`CouponExpiryJob.remindExpiringCoupons`，去重键
   `coupon-expiring-{id}`）与预约提醒（`AppointmentReminderJob`，每小时、2 小时窗口、
   `order-appointment-{id}`）都已有生产者，邀请进度通知也有了（`InviteService` 的 `TYPE_INVITE`）。
4. **F002 的资料编辑入口**（上一轮记为缺口）已接上：`ProfileView.vue` 的「编辑资料」按钮 →
   `cApp.updateMe`，并有 `profile-edit.spec.ts` 4 例钉住「留空＝不改 / 空串＝清空」。

**B. 本轮的独立复核查出四处「上一轮给了 ✅ 但要求没成立」——这是本轮最重的发现**

5. **F016 的邀请反作弊：三层判据在生产只有一层活着**（详见第二节 F016）。三层判据是真代码，
   但其中两层要求「邀请码主人的设备 / IP / 号段」非空，而**创建邀请码的唯一生产入口传的是三个 null**
   （`AppGrowthConsole.createInviteCode` → `inviteApi.ensureInviteCode(userId, entry, null, null, null)`），
   所以那两列在生产库里恒为 NULL、永不命中。测试之所以全绿，是因为它们**直接调 API 传了这三个值**
   （`InviteTest` 7 处），HTTP 用例只传 `channel`。**这与上一轮修的「端口只有测试实现」是同一型缺陷**：
   测试证明机制可用，生产路径是断的。
6. **F017 的「打卡得券」没有实现**：`Coupon.SOURCE_CHECK_IN_TASK=2` 这个来源码与它的字典项都在，
   但生产代码里 `couponApi.issue` 只有三处（邀请 / 月度阶梯 / 积分兑换），**没有一处用它**；
   打卡只发积分。另外任务中心的 6 条任务里有 3 条（签到 / AI 建议 / 分享）**没有任何加分成产者**。
7. **F019 的「三级权益总表」在数据层不成立**：`user_right` 的种子只有 4 行码，其中只有
   `community.post` 有真正的消费者；打卡阶梯权益（`SOURCE_CHECK_IN=3`）**没有任何生产授予路径**。
8. **F020 的「录入即生成卡片」不成立**：`createCard` 在前端零调用点、后端也没有「打卡 / 就医记录 →
   建卡」的 hook。卡片的**唯一生产者是测试**。

**C. 另有五处是**口径**修正（结论对、说法更准）**

9. F005 的「7 天补录」只到 API 层——C 端没有日期选择器，用户只能补今天/撤销今天。
10. F007 的「天气、疫情（未开票）」写成「差两项」不准确：那是 **ADR-0019 的明确裁决**（首期砍掉），
    属于 ⛔ 而不是欠账；真正的欠账是 `reminder_rule` 与 `care_mode_rule` 的运营入口（ADR-0010 的
    「业务可调项进运营后台」在这两项上只落了一半）。
11. F008 的「没有以行为为主线的独立报告」同样是 ADR-0031 的裁决（「不再各出一类报告」），
    不是漏做 → F008 升 ✅，那半项记 ⛔。
12. F015 的券来源是**五种**（含月度阶梯），不是上一轮写的四种；且发放侧确实有一处「自动挑贡献」
    （承担成本的服务者额度），只是它不是 BPM-3 要的「为用户匹配最优可用券」。
13. F004 的生产写入有**三处**都写死 `SOURCE_USER`（上一轮写两处）。

**D. 还有三处新发现的生产面缺口**（上一轮未载，见第五节 5.4 与第六节）

14. **F018 的月度批算在生产没有事务**：`MonthlyLadderJob.scheduled()` 调本类的 `run()` 是**自调用**，
    Spring 的事务代理不生效——而它的 javadoc 承诺的「重跑不会重复发券」正建立在「一次批算一个事务」上。
    **本轮已修**（连同另外三处同类写法），并加了一道结构护栏。
15. **运营后台的 AI 运营写入面缺页**：`/admin/ai/*` 的七个写入接口（提示词 / 红线 / 分级规则 /
    护栏词表 / 运行时开关）后端与契约都齐，运营后台只接了**两个只读**（`GET /ai/prompts`、
    `GET /ai/switches`），`SettingsView.vue` 自己写着「AI 运营模块缺页」——ADR-0010 的
    「入库 + 运营后台」只落了一半（改红线现在要直连 API 或改库）。
16. **ADR-0040 要求的「轮询兜底」没实现**：三端 0 处 `setInterval` / `EventSource` / `WebSocket`。
    实时通道按该 ADR 后置是对的，但「后置」的**前提**是轮询兜住，而现在两条都没有。

**工程质量仍在同阶段项目的上游**：本轮又把两条「只有约定、没有执行者」的规矩变成了断言
（调度与事务的边界、契约与 DTO 的漂移**各在本轮抓到一次真实偏差**），并把一处跨端重复了五份的字典收成一份。
另外两处**开工时就是红的**护栏（术语纪律、契约/DTO 漂移）已全部修绿。

## 五、本轮重构记录（分层 / 命名 / 异常 / 去重 / 注释）

原则与前三轮相同：**只做行为不变的重构**，每一处都由三套测试兜底；动不到的地方写明理由。

### 5.1 分层与模块边界：把「调度触发」与「事务边界」拆到两个 bean（本轮主要改动）

上一轮修的是「端口声明了没人实现」，本轮修的是它的近亲：**声明了、也在跑，但在生产少一层保护**。

| 改动 | 为什么 |
| --- | --- |
| 四个批算类拆出 `*Scheduler`：`MonthlyLadderScheduler`（ph-privilege）/ `CouponExpiryScheduler`（ph-privilege）/ `QualificationExpiryScheduler`（ph-provider）/ `AppointmentReminderScheduler`（ph-order） | 这四处的 `@Scheduled` 方法调的是**本类的** `@Transactional` 方法（`run()` / `sweep()` / `remind()`）——**自调用绕过 Spring 的代理**，事务在生产静默失效：批算变成「每条语句各自提交」。而集成测试是**注入 Bean 调那个方法**的（走代理、有事务），所以三套测试全绿也看不出来。最重的后果在月度阶梯：它承诺「重跑只发一次」，而「券已发、发放记录未写」这种半成品状态正是没有事务时最容易留下的 |
| 拆法沿用本仓既有范式，不新造一层 | 仓库里**已有两个同类先例**：`ReminderScheduler`（触发）调 `ReminderGenerator`（逻辑）、`HealthReportScheduler` 调 `HealthReportService`。四个 Job 类只删掉 `@Scheduled` 方法与日志行（日志移到触发器，仍是同一句话），其余一行未动——测试没有改一行 |
| 四个 Job 的类注释各加一段，说明「触发在别处」与原因 | 否则后来者会把 `@Scheduled` 加回去（缺陷的成因就是它看起来很正常）。注释里点名护栏与两个先例 |
| **新增护栏** `architecture/ScheduledTransactionBoundaryTest`（2 个用例） | 这条规矩原先**没有执行者**。判据：`src/main` 里**同一个类不得同时出现 `@Scheduled` 与 `@Transactional`**——静态文本认不出调用图，认「同处一个类」是保守但绝不会漏的近似（自调用不可能跨类发生）。两个反空转前提（扫到 ≥450 个生产源文件、认出 ≥10 个 `@Scheduled`、≥200 个 `@Transactional`）+ 一个「规则真的会响」的用例（临时目录里搭小树：同类两个注解被报出、分居两类放行、**只在注释里提到注解不算**——本仓注释密度高，用「包含字面量」会把注释判成违规） |

口径同步写进 [`docs/conventions.md`](../conventions.md) 的开发纪律（「定时任务与事务分居两个 bean」+ 指认护栏）。

### 5.2 消除重复逻辑：券的来源 / 状态字典五份合一份

| 改动 | 原先 |
| --- | --- |
| 新增 `packages/shared/src/dict/coupon.ts`：`COUPON_STATUS` / `COUPON_SOURCE` / 两组 `*_OPTIONS` / `couponStatusLabel(status, fallback)` / `couponSourceLabel(source, fallback)` | 同一张 1–5 → 中文名的表在**五处**各写一遍：C 端 `utils/coupon.ts`、服务者 `utils/labels.ts`、运营后台三个面板（券实例 / 发放 / 券池总览）各一份 `switch`。代码逐字相同，**差别只在认不出码时回什么**（C 端「未知来源」、两个后台「—」） |

| 分页页脚（`上一页`/`下一页` 在 **29 个文件**、74 处）与 C 端 16 个视图的加载样板 | 都是真重复（约 300 行），但共享的是**交互状态机**而不是业务组件——需要先做一次 ADR-0015 式的边界澄清（哪些算 primitive、`usePagedList` 与后台两个 composable 的边界在哪）。上一轮已列为待办，本轮预算优先给正确性 |

## 六、缺失项的修复建议（按优先级）

> 排序依据是**依赖关系**与**投入产出比**，不是条目编号。第 1 项是本轮新发现的、也是唯一让
> 「安全机制写着三层实际只有一层」的一项。

1. **邀请反作弊三层的生产可用性（最高优先）**。三层判据是真代码，但两层要求码主人的设备 / IP / 号段，
   而创建邀请码的入口传 `null,null,null`（`AppGrowthConsole`），那三列恒为 NULL。
   两个可选修法：**①** 给 `InviteCodeRequest` 加 `device_id`（前端传自己的设备号，与归因侧同源），
   服务端同时补 IP 与号段（`ClientIp` 已有、手机号前 7 位可由 ph-account 的一个只读方法提供）；
   **②** 只补服务端能自己取的两项，但那样仍不构成同 IP + 同号段的合取判据，等于没修。
   **必须先定一件事**：这条规则一开，被判定「同 IP 同号段」的邀请会真的被拒——ADR-0046 的待澄清里
   已有这条取舍，落地前与验收方确认一次。工作量：契约 1 个字段 + 前端 1 处 + 服务端 2 处取值。
2. **券与积分的「开箱可用」**（F017/F018/F019 的公共前置）。三处症状同一个根因：
   `coupon_template`、`point_ladder_tier`、`invite_ladder_tier` 的**奖励与档位零种子**，
   而配置入口只有 API（运营后台没有承载页）。开箱后的现状是：积分只能攒不能花、月度阶梯永远发 0 张、
   邀请阶梯不发券。建议按「先种子、再页面」两步：**①** 用一次迁移补最小可用的种子（至少一张可兑换券模板、
   一组积分档位），这一步能立刻让 F017/F018 从「机制在、产物无」变成可用；**②** 在运营后台的「券池管理」
   下加两个配置面板（券模板已有页面，缺的是阶梯与兑换档位）。
3. **服务者侧的照片墙与报工（F023 的最后一段）**。前置是一个业务输入：服务者令牌能不能用文件直传接口
   （`ph-file` 现在四个方法全部 `requireDomain(APP)`，服务者令牌必 40100）。定了之后就能接
   `saveOrderPhotoSlot` / `reportOrder`（两个 API 方法已写好但没有调用点），顺带把 40901 的前端文案补上。
   **它同时是「订单 → 档案闭环」的前置**——报工不落档案，F004 的「三源并存」就永远只有一种来源。
4. **订单 → 健康档案的同步（F004 / F023 的同一条链路）**。报工成功后调一次 `ArchiveSectionService`
   写一条 `SOURCE_PROVIDER` 的记录，「服务留痕 → 健康档案」这条价值链路才算闭环。建议与第 3 项同一个切片。
5. **C 端知识库浏览页（F024/F025 的界面）**。后端只读出口已可用、有 4 条测试；前端缺的是路由 + 客户端方法
   （`cApp.ts` 里连方法都还没有）+ 一个列表 + 一个详情，复用 C 端已有的四态组件。这是本轮之后
   最小的一块界面欠账。
6. **运营后台的 AI 运营写入面（F006 的限定①）**。七个写入接口后端与契约都有，只差页面。
   ADR-0010 的分层要求「业务可调项入库 + 运营后台」，只落了一半意味着**改红线词要直连 API**。
   同一类欠账还有提醒规则（F007）与照护阈值（F009）——建议一次做一个「规则配置」分段页，三张表共用形态。
7. **任务中心三条空转任务 + 打卡得券（F017）**。要么补生产者（签到 / AI 建议可以；分享在桌面 Web 上没有
   观测点，建议**明确裁决不做**并同步契约的行为分值表），要么从契约里删掉那三行——现在是最坏的状态：
   契约承诺了、页面显示进度、永远不动。
8. **C 端的两个录入入口**：档案补录（F005，缺日期选择器）与就医记录（F004，缺 `medical` 分项入口）。
   两处都是「后端早就能收、前端没有入口」。
9. **经验卡片的录入（F020）**。ADR-0051 的设计是「前端从记录预填」，前端没有这个入口。
   做完它，社区才有内容来源（现在卡片只能由测试造出来）。
10. **轮询兜底（F026 的限定②）**。ADR-0040 把实时通道后置时，保留条款是「必须保留轮询兜底」；
    三端 0 处定时刷新。最小实现是消息中心与邀请进度两个页面各加一个 `setInterval` + 页面隐藏时停表。
11. **券模板不可用口径的剩余两处（40001 vs 40400）**：把 `CouponContributionService.requireTemplate`
    拆成「按请求体引用取」（40001）与「按既有记录取」（保持 40400 或改为内部一致性故障），
    再统一 `CouponContributionService` / `CouponPoolService`，最后改契约描述。口径已写进 `conventions.md`。
12. **其余小项**：F021 的三个模块缺接口（客户维度 / 区间聚合 / 服务者推广码）、F022 的区域保护与
    `ProviderGrowthFactsApi` 接线、前端分页与视图加载样板的收口。各自边界清楚，建议与对应 ADR 一起开票。

**关于支付（F014 的支付部分、F021 的结算中心）**：不在上述任何一项里。
按 ADR-0002 / 0036 等甲方澄清「钱到店付还是线上收」之后单开一票；**本轮未改动任何相关代码**，
服务者后台的「结算中心」在到店付下是对账视图（有流水与核销明细，没有余额与提现），不是缺失。

## 九、本轮发现但**未修**的问题（交下一轮裁决）

1. **邀请反作弊两层在生产是死代码**（第六节第 1 项）——本轮唯一发现的「安全机制写着三层、实际只有一层」
   的问题。修它需要一次带决策的切片（契约加字段 / 加端口 + 「开启即开始拦截」的口径确认）。
2. **`invite_code` 的三个 `owner_*` 列恒为 NULL**——与第 1 项同源，但它还有第二个后果：
   `SAME_DEVICE` 那条规则里「同一台电脑上的一家人会被误伤」的已知代价，**现在连误伤都不会发生**
   （因为判据是空的）。也就是说，ADR-0046 里写的那个取舍在今天的代码里还没真正成立过。
3. **`frontend/` 空目录的创建者仍未定位**——第二轮发现、第二轮删掉、本轮又出现（root 所有，空）。
   它不是仓库的一部分（不入 git），删除安全，但**每轮都要删一次**这件事本身值得查一次（宿主侧工具/脚本）。
4. **契约的行为分值表与实现不一致（F017）**：`contract/app.yaml` 的行为分值表列了「签到 1 / 完善档案 10」，
   而这两个行为码在生产里没有加分成产者。要么补生产者，要么改契约——现在是最坏的状态：契约承诺、页面显示、永远不动。
5. **`ai_consult` 的三列留痕只写不读**（`grading_rule_hits` / `unvetted_hits` / `retrieval_check`）——
   数据在积累，没有接口或界面能取到，只能手写 SQL 看。要么在运营后台加排障详情页，要么在实体注释里
   写明「只供 SQL 排障」，别继续含糊。（上一轮已记，本轮仍在，且随着 §一 D15 的 AI 运营页缺失而更明显。）
6. **`ProviderFacts.findListedService` 没有任何调用方**——它是为「读路径不该整页失败」写的降级版本，
   而接线的两个消费点用的都是 `requireListedService`。要么给它一个消费方，要么删掉。（上一轮已记。）
7. **前端 6 个 API 方法定义无调用点**（`saveOrderPhotoSlot`、`reportOrder`、`getOrder`(服务者侧)、
   `createCard`、`updateArchiveRecord`、`lockCoupon`）。其中四处对应已知功能缺口（报工 / 服务者订单详情 /
   发卡 / 改档案），另两处（`lockCoupon`、`listComplianceDocuments`）建议逐条裁决「缺界面」还是「删方法」。
8. **`provider.region_code` 的区域保护（F022 的另一半）**——口径已定（审核期软约束 + 阈值可配），
   字段无人写入。缺的是业务输入（录入入口）不是代码；要做它至少要定「区域怎么划 / 保护什么 /
   与等级怎么联动」三件事（ADR-0052 待澄清 1）。
9. **两处 ADR 与代码不同步，本轮按惯例没有回填 ADR 正文**：ADR-0052 待澄清 2 写「没有改任何推荐逻辑」
   而代码已按 `provider.level` 排序；ADR-0019 的「天气 / 疫情首期不做」只存在于 ADR 里，
   代码、库与界面都没有任何标记（生产上是**静默的六类**）。建议下次写新 ADR 时以「取代/补充」的形式引用它们，
   而不是改旧文——旧文是当时的记录。
