# 邀请与积分：归因时点、反作弊判据、两套账的边界、月度阶梯骨架

实现 [ADR-0039](0039-invite-review-assessment-analytics.md) 第一节（邀请与归因）与
[ADR-0038](0038-order-redeem-rights-points.md) 第四节（积分与任务）的切片（#111 / #113）。
契约在 `contract/admin.yaml` 的 `/invites/**` 与 `/points/**`，代码在 `ph-privilege`，迁移 V26 / V27。

本文只写实现决策与接线点；对象定义、分值表、阶梯门槛都在那两份 ADR 里，不重复。

## 一、归因时点：注册那一刻，一次，不补填（决定）

- `invite_relation.invitee_user_id` **唯一**：一个被邀请人一辈子只被归因一次。
  重复归因返回 `ALREADY_ATTRIBUTED`（不是报错，是明确的业务结果）；
- 归因命令里带的 `channel` 区分「链接预填（1）」与「手工填（2）」——
  两者都算「用户填了码」（ADR-0039 的口径：以填的为准，链接只做预填）；
- **没有任何接口能补一条邀请关系**（运营后台也没有）：补填是刷券的入口，
  这条口径在接口层就没有出口，而不是靠运营自觉；
- 被反作弊拦下时**注册仍然成功**：不能因为邀请码可疑就不让用户注册。
  拦下的结果是一条可查的反作弊记录（`invite_risk_record`），而不是一条关系。

## 二、有效邀请 = 完成建档 + 24 小时内有行为（决定）

关系因此有「待生效（1）」这个中间态，由**结算批算**（`InviteSettlementJob`，每小时的第 5 分钟）
在观察窗结束后下结论：有效（2）或无效（3）。阶梯计数与积分**都按有效数算**，不按注册数——
否则同一批刷出来的号当晚就能把阶梯奖领走。

**「有行为」的判据是刻意的收口**：该被邀请人在观察窗内**有积分流水**，
且**排除「完成建档」本身**。

- 为什么用积分流水：打卡、签到这些行为本来就会发分（`change = 0` 的也记一条），
  所以积分流水就是一份现成的行为账，不需要再建一张跨模块的行为表；
- 为什么要排除「完成建档」：它是有效邀请的**触发条件**，拿它当活跃证据等于让这条规则
  自动失效（任何人都能点一下建档）；
- 代价：「只看不点」的浏览行为不算数。要不要扩到「浏览了服务目录 / 问过一次 AI」，
  见「待澄清」第 3 条。

## 三、反作弊三层的判据与代价（决定）

| 判据 | 精确条件 | 已知代价 |
| --- | --- | --- |
| `SELF_INVITE` | 被邀请人就是邀请码的主人 | 无 |
| `SAME_DEVICE` | 被邀请人注册设备 == 邀请码**创建时**的设备（两者都非空） | **刻意从严**：同一台电脑上的一家人会被误伤。误伤的用户能找客服，刷出来的券收不回来 |
| `SAME_IP_SEGMENT` | 同一出口 IP **且**手机号前 7 位相同 | 两个条件同时成立才拦：只看 IP 会误伤共用 WiFi 的同事、学校、咖啡店 |
| `NO_ACTIVITY_24H` | 观察窗内没有行为（第二节的判据） | 被邀请人「注册了但一周后才开始用」拿不到奖励——这是 ADR-0039 明确要的从严 |

判据需要的数据：码主人的设备 / IP / 手机号**前 7 位**（存在 `invite_code` 上，生成邀请码时采），
被邀请人的同类信息由注册流程随命令传进来。**不存完整手机号**：完整号属身份信息（ADR-0013 那套
加密与查找列），而「同号段」这个判断只需要前 7 位。

命中的记录进 `invite_risk_record`（可查、可按判据聚合）：运营要能回答
「今天同设备拦了多少」，日志里翻不出来。

## 四、奖励物不重复：两套账，一次行为只发一种奖励（决定）

ADR-0038 第四节点名要钉死的那条，落到实现上是三处：

1. **邀请行为**：有效邀请给邀请人 **20 积分**（`source_ref = invite:{关系 id}`，唯一键兜底，
   重放不会发第二笔）；
2. **阶梯达标**：只在达到门槛**那一次**发奖励（`(user_id, threshold)` 唯一），
   之后新的邀请不再重复发同一档——这正是「同一行为不得重复发奖励」的一种情况；
3. **打卡**：给积分（3 分），**不再发券**；打卡阶梯给权益（ADR-0038 第三节的来源之一），
   那是另一套账的推进，不是把同一个行为的奖励发两遍。

阶梯档位（1/3/5/10/15）的门槛是产品定的，**奖励物可配、且默认未配**：
`reward_type` 为空表示这一档达成时不发东西（达成记录照记）。
「谁在哪一档」是数据，「发什么」是配置——不编一个「满 3 人送 20 元券」，
那是替甲方做产品决策（见「待澄清」第 1 条）。

## 五、积分：整数、带余额的流水、每日上限只作用于占上限的行为（决定）

- **积分是整数**（`INT`），不参与任何金额计算与兑换现金（CONTEXT.md 的积分条目）；
- 流水带 `balance_after`：只记变动数的话，事后无法从流水重建余额，客诉时对不上账。
  余额与流水在同一事务里改；同一用户并发发分靠 `SELECT ... FOR UPDATE` 锁账户行，
  扣分靠 `WHERE balance >= ?` 的**原子条件更新**（先查后扣在并发下会把余额扣成负数）；
  **判据必须在锁内读**（每日次数、每月次数、一次性、日上限都是「读出来的」规则），
  所以 `award` 的第一条 SQL 就是锁账户行，且事务隔离级别取 **READ COMMITTED**——
  理由与券的发放完全相同（MySQL 默认 REPEATABLE READ 的快照会让等锁之后的读仍看旧数据，
  于是并发可以绕过日上限），实测与修法记在 [ADR-0044](0044-coupon-pool-implementation.md) 第三节；
- **每日上限（默认 20，可调）只作用于 `counts_toward_daily_cap = 1` 的行为**：
  邀请（20 分）与完善档案（10 分）不占上限（ADR-0038 第四节），
  否则一次邀请就把当天的上限吃光，之后用户做什么都不再得分；
- 频次三件套都在行为表里：每日次数（签到 / 打卡各 1 次）、每月次数（评价 5 次）、
  一次性（完善档案）。判据是**业务日**（`business_date`，东八区），不是 `created_at`——
  跨零点时两者会差一天；
- 达到上限时**整笔不发**，不做部分发放：积分只涨不部分，「这个行为拿了几分」要能一句话答上来。

## 六、兑换只兑平台补贴券，且与扣分同一个事务（决定）

- 建兑换档位时就校验券模板的 `cost_bearer = 2`（平台补贴），发券前再判一次（防御性）；
  理由见 ADR-0038 第四节：兑换消耗的是平台的钱，不消耗服务者的贡献额度；
- 扣分 + 发券在**一个事务**里：要么都成、要么都不成；
- 兑换的幂等靠调用方的 `Idempotency-Key`（ADR-0028）：一次兑换没有天然的业务引用，
  所以不把 `source_ref` 当成幂等键用（它由「用户 + 档位 + 毫秒」拼成，只用于追溯）。

## 七、任务清单入库存配置，但任务本身不额外发分（决定）

- 任务（每日 / 每周两档）与行为分值都进库 + 运营后台可改（ADR-0010 的三层配置）；
- `point_task` 引用**已有的行为码**，进度按行为流水聚合，任务表里不存进度
  （否则进度有两个来源）；
- 任务上的 `points` 只是把行为的分值取出来展示——**任务完成不额外发分**，
  理由与第四节同一条；
- **行为码不能通过接口新增**：行为要有代码去触发它，加一行数据只会产生一个永远不会发生的动作。
  新增行为是代码变更（本切片只允许改分值、频次、启停）。

## 八、月度阶梯只做骨架，取达成的最高一档（决定）

- 每月 1 日 09:00 算**上月**累计获得积分 → 按档位发券（`MonthlyLadderJob`）；
- **种子里一个档位都没有**：门槛值与奖励没有规则依据，不编。档位为空时批算照跑、
  不发任何券（骨架是通的，日志里能看到「扫了多少人」），运营配好档位即生效；
- **年度大奖不做**，连占位都不留：占位的实现会在某次验收里被当成「已经做了」；
- 一个人只拿**达成的最高一档**的奖励（不是累加多档）。这条 ADR 没写，是本切片的决定，
  理由：阶梯的通常语义就是这样，而且它最好解释（「上月 520 分 → 拿 500 分档」）；
- 幂等：`(user_id, period)` 唯一 + 先查后插，批算重跑与补跑都只发一次。

## 需要协调（接线点，不是待澄清）

这三处都在别人的模块里，本切片**不改**，只把接口与实现留好：

| # | 接线点 | 要做什么 |
| --- | --- | --- |
| 1 | **注册成功后前端单独调一次** `POST /api/v1/app/invites/attribution`（契约 `app.yaml` 已定，见下「实现修正」） | 服务端在**归因时点**补齐来源 IP / 手机号段 / 注册时刻（取 `user.created_at`，**不由客户端说了算**）；`attributed=false` 时注册照常成功（只记一条反作弊记录），重复调用回 `ALREADY_ATTRIBUTED` |

**实现修正（2026-09-30，接线时发现并消解）**：本节原写「在 `AccountService.register` 内调 `attribute(...)`，把邀请码随注册请求传进来」。但冻结后的契约把归因定成**注册后的一次独立调用**，两者不能同时成立——前者要改 `RegisterRequest` 的形状，而那个 DTO 已被既有测试钉住（改它等于改一个已交付接口）。按 [ADR-0047](0047-contract-ownership-and-parallel-work.md)（契约是实现方唯一接口来源），**以契约为准**：归因落在 `InviteAttributionController`，注册接口形状不变。「归因只有一次机会」这条口径不受影响——它在 `invite_relation.invitee_user_id` 唯一约束与接口层「没有补填出口」上，而不是在「谁发起调用」上。

**建档完成**同理落在 `ph-record` 的 `POST /api/v1/app/pets`（`PetService.create`，与建档同一事务）：那才是「完成建档」，改昵称/头像属可选动作；另一处（`ph-account` 的档案完善）不重复调用。
| 2 | ph-record 的建档（`POST /api/v1/app/pets`）或 ph-account 的完善档案（二选一，由产品定） | 调 `InviteAttributionApi.markProfileCompleted(userId)`；返回 false 表示这个人不是被邀请来的，什么都不用做 |
| 3 | ph-record 的打卡、ph-content 的评价、档案完善 | 各自调 `PointsApi.award(new AwardCommand(userId, 行为码, sourceRef, remark))`。**发分失败（返回 `awarded=false`）不该让主流程失败**（打卡要成功，分可以下次再说）；同一行为的 `sourceRef` 必须稳定（如业务日、订单号、邀请关系 id），幂等靠它 |

C 端的邀请与积分接口（我的邀请码 / 我的邀请进度 / 积分中心 / 兑换）**留到下一波**（`app.yaml`），
建议的接口清单写在交付报告里。

## 待澄清（需要甲方拍板）

1. **阶梯奖励物**：1/3/5/10/15 五档各发什么（券模板 / 权益码 / 几张 / 永久还是当月）没有依据，
   现在五档全部留空。空着是**有效状态**：达成记录照记，配上就发；
2. **月度阶梯是取最高一档还是累加多档**：本切片选「取最高一档」。如果甲方要累加
   （跨过 500 分档的人同时拿 100 分档的奖），实现要改 `highestReached` 一处；
3. **「24 小时内有行为」的边界**：现在只认积分流水里的行为（打卡 / 签到 / 评价类），
   浏览、AI 咨询不算。要扩的话先要有跨模块的行为信号（埋点或一张行为表）；
4. **邀请的「永久权益」具体是哪个码**：ADR-0038 第三节只说来源有「邀请（永久）」，
   没说邀请给的是什么能力。当前实现是「配了才发」，配置权在运营；
5. **积分兑换是否限次数**：现在只限余额（够就能兑），不限每人每档位的兑换次数。
   若要做「每人每月最多兑 2 次」，需要一个新的判据与计数（属 #121 的反刷范围）；
6. **`invite_code` 的渠道字段**：生成时记 `channel`，但归因时的渠道才是真正发生的那次
   （`invite_relation.channel`）。码上的那个字段现在只做记录，不确定要不要用于分析。

## Consequences

- 交付文档的「K 因子 &gt; 1」按 ADR-0039 退场，运营总览给的是**有效邀请转化率**
  （有效 ÷ 注册）。这一条要与验收方说明；
- 邀请的 C 端入口（分享链接带 `?invite=CODE` 落地页记 7 天）在下一波；
  本切片只保证「码存在、归因存在、算得对」；
- 积分与权益是两套账：本切片的积分流水与权益授予**没有互相引用**，
  唯一的连接点是「同一行为不重复发奖励」这条纪律（第四节）。
