# 打卡与健康评分：任一项即算打卡、7 天可补录；评分 = 完整度 + 异常扣分

回答地图 [#57](https://github.com/QIUZI-HONG/pet-health/issues/57)，并作为切片 [#97](https://github.com/QIUZI-HONG/pet-health/issues/97) 的依据。两个决定一起裁，因为它们互相牵连：评分要有数据，而数据来自打卡。

## 决定一：打卡在桌面 Web 上放宽完成条件

交付文档 F005 要求「每日 6 项、3 秒完成、连续打卡有阶梯奖励」。但 C 端现在是桌面 Web（[ADR-0001](0001-all-web-clients.md)），**用户不会每天坐到电脑前打卡**——强制六项的结果是大多数人放弃，而连续天数与阶梯奖励等于作废。所以：

| 项 | 决定 |
| --- | --- |
| 当日打卡的判定 | **任一项提交即算当日已打卡**（不必凑齐六项） |
| 重复提交 | 同「宠物 + 日期 + 分项」为**更新**而非新增（幂等）。用户改主意（饮食从「正常」改成「食欲差」）就是改这一条 |
| 补录 | 支持回填**过去 7 天**，记录上标 `backfilled=1`，不冒充当场录入 |
| 桌面交互 | 首页任务卡**行内展开**录入（不弹层），另给「全部正常」「和昨天一样」两个一键操作——六项点完仍在 3 秒量级 |
| 连续天数 | 按「有记录的连续自然日」计算，**补录计入**；断签归零 |
| 阶梯奖励 | 不在本切片（属 F017 / [#113](https://github.com/QIUZI-HONG/pet-health/issues/113)）；连续天数先只做展示 |

（连续天数为什么允许补录计入：7 天窗口本身就限制了回溯深度，用户最多把一周补齐，刷不出长连续。权益侧若日后要更严的反作弊规则，由 #113 单独定。）

## 决定二：五维评分 = 记录完整度 + 异常扣分

`health_score` 表只有分项字段，**算法交付文档没有定义**（09-19 的评估报告已把它列为「无法开发」的缺口）。本项目也没有临床参考数据（品种体重区间、指标阈值都不存在），所以不能假装做医学评估。

**算法**（窗口 = 近 7 天，含今天）：

```
每维 = 70 × 完整度 + 30 × (1 − 0.1 × 异常项数)      （结果四舍五入，最低 0）
  完整度 = 该维覆盖的分项在窗口内「有记录的天数」÷ 7
  异常项数 = 窗口内该维分项里 abnormal=1 的记录条数（每项扣 10，扣到 0 为止）
总分 = 已计入维度的等权平均
```

| 维度 | 数据来源（`archive_record.category`） | 计入条件 |
| --- | --- | --- |
| 生理 | 1 体重、2 饮食、3 排泄 | 恒计入 |
| 行为 | 4 行为、5 情绪 | 恒计入（**情绪没有独立维度，并入行为**——交付文档的打卡有六项、评分只有五维，这是两者差额的落点） |
| 卫生 | 6 卫生 | 恒计入 |
| 防疫 | 7 防疫（疫苗 / 驱虫） | **有疫苗或驱虫记录时才计入**，否则显示「待录入」——录入入口属 [#102](https://github.com/QIUZI-HONG/pet-health/issues/102) |
| 老年 | 同「生理」的来源 | **仅当专项开启时计入**（年龄 ≥ 7 岁或标记慢病，见 F009 / [#116](https://github.com/QIUZI-HONG/pet-health/issues/116)）；未开启显示「— 未开启」 |

算例（也写进了给用户的选项说明，实现要与它一致）：

```
近 7 天：有记录 4 天，其中「排泄异常」1 次
生理 = 70×(4/7) + 30×(1 − 0.1×1) = 40 + 27 = 67
行为 = 70×(2/7) + 30×1.0         = 20 + 30 = 50
卫生 = 70×(5/7) + 30×1.0         = 50 + 30 = 80
防疫 = 无疫苗/驱虫记录 → 待录入，不计入
老年 = 未开启 → 不计入
总分 = (67+50+80)/3 = 66
```

## Considered Options

- **严格每日六项**（照文档字面）：与 F017 口径完全一致，但桌面场景下多数人断签，等于废掉这条留存机制。
- **改成周维度打卡**：最贴近桌面实际频率，但用户故事 8（连续天数）与 F017（打卡得券阶梯）都要跟着改，连带 #112 权益与 #113 积分，与交付文档差异最大。
- **只按记录完整度评分**：用户一眼懂，但**逻辑上错**——异常事件（吐了、不吃）反而因为「记录了」而涨分。
- **以异常信号为主的扣分制**：最像健康评估，但阈值没有临床依据，风险最大（给用户一个看起来像医学结论的数字）。

## Consequences

**评分是「被观察到的健康」，不是医学评估。** 这个口径必须落到文案上：分数档位只用中性措辞（良好 / 尚可 / 需关注），页面上要给出「为什么是这个分」（哪几维被记录完整度拉低了）。**分数不得盖过风险等级**：将来 AI 咨询（[#98](https://github.com/QIUZI-HONG/pet-health/issues/98)）落地后，若近期有红色风险记录，评分卡只展示趋势、不展示「良好」——医疗场景宁严勿松（docs/conventions.md）。

**完整度进算法意味着「不记录就掉分」。** 这是刻意的：它把「持续观察」本身当成健康行为。代价是用户可能觉得被惩罚，所以首页必须能一眼看出「这几维是因为没记录才低」，而不是让人以为宠物病了。

**评分在写入时实时重算当日行**（`health_score` 按 `pet_id + calc_date` 唯一）。理由：F005 要求打卡「有反馈」，等定时任务批算就看不到即时变化。历史行保留，供趋势与周报（[#115](https://github.com/QIUZI-HONG/pet-health/issues/115)）使用。

**对交付文档 DDL 的两处偏离**（都是实现所必需，不是随手改）：
1. `archive_record` 增 `record_date DATE`——文档靠 `created_at` 判定日期，而**补录必须有独立的业务日期**；
2. 增 `abnormal TINYINT`——评分要按窗口聚合异常次数，用列比每次解析 JSON 干净。
   另按 [ADR-0011](0011-persistence-and-migrations.md) 统一补审计列。
