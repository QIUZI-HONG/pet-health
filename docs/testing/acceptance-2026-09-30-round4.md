## 四、偏离清单的变化

本轮**没有新增对交付文档的偏离**，但有两处需要向验收方说明的**新决策**：

| 决策 | 依据与代价 |
| --- | --- |
| 服务者域的文件直传**只开 presign**，且把 `biz_type` 收窄成只有 `care` | 读走订单里的签名地址、替换走槽位整体替换——少一个入口就少一处要守的归属判定。代价：误传的照片成为文件域孤儿行，门店自己删不掉（`GET/DELETE /files` 未开） |
| 报工回流档案落在 **`category=10`（其他指标）** | 打卡六项有唯一键（与用户当天打卡撞键会把报工变成 50000）；防疫/证件是「被机构核验的事实」、就医是用户自述、老年专项常态不可见。落 10 不伪造事实、也不进评分维度。代价：它会出现在用户「核心指标」分项里、该分项条数 +1；要更干净需要在 ADR-0030 的映射里补一个「服务记录」分项（见 ⑥-6） |

## 六、剩余项的修复建议（按优先级）

1. **首批配置的数值要运营确认一次**（已入库，见 ⑩-2）。交付文档写了的那部分照它取了
   （20 元洗护券、1/3/5/10/15 档、绑 `GROOMING` 分类），**没写的那部分是我取的暂定值**
   （30 分兑 10 元券、60 分兑 20 元洗护券、月度 100/300 分两档、被邀请人 20 分）。
   这些数字直接决定平台的补贴成本，**请在运营后台核一遍**（「积分与邀请配置」页可改，改完立即生效）。
   另有一处**代码级差异**：交付文档 BPM-2 说被邀请人「同样得 20 元券」，
   而发券给被邀请人这条路径不存在（被邀请人侧只有积分机制）——要做得新增代码，不是改配置。
2. ~~同设备那一层反作弊~~ **已完成**（见 ⑩-1）：`InviteCodeRequest` 加了 `device_id`，前端上报本机标识，
   服务端落 `invite_code.owner_device_id`，并有一条走生产路径的用例钉住「换账号、同一台设备 → 拦下」。

## 九、本轮我自己拍的三个判断（都可以推翻，但要知道推的是哪一条）

1. **IP + 号段那一层只在「地址能区分来源」时才判**（`InviteRiskGuard.carriesSourceIdentity`）。
   回环、私网、链路本地、CGNAT 这些地址段是**由构造决定共享**的：拿它们比「是不是同一个出口」，
   结论不成立；一旦拿它当判据，规则实际退化成「同号段就拦」，比 ADR-0046 想要的严得多。
   更要紧的是**部署形态**：正式环境前面有反向代理，而 `ClientIp` 刻意只读连接地址、不读可转发的头
   （ADR-0028，可信代理白名单留到 #66）——那时代理之后所有请求都是同一个地址，这一层会恒真。
   **等 #66 落地、能取到真实客户端 IP 之后，这条豁免应收窄到只剩回环地址。**这条与 ADR-0046 的
   原文有细微差别（它没说地址段的事），所以记在这里而不是偷偷改 ADR。
2. ~~同设备那一层保持关闭~~ → **当轮收尾时已实现**（见 ⑩-1），判断随之作废；
   留下的取舍是：设备号是**客户端声明**的（桌面 Web 没有更硬的来源），所以它拦的是
   「懒得换设备的刷量」，不是「换设备也拦得住」。这条限度写在 `InviteCodeRequest` 的注释里，
   不假装它比实际更强。
3. **券模板不可用的口径：契约的文字优先于 conventions 的三行规则**。
   第三轮报告把「`CouponContributionService` / `CouponPoolService` 的 40400 → 40001」列为待办，
   本轮逐处核对后结论是**不该改**：`CouponPoolService` 的两处读的是**路径资源**（40400 正确），
   `CouponContributionService` 的请求体那一支在契约里明文写着 40400 并给了理由（「平台补贴券不能贡献，
   对服务者来说它等于不存在」）。所以我改的是 `docs/conventions.md`（补一条可见性例外），
   而不是改代码或契约——**两份文档不一致时，接口层以契约为准**，这一条本身也值得写进 conventions。

## 十一、同日第三轮：把「点了会发现不对」的四件事收掉

上一轮结束后列的「点了会发现不对」清单有四条（第 5 条是业务数值，不动），本轮按**第一版**的标准逐条处理。

### ⑪-1 评价晒单（此前完全没有落地）

**症状**：用户完成订单后没有评价入口；`provider.rating` 在契约里被标注为「**恒为 5.0**」；行为分值表里
写着「评价晒单 5 分」却永远发不出——那是「点了会发现不对」里最重的一条。

| 落点 | 说明 |
| --- | --- |
| 契约 | `POST /orders/{order_id}/review`（评分 1–5 必填 + 文字 ≤500 可选）、`GET /providers/{provider_id}/reviews`（分页）；`OrderView` 增加可空的 `review`——**没有它，用户刷新后还会看到评价入口**，点下去只拿 40900 |
| 迁移 | `V40__order_review.sql` + `U40`：`order_review` 表，`order_id` 唯一（**一单一评**）、`(provider_id, created_at)` 索引（唯一的列表读法） |
| 后端 | 表归 **ph-order**（评价属于订单）：未完成订单 → 40900 并点名状态；别人的订单 → 40400（与越权同码）；评分越界 → 40001；一单只能评一次。**门店评分**走新端口 `ProviderRatingApi`（`ph-api` 声明、`ph-provider` 实现 + `@Primary`，参数用基本类型所以不需要契约条目）——算在 ph-order（它拥有评价表）、写在 ph-provider（它拥有 `provider.rating`），ADR-0006 两侧都不破 |
| 发分 | `REVIEW` 行为分走**领域事件 AFTER_COMMIT**（不在评价事务里直接调）：同事务发分一旦抛异常会把事务标成 rollback-only，**评价本身也被回滚**——`CheckInPointsListener` 的注释里写着这处两难 |
| C 端 | 订单详情：只有「已完成」才出现评价入口，提交后原地显示；门店详情：评分 + 条数 + 评价列表（含空态）。类型全部来自生成物 |
| 测试 | `OrderReviewTest`（6 例，走 HTTP 缝）：未完成三态各 40900、别人的单 40400 且不落库、一单一评（第二次 40900 + 行数仍 1 + 流水仍 1）、0/6/缺失/超长 → 40001、**评分真的从 3.00 变成 4.00**（并断言 C 端详情读到的字符串）、列表分页与越界。前端 `order-review.spec.ts` 12 例 |
| **变异验证**（证明断言不是摆设） | 去掉「只有已完成才显示入口」→ 对应用例红；注掉评分回写 → `providerRatingFollowsReviews` 红在 `expected: 3.0` |

**顺带修掉一个真实缺陷**：`Provider` 的 `intro / businessHours / lng / lat` 带 `@TableField(updateStrategy = ALWAYS)`（为让「清空」能落库）。
最初用「只 set 了 rating 的实体 + `updateById`」回写评分，**把该门店的营业时间一起写成了 NULL**——集成测试逮到（下一个用例下单直接「当天不营业」），
改成手写单列 UPDATE。这类陷阱的成因是「更新策略是列级的」，别处都是先读整实体再更新，所以没有第二处中招。

**一处被迫的偏离**：评价列表**需要登录**（契约里写明了）。C 端免登录只读路由表在 `JwtAuthenticationFilter`，
不在本切片边界内，所以按「内容面游客只给浏览服务」的口径处理；要放开给游客，只需在那张表里加一条正则并把契约改回 `security: []`。

### ⑪-2 任务中心：一条接上、一条撤掉

- **AI 建议（`DAILY_AI_ADVICE`）接上了生产者**：`ph-ai` 在咨询成功后记一次 `AI_ADVICE` 行为（0 分，只驱动任务进度）。
  依赖方向沿用 `ph-record` 的既有先例（直接依赖 ph-privilege 的 `api` 包，边界护栏放行 `api` 层）。
  **记行为失败绝不影响咨询主流程**（catch + WARN）。两个口径写在 `AiAdviceRecorder` 的注释里：
  **降级不记**（那一轮没走通 AI 判断，记它等于把没产出的咨询算成完成）、**红线短路记**（它给的是平台的急症建议，
  排除它会让「问急症的人任务永远不前进」）。
- **分享（`DAILY_SHARE`）明确撤掉**：桌面 Web 上没有可靠的服务端可观测事件（用户复制链接无法在服务端确证），

  **留一条永远 0/1 的任务比撤掉它更糟**：那是在向用户承诺一件平台不打算兑现的事。
  顺带把**行为分值表**也按 `status` 过滤（停用的行为还列着「0 分 · 每日 1 次」只会误导）。

| 迁移 | `V41` + `U41`：新表 `check_in_reward_rule`（`streak_days` 唯一 + `status` + 审计列），种子 **连续 7 天 → 1 张 `CP-101`**（20 元洗护券，`V39` 建的） |
| 触发 | `CheckInRewardListener`（`@TransactionalEventListener(AFTER_COMMIT)`）**复用** `CheckInService` 已经算出来的连续天数，**没有另写一套**；发券走 ph-privilege 的 `CouponApi`，来源码 `SOURCE_CHECK_IN_TASK`（**本轮之后它不再是死码**） |
| 幂等 | 引用 = `checkin-reward:{userId}:{档位}:{这一轮连续的起始日}`。**起始日才是「这一次达成」的身份**：同一轮连续的第 7/8 天、跨天重试、并发都算同一个引用 → 只发一张；用提交日会让第 8 天变成另一条引用 → 多发一张 |
| 判定用 `>=` 而不是 `==` | 某天的事件丢掉（瞬时故障、重启）不会再漏发；重复发放由上面那条引用兜住 |
| 测试 | `CheckInRewardTest`（2 例，走生产打卡接口造数据）；**变异验证**：把引用改成提交日 → 两条都红 |

**一处已知弱点（下一版要收）**：因为「一轮连续只发一张」，用户**每天撤销最早那天 + 当天再打一项**，
就能把连续段整体后移一天，从而每轮各拿一张券（需要刻意 undo/redo，且每天仍受每日上限约束）。
根治要给「达成」落一张台账表（像 `point_ladder_grant` 那样的 `(user, 档位, 一轮)` 唯一行）——
本轮按「第一版」的最小面故意没建。**这一版的配置也只有种子、没有运营页面**，改法写在迁移注释里。

### ⑪-4 运营后台「进不去」
