# 契约先行与单一写入者：并行开发的协作规则

**一份契约文件在同一时刻只有一个写入者，且写入者是协调者，不是各路的实现者。**

流程固定为四步：① 开工前由写入者把该域契约**写完**（不是边写边实现）→ ② 跑 `pnpm gen:api` 生成前端类型 → ③ 派实现，实现方**只读契约**（后端 DTO 手写但与契约字段对齐，这是 AGENTS.md 原本的分工）→ ④ 实现方发现契约与实际不符时**停下来报告**，由写入者改契约、重生成、广播给所有在飞的路。

配套加一条**自动校验**：拿 Java DTO 的 record 组件名与必填性，对比契约 schema 的 `properties` / `required`，不一致即红。理由是它替代的正是「靠人盯字段名」——并行开发下没人盯得住四十个接口。

推进顺序定为**交易优先**：订单 → 核销 → 照片墙 → 券的 C 端 → 社区 → 考核与看板。依据是依赖长度：照片墙、评价、券核销、考核全挂在订单主干上，主干通了之后每个功能都能立刻在它上面验证。

## Considered Options

**一次性全量冻结**（把四个域的剩余接口一次写完再全面开工）

- 并行度最高，且接口的一致性可以在一次评审里看完。
- 但契约定形时**没有任何实现验证过它**。四十个接口里出现三五个形状不对是常态（本项目的契约也在实现过程中改过：状态码语义、幂等口径、字段命名都动过），而每改一次都要重新生成、通知所有在飞的实现——**那正是要避免的串行，只是换了个触发点**。

**维持现状**（每个实现方持有自己域的契约文件，写实现的同时写契约）

- 设计与实现贴得最近，反馈最快。
- 实测的代价：`app.yaml` 卡过三路（档案线持有期间，交易 / 增长 / 社区全都开不了工），`provider.yaml` 与 `admin.yaml` 卡过两路。文件所有权成了并行度的天花板——这不是理论风险，是这轮开发的实际瓶颈。

**按域先写后派 + 单一写入者**（选它）

- 每个域的设计在实现前就定稿（可被评审），又不必在没有反馈的情况下冻结全部四十个接口。
- 域内可以多路并行（同一域的实现方共享同一份**只读**契约）。
- 写契约是**设计工作**，本来就不该并发——把它收给一个人，冲突在物理上消失。

## Consequences

- **协调者成为契约路径上的单点**。这是刻意接受的：契约写入需要全局一致性（同一个概念在两个域里不能有不同形状），而单点是达成一致最便宜的方式。代价是每波开工前有一段「只有一人在写」的时间。
- **每次契约变更有一个广播延迟**（实现方报告 → 写入者改 → 重生成 → 通知）。比「两个 agent 同时改、其中一个的改动静默丢失」便宜得多。
- **DTO 自动校验会先红**：现有 DTO 与契约之间可能已经存在差异（`ContractJsonTest` 只覆盖了信封与部分字段集合）。要按域分批修到绿，**不要**为了让校验通过而放宽校验本身。
- 已有的事实先例被这条规则追认：`provider.yaml` / `admin.yaml` 的路径参数统一 snake_case、`*Input` → `*Request` 的改名，都是「一个写入者改、其余只读」才做得干净的改动。
