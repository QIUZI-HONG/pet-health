# 提醒体系：只做站内，五类提醒，红色不可关闭

回答地图 [#56](https://github.com/QIUZI-HONG/pet-health/issues/56)，并作为切片 [#99](https://github.com/QIUZI-HONG/pet-health/issues/99) 的依据。

交付文档 F007 定义了 8 类主动提醒、靠「定时任务 + 推送」送达。但 [ADR-0001](0001-all-web-clients.md) 取消了微信订阅消息，本轮又确定只做站内消息中心——**没有任何外部触达通道**。这一票要回答的其实是：一个「必须登录才能看到」的提醒体系还剩多少价值。

## 决定

### 一、通道：站内为唯一保证送达的通道，「主动」的口径要改

**「主动」= 系统主动生成（不等你问），不是主动送达。** 用户回到站内时，该关注的已经排在那儿了：首页强提醒流 + 未读角标 + WebSocket 推给正开着的页面（[#85](https://github.com/QIUZI-HONG/pet-health/issues/85) 已定）。

**浏览器通知（Web Notifications / Web Push）列为二期增强**，二期才做、且只做「尽力而为」：它不需要任何第三方资质，是唯一能低成本往外迈半步的通道，但要 Service Worker + VAPID，且用户不打开浏览器仍有收不到的情况。数据模型里**预留通道位**（`message.channel_state`），二期加 `browser` / `email` 时只扩这一列。

短信与邮件不做：短信要钱、要模板报备，而且本项目至今没有短信通道（[#81](https://github.com/QIUZI-HONG/pet-health/issues/81) 的验证码登录同理）；邮件要新增邮箱字段，国内宠物主开邮件的比例很低。**为通道掏钱之前，先把生成规则验证明白。**

**代价写清楚**：产品文案不得再说「24 小时监护、实时预警」这类承诺——用户不登录就收不到。界面与文档统一说「你一登录就能看到该关注的」。

### 二、类型：首期五类，天气与疫情砍掉，疫苗/驱虫先补最小录入

| 类型 | 数据源 | 首期 | 说明 |
| --- | --- | --- | --- |
| 异常 | 打卡里用户标注的异常 | ✅ | 写入时**即时**生成（刚标异常就能看到反馈） |
| 趋势 | 打卡的体重记录 | ✅ | 近 7 天体重变化 ≥ 5% 触发 |
| 日常 | 打卡状态 | ✅ | 当天未打卡时提醒（每天最多一条） |
| 疫苗 / 驱虫 | **新增的最小防疫日期录入** | ✅ | 到期前 7 天开始提醒（阈值入库可调） |
| 慢病 / 老年 | 宠物表的生日 + 慢病标记 | ✅ | 每季度一条（如「已进入老年期，建议半年一次体检」） |
| 天气 / 疫情 | 无（外部数据源） | ❌ | 没有数据源就没有可测的行为，硬接一个公开 API 只是多一个不可控依赖 |

**为什么先补最小防疫录入**：疫苗到期提醒是这套体系里用户最认、最不容易被当成骚扰的一类（有时间点、有行动、不制造焦虑），而它只需要两个日期字段。推迟到 [#102](https://github.com/QIUZI-HONG/pet-health/issues/102)（档案分项）会让 #99「做完了却没什么可提醒」。顺带它让健康评分的**防疫维度**从「待录入」变成可计分（[#97](https://github.com/QIUZI-HONG/pet-health/issues/97) 留下的口子）。

### 三、时点：批算 + 即时混合，阈值必须入库

- **到期/周期类**（疫苗、驱虫、日常、慢病/老年、趋势）：每天 08:00（Asia/Shanghai）批算一次；
- **异常类**：打卡写入时即时生成。

批算让「提醒什么时候来」可预测、可解释、便于去重与测试；异常即时是因为它天然有反馈价值。**定时任务用 Spring `@Scheduled`**——[ADR-0003](0003-lean-middleware.md) 已去掉 XXL-JOB，单进程部署下够用。

**阈值与开关一律入库**（`reminder_rule` 表），不写死在代码里。这是 [ADR-0010](0010-ai-config-layering.md) 对「业务可调项」的要求，也是 [#64](https://github.com/QIUZI-HONG/pet-health/issues/64) 点名的缺口（交付文档把提醒阈值写死在了测试用例里）。运营后台的编辑界面属 [#118](https://github.com/QIUZI-HONG/pet-health/issues/118)，本期只落表与默认值。

**另加一条：读消息中心/首页时惰性补算一次**（与批算共用同一个幂等生成函数）。理由：只做站内时，「批算」与「用户看到时才算」对用户不可区分，但惰性补算能保证用户打开时看到的一定是最新的，成本是零；二期加了外部通道之后，批算才是送达的载体。

### 四、消息中心一张表装两类内容

术语表原本只有「提醒」，交易类消息（订单状态、券到期、邀请进度）没有位置。定为：

- **消息 Message**：站内消息中心里的一条内容，分两类来源——`kind=reminder`（健康提醒，系统主动生成）与 `kind=notification`（业务通知，事件驱动）。
- 未读/已读/未读角标是**跨类的统一行为**，一张表一处实现。两张表会让「未读角标」「全部已读」变成两份实现，而 [#85](https://github.com/QIUZI-HONG/pet-health/issues/85) 已经预告了多端已读会错乱（文档的 `reminder` 表只有 `is_read` 一个字段）。

**这是对交付文档 7.2 DDL 的偏离**：文档只有一张 `reminder` 表。本 ADR 保留它的字段（`type` / `remind_at` / `risk_level`），另加 `kind`、`dedup_key`、`channel_state`、`read_at`，并把表命名为 `message`。

### 五、防骚扰：红色不可关，每天最多三条，同日同类更新而非新增

| 规则 | 定值 |
| --- | --- |
| 开关 | **红色等级的健康提醒不可关闭**；其余按类型可关（默认全开） |
| 每日上限 | 每宠物每天最多 **3 条**（阈值入库，运营可调）；超出按紧迫度保留前几条 |
| 去重 | 幂等键 = 宠物 + 类型 + 窗口（日期 / 到期日 / 周期）；同键**更新内容**而不是新增——疫苗从「还有 7 天」到「还有 6 天」是同一条在变 |
| 日常类的累积 | 生成今天这条时，**撤销该宠物未读的旧日常提醒**（已读的留作历史）——不活跃用户回来后不该看到三十条「今天还没有记录」 |
| 上限的口径 | 按「**今天新生成了几条**」算（`created_at`），不是按业务日期——补录会把业务日期填到过去，按业务日期算的话补 5 天就能堆出 5 条 |
| 已取消 | 用户可删除单条（软删除），不等于关闭该类型 |

依据是交付文档 13.1 的决策优先级「**用户安全 > 商业目标 > 体验 > 性能**」：红色风险属于安全，不能被关掉；其余属于体验，用户说了算。#99 的验收标准里已有「同类型同宠物不重复」，这里把数值与截断策略补实。

> **与初稿的一处更正**：初稿写「超出的合并为一条『今天还有 N 条提醒』」。实现时改成**按紧迫度保留前几条、其余不生成**——消息中心本身按时间列出全部，再加一条汇总条只会多一条还要点开的噪音。这条改动是评审时发现的，记在这里免得后人以为漏做了。

## Consequences

**提醒不再是「触达」，而是「待办队列」。** 界面上要让用户一眼看到「有几条没看」，而不是期待他收到推送。首页强提醒流的 6 个位置按 `risk_level` 与 `remind_at` 排序取前 6 条（交付文档 4.16.2 画的就是 6 张卡）。

**预约提醒推迟到 [#109](https://github.com/QIUZI-HONG/pet-health/issues/109) 之后**：它依赖订单，而订单还没实现。#99 的验收标准里原本写着「预约提醒」，本期改为前五类；这条已在该票上注明。

**「实时」的边界**：提醒的实时性只体现在「正打开着页面时通过 WebSocket 收到」，不打开就没有。这条与 [#85](https://github.com/QIUZI-HONG/pet-health/issues/85) 的分工是：本 ADR 定生成与呈现，#85 定通道协议。

**「红色不可关闭」在开关这一层的落地是按类型**：开关是类型粒度的，而一个类型里可能既有黄也有红。承载红色风险的是**异常类**（AI 咨询给出红色分级后写进这一类，见 [#98](https://github.com/QIUZI-HONG/pet-health/issues/98)），所以它 `closable=false`、用户关不掉，其余类型可关。这条在代码里是真的（`MessageService.isClosable`），前端把不可关闭的开关置灰并写明原因。

**批算与惰性补算的关系（实现说明）**：每日 08:00 用 Spring `@Scheduled` 批算一遍（遍历有宠物的用户）；用户读消息列表或首页强提醒流时再惰性补算一次，两者共用同一个幂等生成函数。**未读数接口不补算**——角标每次切页都会拉，不该让它写库。代价是：批算没跑（或服务停机）时，用户仍能在打开页面时看到提醒，但角标要等列表/首页加载后才更新。

**将来要接外部通道时**，需要回到这里改：新增 `channel_state` 取值 + 一个送达器 + 一条「送达失败不影响主流程」的规则（交付文档 2.4 已有此约定）。
