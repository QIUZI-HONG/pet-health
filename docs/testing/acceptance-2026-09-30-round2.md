## 一、结论摘要

**交付文档的 27 项功能：完整完成 13 项、部分完成 14 项、缺失 0 项**，另有 2 个附项已裁决不做。

- **完成（13）**：F001 F003 F005 F006 F009 F010 F011 F012 F013 F016 F017 F019 F020
- **部分完成（14）**：F002 F004 F007 F008 F014 F015 F018 F021 F022 F023 F024 F025 F026 F027
- **缺失（0）**
- **已裁决不做**：微信登录与短信验证码（ADR-0027）、视频理解输入（ADR-0004）
- **支付链**：💳 待甲方澄清（ADR-0002 / 0036：钱在门店付，平台不经手资金）

与上一轮（完整 18 / 部分 9）相比**完成数下降 5 项**——这不是功能退步，而是上一轮的清单把
「有一套能跑的测试」当成了「这条需求已经成立」。本轮的每一项改动都是**状态判定与证据的对齐**：

**两处是真缺口，其余是措辞：**

1. **🔴 跨模块端口在生产没有实现（本轮已修）**。`ProviderServiceQueryApi` / `UserQueryApi` /
   `PetFactsApi` / `CouponFactsApi` 四个接口在 `ph-api` 里声明、消费方用 `ObjectProvider` 就地取实现，
   而**生产代码里没有任何实现**——集成测试注入了等价桩（`OrderTestSupport.StubCrossModuleApis`），
   所以 394 个用例全绿，线上却：下单与号源查询报 **50300**、按手机号核销报 50300、
   订单详情的预约人与券卡片恒为空。上一轮 F014 写的是「创建（锁券 + 占用号源）……全部实现并测试」，
   读起来像能用。**本轮把四个适配器补齐**（落在拥有该表的 service 上，与仓库既有范式一致），
   并加了一道 `PortWiringTest` 让这类缺口不能再悄悄出现。
2. **🔴 两个后台没有登录入口**。服务者后台 11 个模块与运营后台 9 个模块**页面都实现了**，
   但 `provider.yaml` / `admin.yaml` 里没有 auth 路径、两端没有登录页，生产代码只签发 APP 域令牌
   （PROVIDER / ADMIN 域仅测试代码签发）。所以这 20 个页面在真实使用中都停在「尚未登录」闸门。
   这是 ADR-0035「需要协调」第 3 条明确记着的欠账，前端也刻意不摆一个「能点但登不进去」的表单
   ——**但上一轮的 F021 给了 ✅ 而没提这件事**，读报告的人会以为后台可用。

**其余 7 处是措辞与事实不符**（逐条见第二节的注）：F004 的「三源并存」（生产只有用户源）、
F004 的「就医记录可录入」（只有 API 层，C 端无入口）、F014 的「订单页是占位」（早已实现）、
F014 的「六态」（实现是五态）、F015 的「自动匹配最优惠券」（无实现）、
F020 的「页面上如实说明」（页面没写）、F026 的「邀请事件会写消息」（邀请侧无生产者）。
另有一处口误：上一轮写「术语纪律零违规」，按 `docs/conventions.md` 自己给的那条 grep 命令跑，
**实测有 1 处漏标**（已修，并把这条人工命令变成了 CI 断言）。

**工程质量仍在同阶段项目的上游**，且本轮把三处「只有约定、没有执行者」的规矩变成了断言：
模块边界（上一轮）、端口接线与术语纪律（本轮）。三份契约类型生成物与契约一致（`gen:api:check` 通过）。

## 五、本轮重构记录（分层 / 命名 / 异常 / 去重 / 注释）

原则不变：**只做行为不变的重构**，每一处都由三套测试兜底；动不到的地方写明理由。

### 5.1 分层与模块边界：把「声明了却没有实现」的端口补齐

这是本轮最重要的一处，因为它不是审美问题而是**生产可用性**问题（第一节已说明影响）：

| 改动 | 为什么 |
| --- | --- |
| 四个跨模块端口的实现落地：`ProviderServiceQueryApi` → `ServiceListingService`（ph-provider）、`UserQueryApi` → `AccountService`（ph-account）、`PetFactsApi` → `PetService`（ph-record）、`CouponFactsApi` → `CouponService`（ph-privilege） | 接口在 `ph-api` 声明、**实现只能由表的拥有者写**（ADR-0006）。四个都是**转交**，没有新查询逻辑：服务项走本模块已有的列表查询与 `ProviderViews.toServiceView`，营业时间走 `BusinessHours.decode`（与门店资料页同一个解码口），用户资料走 `toProfile`（与 C 端自己的资料**同一份映射**），券视图走 `PrivilegeViews.toCouponView`（与「我的券」同一份装配）。**没有各自新写一套**，这正是要避免的分叉源 |
| 落到**拥有方的 service** 上，而不是新建四个 Adapter 类 | 仓库既有范式是「拥有该数据的 service 直接 implements 端口」（17 个实现里 16 个如此，唯一的 `ProviderAccessAdapter` 是因为它包的是包级私有的 `ProviderAccess`）。沿用范式而不是新造一层 |
| 四个类补 `@Primary` | 集成测试里有等价桩（`OrderTestSupport.StubCrossModuleApis`）且消费方用 `ObjectProvider` 就地取实现——两个候选且无主会抛 `NoUniqueBeanDefinitionException`，把「有实现」变成 500，正好抵消接线的意义。`ProviderAccessAdapter` 的注释里已经把这个坑写清楚了，本轮照抄同一个取舍（第一遍跑出 22 个失败正是踩了它） |
| **新增护栏** `boot/architecture/PortWiring` + `PortWiringTest`（3 个用例） | 这条规矩原先**没有执行者**：接口声明了、实现没人写，测试注入桩所以 CI 全绿。检查器把它变成断言——`*Api` 接口必须有 `src/main` 里的实现，**测试桩不算**（事故能瞒过 394 个用例正是因为桩在 `src/test`）。两个反空转前提（扫到的文件数 ≥400、端口数 ≥20）加两个「规则真的会响」的用例（临时目录里搭小树：只有测试实现的端口被报出、多实现与换行的 `implements` 都认出来） |

**`PortWiringTest` 的基线是一条有据可查的例外，不是零**：`ProviderGrowthFactsApi`（考核的拉新与券）
**刻意不实现**——ADR-0052 的「需要协调」写着，拉新那一半要先把「服务者的拉新入口」落下来
（交付文档 F022 的店内二维码把用户绑到门店），而现在的邀请关系只有用户对用户，**这条口径本身未定**；
实现它的四个方法只能靠编。未接线期间考核按「不参与、重算权重、明细注明」处理（ADR-0050 §四），
是**被声明的降级**。所以测试里那条例外必须写明 ADR 依据——让「故意留白」与「忘了接线」在代码里长得不一样。

### 5.2 统一异常与日志口径

| 改动 | 原先 |
| --- | --- |
| `SlotGrid.of(BusinessHour)` 补 WARN 日志 | 那里原先写着「脏数据不该让整天的号源列表变成 50000……**但必须留痕**」，而**这个类没有 logger**——注释要求的事做不到。门店的营业时间列写坏后，表现是「整天不可预约」而运维侧零信号。日志措辞与 `BusinessHours.decode`（写入口那一侧的同类脏数据）对齐 |
| `AiServiceClient` 的两个降级分支补 WARN | `matchSymptoms` 与 `browseKnowledge` 都静默 `catch (RestClientException) → unavailable()`，整个类没有 logger。不抛是对的（对用户就是「暂时看不出来」），**但不记就是吞异常**：AI 服务整体不可用时这两条链路在日志与指标里完全无声，而界面只显示「暂时认不出」。类注释同时补上「三条链路对失败的处理是两种，但两种都必须留痕」 |
| 券模板不可用的错误码拆分：`PointsAdminService.requireSubsidyTemplate` 的「不存在或已停用」从 **40900 → 40001**，契约同步改 | 「冲突」的前提是两边都存在——一个连可用模板都指不到的 id 不是冲突状态。同一失败原先在三处给了三个码（40001 / 40400 / 40900），**本轮只改了无争议的那一支**：`CouponContributionService.requireTemplate` 同时服务「请求体引用」与「既有记录的内部读」两种语义，一刀切会改错（见第六节第 8 项） |
| `ErrorCode` 的 40901 注释纠偏 | 注释写「契约侧待补一行」，而 `contract/common.yaml` 里**已经有** 40901。这类「注释与实现相反」正是上一轮修过 3 处的那一类：危害是让后来者绕开正确路径 |
| **新增文档口径** `docs/conventions.md` 的「引用了一个不可用的资源时用哪个码」 | 三处分叉的根因是**约定文档里没有这一条**。补上三种位置的三条规则（请求体引用 → 40001、路径资源 → 40400、存在但用途不符 → 40900），并写明它统一到什么程度 |

### 5.3 消除重复逻辑

| 改动 | 原先 |
| --- | --- |
| `ph-provider`：`Coordinate` 值对象（`longitude` / `latitude`）收口两处**逐字相同**的经纬度解析与区间校验 | 同一段代码在入驻（`OnboardingService`）与门店信息维护（`ProviderProfileService`）里各一份。代价不是行数而是**同一个坐标在两个入口可能得到不同结论**（改一处漏一处 → 提交入驻被拒、改门店却通过）。范围常量（±180 / ±90）也随之只留一处 |
| `ph-provider`：`ProviderAccess.requireById(long)` 收口两处相同的 `requireProvider` | 「查不到就是 40400」是**一条对外口径**，两份实现意味着它能悄悄分叉 |
| `ph-ai`：`RiskLevel` 枚举收口两处相同的 `riskLevelOf` | `green/yellow/red → 1/2/3` 的换算原先在知识浏览与症状识别里各一份，而后者注释还自认「与 AI 咨询同一口径」——作者知道它有多份。同一份数据在两个入口分级不同属于「两处都对但合起来错」。**认不出返回 null 而不是兜底成 GREEN**：兜底会把「那条知识的分级写坏了」变成一个看起来正常的绿色建议 |
| `ph-privilege`：`InviteLadder.enabledTiers(mapper)` 收口邀请阶梯的两处读法，**并修掉已经发生的分叉** | 发奖侧只取**启用中**的档位，C 端展示侧取**全部**档位。于是运营停用某一档之后，C 端仍会把它当作「再邀 3 人得券」的下一个目标显示出来，而那一档永远不发——**不是显示问题，是平台作出的承诺与兑现不一致**。口径定为「停用档位对用户完全不可见」（停用这个动作要表达的正是「这一档现在不作数」），两处都从这一处取 |
| `ph-provider` 的 C 端文案：`ProviderBrowseService` 的 40400 文案「服务者不存在或当前不可预约」→「**这家门店**不存在或当前不可预约」 | 这条 message 会**原样展示给 C 端用户**（`ProviderDetailView` 把它直接放进 errorMessage），而 C 端从标题到按钮一律说「门店」。「服务者」是平台内部与两个后台的用词，同一屏上两个词指同一个东西，用户只会以为页面出了错。判定方法（会不会被 C 端直接展示）写进了 `CONTEXT.md` 的服务者条目 |

### 5.4 配置与部署路径：一处「照文档配也不生效」

| 改动 | 原先 |
| --- | --- |
| `application.yml` 补 `app.assessment.super-admin-user-ids: ${ASSESSMENT_SUPER_ADMIN_USER_IDS:}`，`.env.example` 列出该项并写明 fail-closed 语义 | 读取处是 `@Value("${app.assessment.super-admin-user-ids:}")`，而 `application.yml` 里**没有这一段**（其余 8 组配置都写了中转）。Spring 的 relaxed binding 只把 `APP_ASSESSMENT_SUPER_ADMIN_USER_IDS` 映射到那个属性，而 ADR-0052 与 `contract/admin.yaml` 让运维配的是 **`ASSESSMENT_SUPER_ADMIN_USER_IDS`**——**照文档配也到不了那个属性**，考核规则与单项分覆盖会永远 fail-closed，只有一行启动 WARN。测试能过是因为用了 `@TestPropertySource`。这与端口未接线是同一型缺陷：**测试证明机制可用，部署路径是断的** |

## 六、缺失项的修复建议（按优先级）

> 排序依据是**依赖关系**与**投入产出比**，不是条目编号。第 1 项是这一轮新发现的、也是唯一让
> 「已实现」的功能在生产不成立的一项。

1. **两个后台的登录入口（最高优先）**。这是「20 个页面都实现了、但真实使用中到不了」的唯一原因。
   前置是**后台账号与角色体系**：`contract/{provider,admin}.yaml` 加 auth 路径、`AccountService`
   签发 PROVIDER / ADMIN 域令牌（`JwtService` 已支持三域，`LoginDomain` 已就绪）、两端各加一个登录页
   往各自的 tokenStore 写入。**一个业务决策要先定**：后台账号是绑定现有 C 端账号 id（ADR-0035 已倾向
   这一条）还是独立一套——前者立刻带来「同一个人既是用户又是店主」的权限口径问题（ADR-0035 的待澄清）。
   代码量不大，卡点在决策而不是实现。
2. **C 端知识库浏览页（F024/F025 的界面）**。后端只读出口已经可用、有 4 条测试
   （`/app/knowledge/entries` 列表与详情、复核状态必填）。这是本轮之后**最小的一块界面欠账**：
   一个列表 + 一个详情，复用 C 端已有的四态组件。
3. **服务者侧的照片墙与报工（F023 的最后一段）**。需要一个业务输入先定：服务者令牌能不能用
   `open.yaml` 的文件直传接口（现在 `provider.yaml` 里没有 files 路径）。定了之后就能接
   `saveOrderPhotoSlot` / `reportOrder`（两个 API 方法已经写好但没有调用点，连 `40901` 的前端文案一起补）。
4. **F015 的「系统自动匹配最优可用券」**。交付文档 BPM-3 的明文要求，实现只在「用户选券」这一步。
   建议做成后端在创建订单时按「可用券中抵扣最多」自动选一张（用户显式传 `coupon_id` 时以显式为准），
   `CouponService` 已有 `check` 与最优惠比较所需的一切数据。**注意**：这改的是下单链路的行为，
   要连带补契约描述与 C 端「是否允许改选」的交互口径。
5. **F026 的两条业务消息**。券过期提醒（`CouponExpiryJob` 里加一次消息写入，代价很小）与预约提醒
   （`ph-reminder` 有 `BusinessMessageApi` 这个接口面，`ph-order` 接线即可）；顺手把
   `TYPE_INVITE` 的邀请进度通知补上（`Message` 里已定义，缺生产者）。
   实时通道（WebSocket / SSE）成本高、收益靠后，**建议先不做**，消息中心已能兜住。
6. **F027 的条款页公开可读**。按 code 分成「公开可读」（隐私政策 / 用户协议 / AI 免责）与
   「需登录」（导出 / 注销）两组，或让 `SessionGate` 支持只读内容。这是**合规缺陷**不是体验问题
   ——协议在注册前不可读，「同意」就没有依据。改动很小，建议尽快做。
7. **F004 的「就医记录」录入入口 + 服务者报工回流档案**。两件事同源：`ArchiveSection.entries()`
   不含 MEDICAL（所以 C 端没有入口），而 `ph-order` 的报工只改订单状态、不写 `archive_record`
   （所以「三源并存」在生产不成立）。前者是加一个分项入口，后者是调一次 `ArchiveSectionService`
   ——后者做完，「服务留痕 → 健康档案」这条价值链路才真正闭环。
8. **券模板不可用口径的剩余两处**（40001 vs 40400）。做法：把 `CouponContributionService.requireTemplate`
   拆成「按请求体引用取」（40001）与「按既有记录取」（保持 40400 或改为内部一致性故障）两个方法，
   再统一 `CouponContributionService` / `CouponPoolService`，最后改契约三处描述。
   口径已写进 `docs/conventions.md`，照它改即可。
9. **F007 的天气/疫情提醒**：需要外部数据源（气象 API、疫病通报源），属新采购与合规问题，
   建议单开一票评估，不要塞进功能轮。
10. **F002 的资料编辑入口 / F018 的年度大奖 / F021 三个模块的缺失接口 / 前端重复的收口**：
    都是明确的、边界清楚的小项。年度大奖建议与 ADR 一起明确「不做」（月度阶梯已覆盖激励）。
    前端那几处（C 端 16 视图加载样板、券来源字典 4 份、分页页脚 36 处、`CommunityView.vue` 1210 行）
    建议与一次 ADR-0015 式边界澄清一起做——共享的是**交互状态机**，业务组件仍不共享。

**关于支付（F014 的支付部分、F021 的结算中心）**：不在上述任何一项里。
按 ADR-0002 / 0036 等甲方澄清「钱到店付还是线上收」之后单开一票；**本轮未改动任何相关代码**，
服务者后台的「结算中心」在到店付下是对账视图（有流水与核销明细，没有余额与提现），不是缺失。

## 九、本轮发现但**未修**的问题（交下一轮裁决）

1. **两个后台的账号与角色体系（第六节第 1 项）**——不是代码问题而是决策问题：
   后台账号绑现有 C 端账号 id 还是独立一套？绑定的坏处是立刻产生「同一人两种身份」的权限口径
   （ADR-0035 的待澄清已经点到）。定了才能开工。
2. **`ProviderGrowthFactsApi` 的口径（ADR-0052 需要协调 1）**——「服务者的拉新入口」这个业务物件
   还不存在，所以考核的拉新与券两项**对所有门店都不参与**。这是一个**有效状态**（不是 bug），
   但要与验收方说明：现在总分实际只由过程分与已接线的项构成。护栏里那条例外就是它。
3. **`AppGrowthConsole` 超载（19 个依赖）**——本轮搬走了阶梯那一块，但券/积分/权益/邀请四个域的
   C 端出口仍挤在一个类里。它的类注释声明「本类只做形状装配，不重写任何规则」，而代码里还剩若干
   跨域读。建议按域拆四个 `*Views`，一次做完风险大，需要单开一票。
4. **C 端 16 个视图的加载样板与 `createLatestGuard`**——`latest-guard.spec.ts` 只钉住 guard 本身，
   各视图的 `finally` 与 `isCurrent` 位置靠人抄，漏一处就是「旧响应覆盖新数据」（仓库记录过 D16
   就是这个 bug）。抽一个比 `useSection` 更薄的 primitive 到 `packages/shared/src/http` 是解，
   但要先澄清它与后台那两个 composable 的边界。
5. **`ai_consult` 的三列留痕只写不读**（`grading_rule_hits` / `unvetted_hits` / `retrieval_check`）
   ——数据在积累，没有任何接口或界面能取到，只能手写 SQL 看。要么在运营后台加一个排障详情页，
   要么在实体注释里写明「只供 SQL 排障」，别继续含糊。
6. **`ProviderFacts.findListedService` 没有任何调用方**——它是为「读路径不该整页失败」写的降级版本，
   而接线的两个消费点用的都是 `requireListedService`（硬失败）。接线之后这个方法的定位更模糊了：
   要么给它一个消费方（订单详情/门店详情的只读展示），要么删掉。
7. **前端 6 个 API 方法定义了但没有调用点**（`lockCoupon`、`createCard`、`listComplianceDocuments`、
   `updateArchiveRecord`、`saveOrderPhotoSlot`、`reportOrder`）。其中三处对应已知的功能缺口
   （发经验卡片、改档案记录、报工），另三处可能是多余的接口。建议先逐条裁决「缺界面」还是「删方法」。
8. **`provider.region_code` 的区域保护（F022 的另一半）**——口径已定（审核期软约束 + 阈值可配），
   但字段无人写入。缺的是业务输入（录入入口）不是代码；要做它至少要定「区域怎么划 / 保护什么 /
   与等级怎么联动」三件事（ADR-0052 待澄清 1）。
9. **`app.assessment.super-admin-user-ids` 的读法**——本轮补上了配置来源，但它仍是全仓**唯一**
   用 `@Value` 读的配置（其余 8 组都在 `*/config/` 下用 `@ConfigurationProperties`）。
   建议随角色体系落地一起改成配置类，那时名单机制本身会被删掉。
