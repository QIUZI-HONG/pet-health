# AI 配置分层：技术参数走配置，业务可调项入库 + 运营后台

AI 相关配置按「谁能改」分三层：

| 类别 | 例子 | 存哪 | 谁改 | 生效方式 |
| --- | --- | --- | --- | --- |
| 技术参数 | API Key、base-url、模型名、超时、重试次数、日预算上限 | 环境变量 / `application.yml` | 部署者 | 重启 |
| 业务可调项 | 提示词模板、硬红线词词典、风险分级规则、降级开关、灰度比例 | 数据库 + 运营后台 | 运营 | 即时 |
| 代码常量 | 工具调用的参数 schema、引用校验逻辑、检索融合算法 | 代码 | 开发者 | 发版 |

## Considered Options

- **全部放代码，走发版**：可 review、与代码同版本；但交付文档 B8 明确要求运营后台能配「风险分级规则、提示词版本管理与灰度、降级开关」，改一个词拉一次发版不成立。
- **全部入库**：最灵活，但把超时、模型名这类技术参数也交给线上改——改错一次全线超时，且难归因；本地开发还得连库。

## Consequences

- 提示词**带版本号入库**，`ai_consultation` 落库 `prompt_version`，每次调用留痕——没有这个，分级漂移无法归因。
- 提示词**灰度**：同一提示词可存在多个版本，按比例分流。出问题回滚 = 改比例，不发版。
- 降级开关是**运营可拉的电闸**：模型异常或成本失控时，运营把开关一关，全量走规则通道，不必等开发者。
- 代价：提示词脱离了代码 review 流程，需要在运营后台补一道改动记录（至少留「谁在什么时候把它从 v3 改成 v4」）。
