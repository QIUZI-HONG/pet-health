# 第十批裁决：里程碑切分、数据模型的唯一来源、合规体系的收口

三条治理类决定，合并成最后一批（同 [ADR-0024](0024-quota-care-community-tracking-packages.md)）。

## 一、里程碑切分（挡 [#69](https://github.com/QIUZI-HONG/pet-health/issues/69)）

**按依赖排四段，不排日历**（地图已定「工期不作为约束，按依赖排序」）：

| 段 | 内容 | 段末验收标准 |
| --- | --- | --- |
| ① 供给底座 | 标准目录、服务者入驻与审核、选品定价上架 | 该段功能清单 + 三套测试全绿 + 契约生成物同步 |
| ② 交易 | 订单（不含支付）、核销、券池与出券 | 同上，且「下单 → 预约 → 核销」闭环可在浏览器里走通 |
| ③ 增长与权益 | 邀请裂变、积分与任务、权益引擎、评价体系 | 同上，且权益叠加与到期回收有用例钉住 |
| ④ 治理与体验 | 服务者考核、埋点与看板、社区、两个后台界面、部署 | 同上，且上线前置清单可逐条勾 |

- **段与段之间是依赖而不是并行**：②依赖①的目录与定价，③依赖②的订单与券，④依赖③的数据。
- 每段结束都要**重跑三套测试 + 契约同步检查**，并把该段的功能清单状态写进 `docs/testing/` 的报告里（不另立进度文档）。

## 二、数据模型的唯一来源（挡 [#64](https://github.com/QIUZI-HONG/pet-health/issues/64)）

**不写手抄的 DDL 汇总**：

- 每张表的权威定义在 `server/ph-boot/src/main/resources/db/migration`（[ADR-0011](0011-persistence-and-migrations.md) 已定「DDL 只由 Flyway 产生」）。
- 全局关系由各模块的 `package-info.java`（模块职责与它拥有的表）与 ADR（跨模块的边界）承担。
- README 里指明「找表定义看 migration」。
- 理由：手抄的 DDL 汇总与迁移脚本双份维护，**必然漂移**，而漂移的 schema 文档比没有文档更坏——它会让人按错误的前提改表。
- 若将来确实需要一份给外部看的可读 schema，**用脚本从库里生成并加进 CI 校验同步**，不手写（本条不阻止那种做法，只是不手写）。

## 三、合规体系的收口（挡 [#74](https://github.com/QIUZI-HONG/pet-health/issues/74)）

**以现状结案，三条待法务/甲方确认**：

- **已就绪（机制）**：三份合规文档的骨架与占位正文、账号数据导出、注销（含二次确认、软删范围、手机号可重新注册）、AI 免责声明的三态文案。
- **待法务确认（内容）**：
  1. **合规文档正文**——库里现在是占位文本，正文要法务出；
  2. **合规文档是否公开只读**——当前要求登录才能读（注册页的《用户协议》《隐私政策》入口点开也被闸门挡住），是否改为公开只读属法务与产品共同决定；
  3. **留存期限**——注销后数据保留多久、档案保留多久、审计日志保留多久。
- **本 ADR 的作用**：把「合规」从「做了没有」变成「哪部分就绪、哪部分等谁」。在三条待确认项闭环之前，合规只到「机制就绪」，**对外不能说「已合规」**。

## Consequences

- 四段里程碑与票的分组大致对应（①#104/#105 ②#109/#110 ③#111/#112/#113/#108 ④#114/#118/#119/#117/#122），但**以依赖为准、不以票号为准**。
- 不写 schema 汇总之后，评审要改表时看迁移与 undo 成对提交（[ADR-0011](0011-persistence-and-migrations.md) 已经这么要求）。
- 留存期限未定之前，注销的「物理删除」不做定时任务（现在只软删）；这条挂在待确认项上，不自行拍一个天数。
