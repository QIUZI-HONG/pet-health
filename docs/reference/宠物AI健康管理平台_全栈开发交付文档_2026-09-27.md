## 第一章 项目概述

### 1.1 背景

城市养宠家庭（25-40岁）普遍面临四类问题：宠物生病不知道严不严重、医疗费用不透明怕被坑、老年/慢病宠物日常照护繁琐、健康记录零散。现有竞品（在线问诊、综合电商、智能硬件、健康管理、内容社区）均为"点状服务"——有事才用、平时不管、不主动预警。

本平台以 AI 为基座，做"面状、持续、主动"的宠物健康守护：24小时全程监护，主动提醒、被动咨询、持续记录。AI 解决不了的，转远程人工；远程解决不了的，再匹配认证商家。形成"AI自助→远程人工→商家服务"三级问题解决生态。

### 1.2 目标

**核心目标**：交付一个可上线、可运营、可验证商业模式的 MVP 产品。

**量化目标**：
- 7日留存 ≥ 30%
- 邀请裂变 K 因子 ＞ 1
- 付费转化率 ≥ 3%
- AI 分诊准确率（0-6月）≥ 70%

**产品目标**：
- 用户可免费完成：建档、每日打卡、基础AI问答、基础提醒
- 用户通过邀请/打卡免费解锁增强功能，或订阅付费
- 商家可完成：选品、定价、出券、接单、核销、看考核
- 平台可统一管理：标准目录、价格区间、券池、流量分配

### 1.3 用户

**C端用户**：城市养宠家庭，犬猫为主，把宠物当"毛孩子"。
- 核心：25-40岁，愿意为健康花钱但不想被坑
- 次级：老年/慢病宠物主人、多宠家庭、新手养宠人

**B端用户**：宠物医院、宠物店/洗护、训犬师、寄养/上门喂养、食品用品、摄影/殡葬/保险/托运等。

### 1.4 范围（做什么）

1. C端：首页健康驾驶舱、服务页、AI管家、健康档案、我的
2. AI：多模态分诊（文/图/视频/语音）、风险分级、主动提醒体系、健康评分、报告
3. 商家：PC后台（接单/核销/券/考核/数据）、技师端小程序（接宠检查/服务留痕/报工）
4. 券体系：商家出券→统一券池→用户邀请任务获取→到店核销
5. 裂变：邀请得券/权益、打卡得券、任务中心、积分体系
6. 社区：同款宠友圈、慢病社群、经验卡片（嵌入首页/AI/档案，不做独立Tab）
7. 权益：邀请阶梯、打卡阶梯、订阅阶梯三级权益体系

### 1.5 不做什么（范围外）

- 不做在线视频问诊（首期用"转人工咨询"文字通道，视频通话留接口）
- 不做硬件对接（零硬件门槛，数据全靠用户录入+商家报工）
- 不做宠物社交/配种/殡葬的交易闭环（只做导流与咨询券）
- 不做保险承保（只做保险咨询导流）
- 不向普通用户收"记录费""基础AI费"（只向深度功能/交易抽佣收费）
- 不做独立社区Tab（社区嵌入首页/AI管家/档案页）

### 1.6 非功能要求

- 响应：P95 < 500ms（列表/详情），AI问答 P95 < 3秒
- 可用：核心链路无单点故障，支持滚动升级
- 安全：用户隐私数据加密、AI不越界诊断、防刷邀请/刷券
- 兼容：微信小程序（iOS/Android）、安卓APP、iOS APP
- 可运维：日志聚合、监控告警、支持回滚

### 2.3 核心业务流程

**BPM-1 用户首次使用主链路**

```
打开小程序/APP
  → 游客态浏览服务目录（只读）
  → 注册/登录（手机号或微信）
  → 添加第一只宠物（必填：昵称/品种/性别/生日/体重）
  → 完成AI健康评估（送券+积分）
  → 进入首页驾驶舱
  → 每日打卡（3秒）
  → AI主动提醒送达
```

**BPM-2 邀请裂变链路**

```
用户在"我的-邀请"生成专属海报/链接
  → 分享给好友
  → 好友点击 → 注册 → 完善档案（绑定邀请人）
  → 双方各得20元洗护券
  → 邀请人累计：1/3/5/10/15人阶梯解锁权益
  → 月度/年度排名奖励
```

**BPM-3 服务交易链路**

```
用户服务页/AI管家推荐选服务
  → 选商家 → 看资质/报价
  → 选标准项目/套餐 → 下单
  → 系统自动匹配最优可用券 → 实付 = 价 - 券
  → 微信支付
  → 预约到店时间
  → 到店：商家扫码核销
  → 技师端：接宠检查拍照 → 服务防护拍照 → 服务 → 取宠对比 → 主人确认
  → 报工 → 自动写入健康档案 → 生成社区经验卡片
  → 用户评价晒单 → 得券+积分
```

**BPM-4 商家入驻与考核链路**

```
商家申请入驻 → 平台审核资质
  → 后台"选品"（勾选标准目录）→ 填价（区间内）→ 选券（勾选必出券目录）→ 上架
  → 店内铺设二维码（用户扫码绑定商家为拉新推荐人）
  → 持续：接单/核销/引导注册/贡献券
  → 每月1日自动计算：总分=拉新40%+券40%+过程20%
  → 等级决定：AI推荐优先级 + 区域保护
```

### 2.4 异常场景与处理

| 场景 | 默认处理 |
|---|---|
| 用户重复注册同一手机号 | 提示"该手机号已注册，请直接登录"，引导登录 |
| 验证码60秒内重发 | 按钮置灰60秒倒计时，同一手机号1分钟1次、1天10次上限 |
| AI服务超时（>10秒） | 前端显示"AI正在思考，请稍候"，10秒后提示重试，最多重试1次 |
| AI不可用/降级 | 降级为"提交成功，兽医将人工回复（预计2小时内）"，转人工队列 |
| 外部知识库检索失败 | 返回通用建议+免责声明，不编造，提示"建议咨询兽医" |
| 支付超时/未回调 | 订单保持"待支付"，30分钟未支付自动取消，券回退 |
| 券核销冲突（重复使用） | 已核销券不可再用，提示"该券已被使用"，记录异常 |
| 商家不在营业时间预约 | 禁止选择非营业时段，提示营业时间 |
| 价格超出允许区间 | 后端校验拒绝，前端输入框提示"价格须在¥X-¥Y之间" |
| 用户删除宠物 | 二次确认弹窗，30天内可恢复（软删除），到期物理删除 |
| 商家清退 | 保留历史订单与档案，禁止新接单，已预约订单自动退款 |
| 网络断开 | 本地缓存档案/打卡草稿，恢复后自动同步，断点续传 |
| 推送失败 | 消息中心始终可达，推送作为增强，失败不影响主流程 |
| 并发抢同一预约时段 | 乐观锁，后提交者提示"该时段已被预约，请重新选择" |

### 2.5 验收标准

- **功能**：F001-F027 全部实现，PRD 功能覆盖率 100%
- **权益**：邀请/打卡/订阅三级权益计算准确，无越权
- **券**：商家出券→券池→用户得券→自动匹配→核销→结算全链路跑通，无超发、无重复核销
- **价格**：商家定价 100% 区间校验，目录外服务须经平台审核
- **服务留痕**：三道照片墙缺一道则系统拒绝报工
- **AI**：基础分诊准确率 ≥ 70%，红色风险必带就医建议+免责声明
- **安全**：无 SQL 注入/XSS/越权，敏感数据加密，通过安全测试
- **性能**：P95 响应 < 500ms，AI 问答 P95 < 3秒，支持 500 并发
- **兼容**：iOS/Android 真机、微信小程序双端通过核心链路
- **体验**：核心操作路径不超过 3 步，打卡 3 秒内完成

## 第四章 UI/UX 设计规范

### 4.1 设计原则

- **宠物友好**：圆润、温暖、低压力，避免尖锐直角和强警示色滥用
- **一屏一任务**：每个页面只做一件事，核心操作3步内可达
- **状态明确**：加载/空/错/无权限四种状态全覆盖
- **安全优先**：AI医疗相关提示使用明确视觉层级

### 6.3 安全方案

- **传输**：全站 HTTPS（TLS 1.2+），HSTS 开启
- **认证**：JWT（Access Token 2h + Refresh Token 7d），Refresh Token 存 Redis 可吊销
- **授权**：RBAC 角色权限矩阵（见2.2），每个接口校验 `角色 × 资源 × 操作`
- **敏感数据**：手机号/身份证/病历 字段级加密（AES-256），数据库静态加密
- **密码**：无密码体系（验证码登录），管理员密码 bcrypt
- **防注入**：ORM 参数化查询，禁止字符串拼接 SQL
- **XSS**：输出编码，CSP 策略，富文本白名单过滤
- **CSRF**：JWT 不依赖 Cookie，天然免疫
- **限流**：Redis 滑动窗口，接口级 QPS 限制；验证码1分钟1次、1天10次
- **防刷**：邀请/券/积分 风控规则（设备指纹、同IP限制、异常行为检测）
- **越权防护**：所有资源访问校验归属（用户只能访问自己的宠物/订单）
- **文件上传**：白名单 MIME + 大小限制（图片10MB、视频100MB）+ 病毒扫描 + 鉴黄
- **隐私合规**：隐私政策、用户协议、AI免责声明；提供数据导出/账号注销接口
- **审计日志**：管理员操作、敏感数据访问全量记录

### 6.4 高可用与可扩展

- MySQL 主从读写分离，Redis 哨兵模式
- 无状态服务多实例部署，Nginx 负载均衡
- 接口幂等（防重复提交，基于请求ID）
- 熔断降级（AI服务不可用时转人工队列）
- 数据库分库分表预留（用户表按用户ID取模，订单表按时间）

### 10.3 部署步骤

1. 服务器初始化：安装Docker、配置SSH密钥、开放80/443/22端口
2. 克隆代码：`git clone <repo> /app`
3. 配置环境变量：`.env`（数据库密码、JWT密钥、微信AppID/Secret、支付密钥、AI API Key）
4. 构建镜像：`docker compose build`
5. 初始化数据库：执行 `db/init.sql` + 分库初始化脚本
6. 启动服务：`docker compose up -d`
7. 配置 Nginx：`docker compose up -d nginx`，配置 HTTPS
8. 配置 CI/CD：Git推送触发自动构建部署到预发→生产
9. 微信开放平台配置：小程序AppID、业务域名、支付目录
10. 健康检查：`curl https://域名/api/health` 返回 ok

```yaml
    image: nginx:1.25
    ports: ["80:80", "443:443"]
    volumes: ["./nginx:/etc/nginx/conf.d", "./ssl:/etc/nginx/ssl"]
    depends_on: [app]
  app:
    build: ./backend
    environment: *env
    depends_on: [mysql, redis]
  mysql:
    image: mysql:8.0
    volumes: ["./data/mysql:/var/lib/mysql"]
  redis:
    image: redis:7-alpine
  rabbitmq:
    image: rabbitmq:3-management
  es:
    image: elasticsearch:8.12
  neo4j:
    image: neo4j:5
```

### 10.5 回滚方案

- 镜像版本化管理，每次构建打 git commit hash 标签
- 回滚命令：`docker compose pull && docker compose up -d app`
- 数据库回滚：迁移脚本必须可逆（up/down），回滚执行 down 脚本
- 灰度：先部署1台，观察10分钟无异常再全量
- 快速回滚目标：5分钟内恢复

### 10.6 监控与日志

- **监控**：Prometheus + Grafana，监控 CPU/内存/磁盘/接口QPS/P95/错误率/队列堆积
- **告警**：企业微信/钉钉机器人，阈值触发（错误率>1%、P95>1s、磁盘>80%）
- **日志**：ELK 聚合，按 `request_id` 全链路追踪
- **业务监控**：每日新增用户、邀请数、券核销数、AI准确率、支付成功率
- **健康检查**：`/health` 接口，K8s/Docker 存活探针
