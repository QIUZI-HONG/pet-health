## 一、结论摘要

**已实现的是一条完整的 C 端纵向切片**（账号 → 建档 → 打卡 → 评分 → 提醒 → AI 咨询 → 档案照片 →
合规三件套），工程质量高于同阶段项目的常见水位：真实 MySQL/Redis 上的接口测试、
契约单一源头、迁移与回滚脚本成对、术语纪律零违规、注释普遍在解释「为什么」。

**但按交付文档的口径，产品整体完成度约三分之一**：27 项功能里
**完整完成 5 项**（F001/F002/F003/F005/F027）、**部分完成 6 项**（F004/F006/F007/F008/F024/F026）、
**未实现 16 项**（F009–F023、F025）、另有 **2 个附项已裁决不做**（微信登录、视频输入）、
**支付链 1 项待澄清**（含在 F014 内）。缺口集中在三块：
**服务供给侧（目录/服务者/选品/订单/核销）、裂变与权益（券/邀请/任务/积分/权益引擎）、
社区与两个后台**。这三块在仓库里的现状是「Maven 模块 + 契约占位 + 已定稿的票」，
即骨架已就位、业务代码为零。

这不是「做坏了」，而是**路线使然**：[地图 #52](https://github.com/QIUZI-HONG/pet-health/issues/52)
把交付切成了逐张裁决的决策票，先打通一条端到端切片（含持久层、鉴权、加密、测试脚手架），
再用同样的模式铺开。本报告的第五节把「哪些是刻意的、哪些是真的缺」区分开了。

## 五、本轮重构记录（分层 / 命名 / 异常 / 去重 / 注释）

原则：**只做行为不变的重构，每一处都由三套测试兜底**；动不到的地方写明理由，不为了「看起来整洁」改语义。

### 5.1 分层与模块边界

| 改动 | 为什么 |
| --- | --- |
| `FileService` 的图像处理（缩放、等比高度、JPEG 编码、两个常量）拆成 `file/storage/Thumbnails`（465 → 396 行） | 变化原因不同：一个管文件生命周期（凭证→落定→读→删），一个是纯计算（无库、无存储、无事务）。原先两处缩放各算各的（一处读常量、一处用参数），改宽度上限必有一处漏改，而漏改的表现是**图被拉扁** |
| `IdempotencyFilter` 的存储半边拆成 `account/idempotency/IdempotencyStore`（410 → 254 行） | 改回放语义不该动 Lua 脚本、调 TTL 不该动过滤器。拆完 `IdempotencyStore` **不认识 Servlet**，可以对它单独讲清「归属令牌为什么必须存在」 |
| 补 `ph-reminder`、`ph-boot` 的 `package-info.java` | 全仓其它 11 个模块都有；模块职责写在包里，读代码的人不必先看 pom |
| 归属校验收口：`CheckInService` / `EpidemicRecordService` 各自的 `requireOwnedPet` 删除，改注入 `PetService.requireOwned` | 四份同样的 `selectOne(id + user_id)` 意味着「软删要不要算不存在」这类口径有四次要同步。收口后 ph-record 只有一处，`PetService` 内部再分 `findOwned`（返回空）与 `requireOwned`（抛 40400），两种语义各自有名 |

### 5.2 命名

| 改动 | 为什么 |
| --- | --- |
| 契约与两端：`CheckInItemInput` / `EpidemicRecordInput` / `ReminderSettingInput` → `*Request` | 契约里请求体 schema 有 `*Request`（12 个）与 `*Input`（3 个）两套写法。**统一到 `*Request`**，并重新生成前端类型（`gen:api`）、同步 Java DTO 类名与引用。Java DTO 的 Javadoc 原先写着 `{@code CheckInItemRequest}`——**契约里根本没这个名字**，属注释与实现相反，一并对上 |
| `MessageService.settings()` → `listSettings()`；`CheckInService.day()` → `dayState()` | 只有名词的方法名读不出「是查还是写、返回一个还是一串」 |
| 新增 `docs/conventions.md`「命名（代码标识符）」一节 | 把「请求体叫 Request、查集合叫 listXxx、查不到即 404 叫 requireXxx、工具类只放静态方法」这些**同形不同名**的选择写成一条约定，别每处临时挑 |

### 5.3 异常与错误处理口径

| 改动 | 为什么 |
| --- | --- |
| 新增 `docs/conventions.md`「删除类接口的幂等口径」一行 + 修契约 `DELETE /messages/{id}` 的 `summary`（原先写「幂等」，实现是 40400） | 仓库里其实有**两条**口径且各自正确：顶层资源（消息/宠物/文件）重复删除与删别人的一律 40400（不泄露存在性）；宠物名下的子资源（打卡分项、防疫记录）先校验归属、自身删除幂等。原先只写在代码注释里、契约那句话与实际相反——现在是一处成文规则 |
| 日期解析统一走 `AppTime.parseDate`（`CheckInController` 不再用 `@DateTimeFormat`） | 同一个 `date` 字段原先有两套解析（请求体走 AppTime、查询参数走 Spring），`2026-02-31` 这种「格式对但日子不存在」在两条路径给出不同话术 |
| `ImageSniffer.probe` 的 `catch (IOException) → empty` 补 WARN 日志 | 返回空是对的（对用户就是「换一张图」），但**不能无声**：魔数对而内容损坏是客户端 bug 或上传被截断的现场（conventions.md 禁止吞异常） |
| `ErrorCode` 的 80001/80002/90001 补注明「无代码路径产出，归属 #110 / #75」 | 与 D28 删掉 60001/60002 的处理保持同一逻辑：先判断是「契约有、实现没做」还是「口径不同」——这三个属前者（券池与定价的票未做），所以**留字段、写明归属**，不静默当死代码 |

### 5.4 消除重复逻辑

| 改动 | 原先 |
| --- | --- |
| 新增 `ph-common/util/Text`（`trimToNull` / `truncate`） | 同一形状三份（`PetService.trimToNull`、`AiConsultService.trim(value,max)`、`FileService` 里手写 `isBlank` 判断） |

| 分页上限收成 `PageResult.MAX_PAGE_SIZE` 一处 | 原先 DTO 注解 `@Max(100)`、MyBatis-Plus 拦截器、service 夹取三处各写一个数 |
| 前端新增 `toApiFailure(error, fallback)`（shared） | 四个视图各写一遍「ApiError → message + requestId，其它 → 兜底」，六行 × 4；「哪些错误带请求 ID」这条规则散在四处 |
| 前端新增 `dict/risk.ts` 的 `riskTone(level)` | 三个页面各写一次分档，且边界不同（`=== 3/=== 2/其余` vs `!level || level <= 1`）——`0/null/undefined` 在三处落到不同颜色。现在**分档只有一份，配色与文案各留在调用点** |
| 把 `.ph-form*` 与 `.ph-card__note` 从视图的 scoped 样式提到 `styles/app.css` | 前者是**真 bug**：RecordsView 用了 `.ph-form/.ph-form__grid`，而定义只在 ProfileView 的 `scoped` 块里——scoped 样式不跨组件生效，档案页表单实际只有 `.ph-field` 生效（栅格与按钮行是浏览器默认排列，肉眼就是「两个输入框没对齐」）。后者在三处值还不一样（13px / 12px / 无定义） |
| AI：四条降级分支改为表驱动（`_DEGRADE_SPECS` + `_degrade()`） | 四个 `except` 分支同形状、共 50 行，改一处要记得改四处；现在一行的差异（风险等级、话术、是否捎带用量、是否提图片）都在一张表里 |
| AI：`tests/eval_cases.py` 收口 `load_cases()` | 结构校验与实弹门槛各有一份读取实现——两份一旦不同步，**结构校验守的就不是门槛跑的那批样本** |

## 六、缺失项的修复建议（按优先级）

> 依赖关系已按票的 blocking 顺序排：先 1，才能做 2。

1. **补 F010/F012 的供给底座（#104 + #75）**——标准目录 + 定价区间 + 服务者入驻审核。
   这是三条链路的共同前置（服务页、AI 找服务、订单都需要「项目编码 + 区间价」）。
   建议顺序：`ph-catalog`（目录与区间校验）→ `ph-provider`（入驻与资质）→ 前端服务页接真实数据。
2. **补 F004 的档案分项与时间轴（#102）**——表结构已定（ADR-0023 单表 + `structured_payload`），
   把「证件与合规 / 就医记录 / 时间轴 / 导出」补齐，C 端档案页才能兑现交付文档的 8 个模块入口。
3. **补 F008 的健康报告（#115）**——评分与趋势已经在库里（`health_score` 按天存行），
   周报/月报本质是对既有数据的聚合 + 模板，性价比高，且是留存抓手。
4. **补 F007 的推送通道（#85）**——先做轮询兜底 + WebSocket 二选一；
   提醒的**生成**已经完整，缺的只是「送达」。
5. **补 F024/F025 的知识库与检索（#100/#101）**——这是 F006 的「最后一公里」：
   现在 `citations` 恒空、药名表还是代码常量（ADR-0021 要求入 DB）。
   做完之后 AI 回答才敢说「基于知识库」（当前对外文案已刻意回避这句）。
6. **F009 专项照护（#116）**——口径已定（派生态），实现量小，依赖档案字段（第 2 项）。
7. **F015–F019 券/邀请/任务/积分/权益（#110–#113）**——建议放在订单之后：
   「券能抵扣」需要订单结构先存在；权益引擎的额度阶梯还需要 #112 的前置数据（免费额度计数已跑）。
8. **F021–F023 两个后台（#118/#87/#114）**——服务者后台与技师端是**供给侧**，
   与第 1、7 项同期做才有意义（没有目录与订单，后台没有东西可接）。
9. **F020 社区（#117）**——独立性强，可以并行；注意 ADR-0024 已定「桌面 Web 上重做」的形态。
10. **横切项**：按 #121 做安全加固与可观测性（限流/审计/幂等已落地，还差真渗透测试与告警面板）；
    按 #123 决定语音转写供应商（F006 的语音输入）。

**关于支付（F014 的支付部分、F021 的结算提现）**：不在上述任何一项里，
按 ADR-0002 等甲方澄清「钱到店付还是线上收」之后单开一票；本轮未改动任何相关代码。
