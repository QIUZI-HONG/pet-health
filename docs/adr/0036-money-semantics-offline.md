# 订单与券的「钱」语义：到店付，实付是预估展示值而不是收款事实

维持 [ADR-0002](0002-offline-payment.md)：**平台不经手资金**，钱在门店直接付给服务者。

订单上保留「总额 − 券面额 = 预估实付」这个计算，但它是**展示用计算值**，字段名与文案都必须标明是预估（`estimated_pay_amount`），**不参与对账、不构成收款事实、不产生任何资金流**。核销是**履约确认**，与收款彻底解耦（[CONTEXT.md](../../CONTEXT.md) 的核销条目已经这么定义）。

## Considered Options

**线上收款（微信支付 / 服务商分账）**（交付文档 F014「微信支付 + 余额」、9.7「真实小额支付跑通」）

- 平台经手资金=**二清**，需要支付牌照或服务商资质、商户号、结算与退款体系，以及一套对账与差错处理。
- 它会连带改掉四张票的前提：#53 的券成本归属、#55 的核销与收款先后、#71 的订阅支付、#77 的订单状态机（`待支付/已支付/已退款` 才有意义）。
- 交付文档自己也没写清资金归属（券的 `merchant_cost` 与 `platform_subsidy` 两个字段谁兜底没定），所以选了它就要**同时**回答这些问题。

**订单完全不出现「实付」**（最保守）

- 数据上最干净：只有总额与券面额，不存在「把计算值当账」的风险。
- 代价是交付文档 5.7 的「实付金额大字 + 划线原价」做不出来，而这正是券体系的卖点展示。

**到店付 + 预估实付**（选它）

- 保住视觉稿与券的卖点（用户看得到「原价 ¥128 → 预估实付 ¥108」），又不制造收款事实。
- 券的作用被限定成**到店抵扣凭证**：它的价值在门店结算时体现，平台只记录「谁出了券、抵扣了多少」，不记「谁收了多少钱」。
- 与 ADR-0002 一致，不需要任何支付资质，且**不阻塞其余 15 张实现票**。

## Consequences

- **交付文档三条验收项按本条改写**（需要甲方书面确认，见下）：F014 的「支付 / 退款」、5.7 的「实付大字 = 实付金额」（改称**预估实付**）、9.7 与 12.1 的「真实小额支付跑通」（改为「到店付 + 券核销全链路跑通」）。
- **订单状态机少三个状态**：`待支付 / 已支付 / 已退款` 在到店付下失去语义，状态机的重建是 [#77](https://github.com/QIUZI-HONG/pet-health/issues/77) 的事，但它的约束是确定的——**钱不再是状态迁移的驱动因素**，「取消」也不再由「30 分钟未支付」触发。
- **「退款」退化为线下动作**：系统里不做退款单、不做退款状态；服务者清退时已预约订单走**取消**，不是退款（交付文档 2.4 那条要按此理解）。
- **对账（Reconciliation）口径随之变化**：没有资金流可对，对账退化为「履约与券核销的核对」——核销记录与券实例的账、报工与订单的账。
- **#71 的订阅阶梯失去支付载体**：订阅若要做，只能是「线下签约 + 后台标记有效期」，属 #71 另议；[#80](https://github.com/QIUZI-HONG/pet-health/issues/80) 的权益引擎因此**按两条路径（邀请 / 打卡）设计，但表结构要能容纳第三条**（这一条 #80 的票里已经写明）。
- 券的「成本归属」在到店付下**不再是资金结算问题，而是口碑与考核问题**：服务者出的券影响的是它自己的核销与考核分（#58/#114），平台补贴券影响的是平台侧的统计。这条留给 #53 落成具体规则。

## 待甲方澄清

本条与甲方验收文档冲突，需要他们**书面确认**（地图 #52 的 Notes 里那句话可以直接用）：

> 验收标准里有「真实小额支付跑通」，但资金二清需要支付牌照或服务商资质。我们按「到店付 + 订单只做预约与券展示」交付，并把这条验收项改掉——请确认。

在确认之前，本 ADR 是**产品侧口径**（不影响其余切片开工），一旦甲方要求线上收款，受影响的正是上面 Consequences 里列的那四处，届时按 #53/#55/#71/#77 的顺序重开。
