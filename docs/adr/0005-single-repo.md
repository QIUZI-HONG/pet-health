# 后端与三个 Web 端同仓（monorepo）

后端、C 端、服务者后台、运营后台、接口契约与文档全部放在 `pet-health` 一个仓库。

## Considered Options

- **两仓（后端一仓 / 前端一仓）**：职责更清楚，但接口契约变更要跨两次提交，前后端版本容易错位。
- **四仓分开**：隔离最彻底，代价是三端共享的设计 token、请求封装与 TS 类型要靠发包同步，对当前规模是纯负担。

## Consequences

- 契约（`contract/`）是同仓的唯一源头：**前端的 TS 类型由契约生成**（`pnpm --filter @pet-health/shared gen:api`），改契约即重新生成、类型立刻报错；**后端 DTO 手写**，靠契约评审与 CI 的漂移检查保证对齐。单仓的价值在于契约与两端代码处于同一个提交里，不会出现一端已改一端未改。
- CI 只需一套流水线，但要按路径过滤触发，避免只改文档却跑全量构建。
- 单仓不等于单构建：后端 Maven 与前端 pnpm 各自独立构建，互不干涉。
