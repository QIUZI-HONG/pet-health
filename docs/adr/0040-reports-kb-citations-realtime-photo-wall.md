# 第七批裁决：健康报告、知识库引用口径、实时通道、三道照片墙

四条互不依赖，合并（同 [ADR-0024](0024-quota-care-community-tracking-packages.md)）。

## 一、健康报告（挡 [#91](https://github.com/QIUZI-HONG/pet-health/issues/91) → #115）

- **两种**：周报（每周一生成上周）与月报（每月 1 日生成上月）。与提醒体系共用 Scheduler；**生成必须幂等**（同一天重复触发只留一条，靠唯一键而不是「先查再插」——后者的并发缺陷在 [ADR-0018](0018-checkin-and-health-score.md) 那批已经踩过）。
- **生成方式：规则模板，不调模型。** 报告里的每个数字都来自既有数据，模型在这里只能产生幻觉、不能产生信息；措辞由模板拼（模板文案入库存配置，运营可改）。
- **固定四段**：① 评分与趋势 ② 异常与亮点 ③ 打卡完成度 ④ 建议清单。
- **权益分档**：基础版只给「评分与打卡完成度」；**完整版**（权益码 `report.full`，见 [ADR-0038](0038-order-redeem-rights-points.md)）加「趋势对比 + 异常归因 + 建议清单」。这是交付文档 4.16.6「完整报告是邀请解锁权益之一」的落地。
- 保留**最近 12 期**；页面内展示 + 可导出（复用既有档案导出通道，不新造下载）。
- **文案改称「健康周报」**：交付文档 4.16.4 的标题是「AI 周报卡」，而我们没有调用模型——不许声称是 AI 生成的（[ADR-0028](0028-security-baseline.md) 的口径延续）。

## 二、知识库的引用口径（挡 [#100](https://github.com/QIUZI-HONG/pet-health/issues/100) / [#101](https://github.com/QIUZI-HONG/pet-health/issues/101)）

- 知识条目带**复核状态**（`pending_review` / `vetted`）。种子内容一律 `pending_review`。
- **只有 `vetted` 条目能出现在 `citations` 里**。未复核条目命中时，回答要明说「该建议尚未经兽医复核」，并保留免责声明。
- **检索失败 = 降级为「无来源的通用建议」**，咨询本身仍然成功（[ADR-0026](0026-ai-degrade-codes-and-daily-budget.md) 的降级口径扩展到检索层）。
- 对外话术的边界：**没有 vetted 引用时，C 端不许出现「基于知识库」**。这句话此前被刻意回避（[ADR-0028](0028-security-baseline.md)），只有在「检索已接 + 至少一条 vetted 条目」之后才解禁。
- **复核流程本身是人工流程**（谁来复核、记录留在哪）——**不许在代码里假造一个复核状态**。
  *（2026-10-01 补上）* 这条留白已由 [ADR-0054](0054-knowledge-review-entry.md) 填上：
  复核入口是**一个人工动作、且要填复核人与资质**（`POST /admin/ai/knowledge-entries/{code}/review`），
  其余运营接口仍然碰不到 `review_status`——「不许假造」防的是自动置位，不是禁止记录人工复核。

## 三、实时通道（挡 [#85](https://github.com/QIUZI-HONG/pet-health/issues/85) → #109）

- **轮询优先**：消息列表、未读角标、订单状态一律轮询（消息中心的惰性补算机制天然适配，见 [ADR-0019](0019-reminder-system.md)）。轮询周期进配置。
- **WebSocket 后置**，且**必须保留轮询兜底**（同一条数据两条通道取一，不允许只有 WS 一条路）。将来做 WS 时的两个落点是**订单状态变化**与**邀请进度**。
- 不做多实例广播（要引入 Redis pub/sub）：当前没有任何一处交互非实时不可，成本高于收益。

## 四、三道照片墙（挡 [#87](https://github.com/QIUZI-HONG/pet-health/issues/87) / [#92](https://github.com/QIUZI-HONG/pet-health/issues/92) → #107）

- **三个槽位**：接宠检查 / 服务防护 / 取宠对比。订单进入「履约中」（[ADR-0038](0038-order-redeem-rights-points.md)）后开放。
- 每槽位可多张照片 + 备注，复用 [#95](https://github.com/QIUZI-HONG/pet-health/issues/95) 的预签名直传；照片 `biz_type=care`、**归属订单**。
- **硬约束落在服务端**：三个槽位都至少有一张照片才允许报工。**前端禁用按钮不算数**——这是交付文档 2.5 的验收标准（「缺一道则系统拒绝报工」），必须由后端拒绝。
- **与用户档案照片分开**（[ADR-0030](0030-archive-sections.md)）：服务留痕照片不进用户的档案照片墙。
- **取宠对比只做左右并排展示，不做自动图像对比**：我们没有图像比对能力，不假装有（「毛发更亮/体重+0.1kg」这类自动结论要等真正的能力，属于待澄清）。

## Consequences

- 交付文档 4.16.4 的「AI 周报卡」名称与实现不符，界面文案按上改（要与验收方说明一处偏离）。
- 报工接口会因照片不全而拒绝，它服务的界面必须把「缺哪一道」说清楚（不能只说「报工失败」）。
- 实时通道后置意味着 P011（订单详情）与 P017（邀请进度）在首期是轮询刷新；文档里「实时更新」的措辞要按此理解。
