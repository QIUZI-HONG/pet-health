# 文件读地址的两种口径：自己的文件按上传者过滤，业务归属在别处的由调用方自校

上位决策是 [ADR-0020](0020-file-storage.md)（文件默认私有、第六节「读图必过归属校验」、
第五节 `role` 字段、第七节「拍照 → 拷到电脑 → 批量上传」）、
[ADR-0040](0040-reports-kb-citations-realtime-photo-wall.md) 第四节（三道照片墙）、
[ADR-0006](0006-modular-monolith.md)（别的模块不碰 `file_object` 表）。
**本 ADR 只把「谁来做归属校验」这件事定下来，并收窄 ADR-0020 第六节的措辞；不改它的任何其他结论。**

落地位置：`server/ph-file/src/main/java/com/pethealth/file/api/`（两个端口）、
`.../file/service/FileService.java`（`FileUrlApi` / `FileQueryApi` 的实现）、
`.../file/web/ProviderFileController.java`（服务者侧的入口白名单）；
调用方在 `ph-order`（照片墙）与 `ph-provider`（资质材料）。

## 背景：ADR-0020 第六节那句话在三种场景里不够用

ADR-0020 第六节写的是「读图必过归属校验（别人的文件按不存在处理，40400）」。这句话对
**上传者就是读者**的场景是对的，也一直这么实现着：

| 场景 | 上传者 | 读者 | 上传者 = 读者？ |
| --- | --- | --- | --- |
| 打卡 / 疫苗本 / AI 咨询的图 | 宠物主人 | 同一个宠物主人（以及他触发的 AI 咨询） | ✅ |
| 三道照片墙（接宠检查 / 服务防护 / 取宠对比） | 服务者（履约中上传） | 门店后台 **和** 宠物主人 | ❌ |
| 资质材料图（营业证照、医师资格） | 门店管理员账号 | 门店自己 **和** 平台的审核员 | ❌ |

后两行如果照字面执行 ADR-0020 第六节，功能直接不可用：审核员不是上传者，看不到材料就没法审核；
宠物主人不是上传者，看不到接宠照片，三道照片墙就只剩下「服务者自己看」。

## 决定

**一、两个端口，口径不同，按场景选，不新造第三个。**

- `FileUrlApi.readUrls(userId, fileIds)`：**按上传者过滤**，只返回属于该用户、已落定的文件。
  用于「上传者就是读者」的场景（当前调用方是 ph-ai 取用户上传的图）。
  C 端的 `GET /files/{id}` 与它同一口径。
- `FileQueryApi`：**按 id 集合取元数据与签名读地址，不按上传者过滤**。用于「业务归属在别处」的场景
  （照片墙、资质材料）。

**二、归属校验的责任在业务侧，且调用方必须先做完再调。** `FileQueryApi` 的契约是：
调用方自己判完「这张图该不该给这个身份看」（订单归属与订单状态、门店归属与审核权限），
文件模块只负责给元数据与短时读地址。**因此这个端口只有读能力，没有批量删除、没有状态变更**——
能写的能力一概不给，越权面收敛到「看到了不该看的图」，不会变成「删了不该删的图」。

**三、签名读地址一律当场签发、不落库。** 库里存的是 `file_id`（V42 的资质材料列就是 `file_id`），
地址是短时链接，存库等于存死链；AI 服务拿到的也是后端当场签发的地址（ADR-0020 第一节的 `presign` 形态）。

**四、资质材料必带图。** `fileId` 必填——图是审核的依据，没有图审核员无从判断。
连带后果是测试里「造一份材料」必须先真的传一张图（`TestUploads` 就是为这条存在的）。

**五、服务者侧还有一层入口白名单，它与文件域的取值表不是一回事。**
`ProviderFileController` 的 `ALLOWED_BIZ_TYPES = care | qualification` 是「**门店的手能传什么**」的判定；
`FileService` 里的六项取值表是「**文件域的合法用途**」表（还包含 `checkin` / `epidemic` / `profile` /
`ai_consult`）。两层都要有：前者收窄服务者域的能力，后者保证用途字段可查。

## Consequences

**好的部分**：照片墙与资质材料都能跨身份读；文件模块不提供写能力，越权面窄；
换 `cos` 驱动时前端与调用方都不用改（拿到的永远是 `file_id` 与短时地址）。

**代价（明确记下）**：`FileQueryApi` 把归属校验推给了每个调用方——**漏一处就是一处越权**。
当前的缓解是「调用点少且都有测试」（ph-order 照片墙、ph-provider 资质材料）；
**没做**的是把「调用方必须先校验」变成结构护栏（例如让端口接收一个「已校验凭据」而不是裸 id 集合）。
这一步等第三个调用方出现时再做——两个调用点还看不出护栏该长什么样。

**与 ADR-0020 第六节的关系**：那句话在「上传者 = 读者」的场景继续成立（`FileUrlApi` 与
C 端 `/files/{id}` 都按它实现）；照片墙与资质材料属于「业务归属在别处」，归属校验由业务模块承担。
**ADR-0020 第六节的措辞按本条收窄**，其余各节不受影响。

**已知欠账（本轮评估发现，见缺陷计划 D-04）**：服务者提交资质材料时只校了 `fileId` 非空，
**没有校验这个 `file_id` 是本人上传的、也没有校验 `biz_type`**——按本条第二节，
这本该是调用方（ph-provider）的责任。这一处要补上，补法是：提交时校验「文件属于提交人 +
用途是 `qualification`」。写进这条 ADR 是为了让它有出处，而不是只停留在代码注释里。
