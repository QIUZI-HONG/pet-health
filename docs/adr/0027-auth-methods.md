# 认证方式只有手机号 + 密码：不做短信验证码，不做微信登录

C 端登录**只有一种**：手机号 + 密码（bcrypt）。不做短信验证码登录，不做微信登录。
将来接入任何并列方式都不推翻密码这条。

## Considered Options

**微信登录**（交付文档 F001 明确要求，7.2 的 `openid_wx` / `unionid` 就是为它留的）

- 需要微信开放平台的**网站应用**：三个端全 Web 之后（[ADR-0001](0001-all-web-clients.md)）没有小程序 JSAPI 可用，而网站应用要企业主体、要审核、要备案域名。
- 需要新增 `openid` 列与「一个手机号两种身份」的合并规则（微信号与手机号可能是同一个人，也可能不是）。
- 现状：`V1__account_user.sql` 建表时已经把这两列去掉并写明了理由（ADR-0001），**这条决策早已生效，本 ADR 只是把它显式化**——它此前只存在于一条迁移注释里。

**短信验证码登录**（交付文档 6.3「无密码体系（验证码登录）」+ F001「手机号验证码」）

- 需要短信服务商：选型、签名与模板报备、按条计费、通道被刷的成本风险。
- **在没有密钥的环境里不可测**：CI 与本地都发不出真短信，于是要么把整条登录路径做成桩，要么这条路径永远没有实测依据。
- 反过来说，一旦有短信通道，它同时解决的是「忘记密码怎么找回」——所以它是**两个需求**的共同前提，不是登录这一件事。

**手机号 + 密码**（选它）

- 零外部依赖，本地与 CI 都能真跑（`AccountFlowTest` 打的就是真实 bcrypt 校验与真实 Redis 会话）。
- 用户故事 1 的原话是「手机号**或账号密码**注册登录」，密码这条在规格之内。
- 与 [ADR-0012](0012-auth-and-session.md) 已定的令牌体系（JWT + Redis Refresh、三个登录域互不通用）完全兼容。

## Consequences

- **没有自助找回密码的路径。** 没有短信通道，忘记密码的用户只能走人工。这是本条接受的主要代价，也是将来接短信时最先受益的一项——**接短信的动机是找回密码，不是登录**，届时验证码登录作为并列方式一起上。
- 交付文档 2.4 与 6.3 里「验证码 1 分钟 1 次、1 天 10 次」的限流指标暂时**没有适用对象**。账号相关接口的限流改由 [ADR-0028](0028-security-baseline.md) 统一覆盖（按 IP 与主体计数），不照搬这两个数字。
- `RegisterRequest.password` 的强度规则（8–32 位、同时含字母与数字）成为**唯一**的账号安全边界，所以它必须一直有校验（现在在 DTO 的 Bean Validation 上）。
- 规格 #93 里「或账号密码」的措辞与交付文档 F001 的「验证码/微信登录」不一致——**以本 ADR 为准**，F001 的三种方式里只落一种。
