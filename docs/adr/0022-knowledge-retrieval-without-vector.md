# 知识检索先做关键词与关系层，向量层挂起

[#100](https://github.com/QIUZI-HONG/pet-health/issues/100) 的验收标准写着「向量检索走 Redis 8 Query Engine」，而 [ADR-0017](0017-model-provider-deepseek.md) 已经记下当前供应商**没有** `/embeddings` 端点（实测 404）。也就是说那一层**没有可用的嵌入模型来源**，而且这件事没有票。本票决定它怎么办。

## 决定

**向量层挂起，先把 L1 + L2 + L3 的另外两条腿做完。**

| 层 | 本期做法 | 状态 |
| --- | --- | --- |
| L1 结构化事实 | MySQL 表 + 代码规则，**不走检索** | 已开始（`knowledge_red_flag`，切片 #98） |
| L2 关系层 | 节点表 + 边表（症状→疾病→药物），人工审核 | #100 做 |
| L3 文本检索 | **MySQL 8.4 `FULLTEXT ... WITH PARSER ngram`**（中文子串已实测可用） | #100 做 |
| L3 向量检索 | **留接口不实现**：`kb_chunk` 仍建（含 `embedding_model` 列），检索侧不回落到向量 | 挂起 |

**#100 的验收标准据此改一条**：原文「中文子串检索走 MySQL ngram；向量检索走 Redis 8 Query Engine」→ 改为「中文子串检索走 MySQL ngram；L2 关系查询与 L1 结构化查询各有一条测试；**向量层留接口，不实现**」。另开一张决策票记「嵌入模型供应商」这件事（本 ADR 不预先批准任何供应商）。

## 依据

- **本地只有一个供应商的凭据**：`ai/.env` 共 9 个键，无任何 embedding / ASR 变量（2026-09-28 核查）。
- **ADR-0017 的两条实测**：`/embeddings → 404`、`知识检索的向量层缺位`。
- **63 号调研已把切换路径论证清楚**：Redis 8 Query Engine + FLAT/FLOAT32/COSINE 是对的基础设施（镜像里 `search` / `vectorset` 已实测可用）；嵌入首选百炼 1024 维，备选 `bge-m3` 同为 1024 维、**可平滑切换**；代价是「换模型 = 全量重建，含 Redis 索引 drop/rebuild」。这些结论**不因挂起而失效**——将来接上时按它执行即可。

## Considered Options

**加一个云嵌入供应商**（63 号调研的首选）。多一个 key、按量计费、语料出本地；而且它会**先于**语料量存在——现在连一条知识条目都还没有，为一个不存在的语料库先付一份订阅与一份数据出境评估，不划算。

**自托管 bge-m3**。免费、语料不出本地，但与 [ADR-0003](0003-lean-middleware.md)「精简中间件」的取向冲突：它意味着一个常驻的推理进程（内存 + CPU 推理延迟），换来的召回增益在几百条语料的规模上无法证明。

**先上向量、临时用哈希/随机向量占位**。绝对不做：那会让检索看起来能用、实际是噪声，比没有更危险——尤其这是医疗场景。

## Consequences

**召回弱在哪些地方是明确的、可观测的**：关键词检索覆盖不了「换一种说法」（用户说「不吃东西」，条目写「食欲下降」）。缓解手段有两个：L2 关系表承担「症状→疾病」这类结构化召回（它本来就比向量更可解释），以及词表/同义词在 L1、L2 里多写变体（`knowledge_red_flag.variants` 已是这个模式）。

**重开条件写死在票上**（不是「以后再说」）：语料超过约 5000 条，或出现至少三个**记录在案**的召回缺口实例（用户提问 → 关键词全都召不到 → 人工补齐后能召到）。到那时按 63 号调研的选型接，基础设施不用换。

**#101（接入真知识库）不受阻**：它的验收标准是「来源可追溯 / 空召回不生成 / 越界句剔除 / 违规推荐硬过滤」，这四条都建立在「召回到的条目」上，与召回用关键词还是向量无关。
