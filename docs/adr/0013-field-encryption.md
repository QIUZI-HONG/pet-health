# 敏感字段加密存密文 + 另存 HMAC 查找列

交付文档 6.3 要求「手机号 / 身份证 / 病历 字段级加密（AES-256）」，但没给做法。本 ADR 定做法：**密文用 AES-256-GCM（每条记录随机 IV），需要等值查询的字段另存一列 HMAC-SHA256 摘要**，两把密钥都从环境变量读。首期落地在 `user.phone`；身份证（服务者资质，[#104](https://github.com/QIUZI-HONG/pet-health/issues/104)）与病历（[#90](https://github.com/QIUZI-HONG/pet-health/issues/90)）落地时照同一套办法。

## Considered Options

- **明文字段 + 数据库透明加密（TDE）**：改动最小，手机号还能直接 `LIKE`。但 TDE 只防「偷走磁盘文件」，防不了「拿到库账号」——而交付文档的验收要求是字段级。
- **只用哈希（不可逆）**：手机号是**要回显、要发短信**的业务数据，不是密码，哈希存了就取不出来，不可行。
- **AES-ECB / 固定 IV（可直接等值查询）**：省掉哈希列，但固定 IV 让相同明文产生相同密文，等于把「哪些用户同号」暴露在密文里，且 ECB 本身是已知弱点。排除。
- **AES-GCM + 另存 HMAC 查找列**（本决策）：密文不可比的代价，换来「同一手机号只可能有一个账号」的约束仍然成立（唯一索引建在 HMAC 列上）。

## Consequences

**写路径：** 明文只在内存里出现；入库前 `phone_enc = 加密(phone)`、`phone_hash = HMAC(phone)`。**读路径：** 按手机号查用户走 `phone_hash = HMAC(输入)`，拿到行再解密回显。

**接口一律返回脱敏值**（`138****8888`，见 `docs/conventions.md`）。解密只发生在服务端需要真值的场景（发短信、导出用户自己的数据），不经过任何列表接口。

**能做到 / 做不到，先说清楚：**

| 查询 | 是否可行 | 说明 |
| --- | --- | --- |
| 等值（按手机号找用户、登录、查重） | ✅ | 走 `phone_hash` |
| 唯一约束 | ✅ | 建在 `phone_hash` 上 |
| 排序、范围、`LIKE` 模糊搜索、`GROUP BY` 原值 | ❌ | 密文没有保序性。所以**运营后台不提供手机号模糊搜索**，要查人先拿 userId 或订单号 |
| 全量导出后离线分析 | ❌ | 同上，需要真值时走应用层解密，且必须有审计 |

**密钥管理与轮换：** `FIELD_ENC_KEY` / `FIELD_HMAC_KEY`（各 base64 的 32 字节）只进本地 `.env`，不进库、不进 git、不贴进对话。密文带版本前缀 `v1:`——换密钥时新写入用新密钥，解密先试当前密钥、再试 `FIELD_ENC_KEY_PREVIOUS`，老数据在下次写入时自然迁移。**HMAC 列换密钥必须走迁移脚本全量重算**（它要参与唯一索引，不能双写共存），所以 HMAC 密钥的轮换当成一次正式的数据库变更来做。

**这里偏离了交付文档的 DDL 一处**：文档 7.2 的 `user` 表是 `phone VARCHAR(20) UNIQUE`。按本 ADR，`phone` 明文字段不存在，改成 `phone_enc`（密文）+ `phone_hash`（查找列，唯一索引）。这是文档没给做法、只给了要求的地方，按 ADR 补，不是推翻文档。

**AES-GCM 的完整性顺带解决一件事：** 密文被篡改时解密会失败而不是解出垃圾，所以不需要额外的校验列。
