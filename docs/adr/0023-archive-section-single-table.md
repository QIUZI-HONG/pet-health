# 档案分项用一张表：archive_record + structured_payload

交付文档 F004 要求档案有 8 个分项（核心指标 / 证件与合规 / 行为 / 情绪 / 卫生 / 饮食 / 老年专项 / 照片视频），加上就医记录这条时间轴来源。「每个分项怎么落表」决定 [#102](https://github.com/QIUZI-HONG/pet-health/issues/102) 与 [#115](https://github.com/QIUZI-HONG/pet-health/issues/115) 能不能开工。

## 决定

**沿用 `archive_record` 一张表**，靠 `category` 细分 + `structured_payload`（JSON）承载各分项的差异字段。**不为 8 个分项建 8 张表。**

三条配套口径：

1. **时间轴是这张表的视图，不是另一份数据**：就医、疫苗、打卡、服务报工都已经是 `archive_record` 的行，按 `record_date` 排序即时间轴。多一张「时间轴表」等于多一处双写不一致。
2. **照片视频分项引用 `file_object`**（切片 #95），不把 URL 抄进 `archive_record`——抄一份就多一份要跟着删的副本。
3. **来源标注落在 `source` 上**（1 用户 / 2 AI / 3 服务者报工），这是 F004「三源写入」的落点，已有列。

## Considered Options

**高频分项独立子表**（体重/饮食/行为/卫生各一张）。字段强约束、单表查询快；但 8 张表会把「统一时间轴」变成跨表 union，而**时间轴正是档案页的主角**（交付文档 4.16.4 画的就是一条时间线）。用弱约束换统一读路径，在这个页面上是划算的。

**先只做 4 个高频分项**。会与交付文档 F004 的验收标准打架，而且「照片视频」其实已被 #95 的照片上传覆盖了一半——留着占位自相矛盾。

**EAV（一行一字段）**。灵活到没有约束，查询与校验都要靠代码兜底，是这类「字段已知、数量固定」场景的反面教材。

## Consequences

**代价是字段约束弱**：`structured_payload` 里的结构不由数据库保证，所以每个分项的字段与必填必须在 **#90（档案分项字段设计）** 里逐项定稿，并由代码 + 校验守住；迁移只保证通用列（`category` / `record_date` / `source` / `due_on` / `numeric_value`）的约束。

**分项与评分维度是两个词，不要混**：档案的 8 个叫「分项」，健康评分的 5 个叫「维度」（生理/行为/卫生/防疫/老年，代码里已是 `HealthScoreDimension`）。两者不同构、也不一一对应——评分维度是**算出来的**，档案分项是**录进去的**。这条已写进 `CONTEXT.md`。
