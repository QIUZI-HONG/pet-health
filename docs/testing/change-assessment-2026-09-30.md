## 1. 执行摘要

**结论：有条件通过——新版四项要求在当前工作区已完成约七成，但「已完成」里有 1 处硬伤、4 处真空白、3 处过程风险。**

**建议按新版推进，且按「先收口、再补缺、最后做套餐」的顺序。**

| 维度 | 结论 |
| --- | --- |
| 服务者端标准化与券体系 | ✅ 联盟分类（V43）、标准目录与区间价、券池、邀请码、考核**基本落地**；❌ 但考核→推荐优先级的**写回那一环没写**（§4.4），被邀请人得券、券自动选优未做 |
| 前端五套视觉稿 | 🟡 **色与 token 已对齐，信息架构按 ADR-0016 走桌面重排**（这是既定偏离，不是缺陷）；五页各有 1–3 个区块缺项（§3）；窄屏（420px）下页面**不可用**（§3.7） |
| 知识库 | ✅ 三层检索（L1/L2/L3）**真的都在跑**，红线短路 + 分级 + 护栏齐；设计文档 `docs/design/knowledge-base.md` 已在库。⚠️ 40 条种子知识全是 `pending_review`，**AI 引用恒为空**（这是数据问题，不是代码） |
| 补全专项 | ✅ 流量平衡（排序层）、三道照片墙、社区与积分（本就完成）；❌ 组合套餐、成本测算、营销中心物料/活动、区域**排他**保护 |
| 技师端合并 | ✅ 已按约束裁剪：不开发小程序，口径并入服务者后台 `/b/standard`（服务标准） |
| 拍照流程 | ✅ 已是「先存电脑再上传」（presign + 直传，ADR-0020） |

**关键风险（三条，按严重度）**

1. **考核写回缺一环，且被两份文档与一处测试注释共同掩盖**：`AssessmentService#writeBackToProvider` 只写 `level` 与 `monthly_score`，**没有写 `recommend_priority`**；而 V45 迁移注释、第五轮报告 §2.3 都声称「与 level/monthly_score 同一处写回」，新增的 `ProviderTrafficBalanceTest` 则用**直接改库**绕过这一段。后果：交付文档 F022「等级决定 AI 推荐优先级」仍然没闭环，运营改档位映射不会影响排序。（详见 §4.4）
2. **88 个文件未提交、两份报告未入库、文档指针过期**：`AGENTS.md` 仍说「第四轮是当前有效清单」，但磁盘上已有第五轮；`docs/adr/` 只到 0052，**却有 32 处引用 ADR-0053**（含迁移与生产代码）。任何人（或 AI）按仓库文档开工，都会拿到一份过期的现状认知。
3. **视觉验收口径先天不成立**：视觉稿是手机竖屏（420×836 + 底部 5 Tab），实现是桌面 Web（左栏 208px，ADR-0016）。文档那条「截图对比须肉眼无差异」是按手机版式写的，**在桌面重排下无法通过**。这不是本轮能改的，需要产品级确认（C 端是否改手机版式），或者把验收口径正式改写为「色值与设计语言一致 + 区块齐」。

**总工作量估算：约 36 人天**（P0 6.5 / P1 26.5 / P2 3），三人并行约 3 周，单人约 7–8 周。明细见 §5、§6。

### 4.4 ⚠️ 硬伤：考核 → 推荐优先级的写回**没有实现**

**事实**（可直接复核）：

```
server/ph-provider/.../service/AssessmentService.java:478  writeBackToProvider(...)
    provider.setLevel(score.getLevel());
    provider.setMonthlyScore(score.getTotalScore());
    providerMapper.updateById(provider);       ← 到此为止，没有 setRecommendPriority
```

全仓 `recommendPriority` 的写点只有两处：① `AssessmentService:216`——运营保存**档位映射表**（`assessment_level_rule`）；② V45 迁移里的一次性回填。**没有任何代码把档位映射的结果搬到 `provider.recommend_priority`。**

**而三处文档都声称已闭环**：

- V45 迁移注释：「把优先级落到 provider 上（**与 level / monthly_score 同一处写回、同一套规则**）」「回填只做一次，之后**由考核写回维护**」；
- 第五轮报告 §2.3：「`provider.recommend_priority`（非空，默认 3），**由考核写回**（`AssessmentService.writeBackToProvider`）」「运营改映射**当场生效**」；
- `ProviderTrafficBalanceTest` 类注释：「排序读的是 `recommend_priority`——**改档位映射立刻影响顺序**」，但用例正文用的是 `jdbc.update("UPDATE provider SET recommend_priority=1 …")`，注释自己承认是「直接改库模拟『考核写回 + 运营改过档位映射』的结果」。

**后果**：排序确实改读 `recommend_priority` 了（这一半是真的），但那一列**上线后不会再变**——运营改档位映射不影响任何东西，交付文档 F022 的「等级决定 AI 推荐优先级 / 流量加权」仍是断的，只是断点从「排序读错列」挪到了「那列没人写」。

**修法**（约 1 人天，含测试）：在 `writeBackToProvider` 里按 `level` 查 `assessment_level_rule` 取 `recommendPriority` 写入；把 `ProviderTrafficBalanceTest` 改成**走真实考核路径**再断言排序；顺手给「只改 level 不改档位映射」补一条反向断言。
