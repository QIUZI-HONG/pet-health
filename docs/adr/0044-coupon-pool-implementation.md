# 券池的实现口径：额度算法、并发防护、成本归属只进统计

实现 [ADR-0037](0037-roles-console-boundary-coupon-pool.md) 第三节（三层对象与额度口径）与
[ADR-0036](0036-money-semantics-offline.md)（钱在门店付）的服务者侧与运营侧切片（#110）。
契约在 `contract/provider.yaml` 与 `contract/admin.yaml`，代码在 `ph-privilege`，迁移 V24。

本文只写**实现决策**——对象定义、谁创建、不做什么，都在 ADR-0037 里，不重复。

## 一、额度是一个算法，不是一个字段（决定）

```
可发放 available = total_count − 已核销 − 占用中
占用中 reserved  = 已发放、未核销、**未过期**（含下单锁定的）
已过期 expired   = 已发放、未核销、**已过期**      → 这部分释放额度回池
对账  issued = redeemed + reserved + expired
```

- 唯一的实现是 `CouponQuota`（一处），所有读写额度的路径都走它：承诺 / 调额 / 撤回 / 发券 /
  过期释放 / 列表展示。
- **不存 `available_count` 列**：存了就要在四个地方同步它（发放、核销、过期、调额），
  而它一旦漂移，「超发」与「发不出去」都不会报错——两种事故都不报错，是最坏的一类 bug。
- 「占用中」**按 `valid_until` 判**，不只看状态列：过期由每日批算翻状态，
  批算与读取之间有窗口；按时间判，窗口里也不会有人占着服务者的额度。

## 二、过期释放不依赖定时任务（决定）

一张券过期的那一刻，额度就应该回来了。所以**可发放额度是读时算出来的**，
批算（`CouponExpiryJob`，每天 01:10）只做两件事：把状态翻成「已过期」、记一条额度释放流水
（`actor_id=0`）。

**否决「批算里做释放」**：那等于把「额度正确」押在一个可能没跑、可能延迟、可能失败的
定时任务上，而它的失效方式恰好是最难发现的——服务者看到额度没回来，运维查不出原因。

## 三、不超发靠锁「一条贡献」+ 实时算（决定）

发券流程在一个事务里：

1. 服务者成本券：`SELECT * FROM coupon_contribution WHERE id = ? FOR UPDATE` 锁住那条贡献
   （按贡献 id 升序取第一条还有余量的，见下），再算余量；余量为 0 → 40900。
2. 平台补贴券：没有服务者额度，但有 `issue_limit`（发放上限），同样在事务里判。

**锁粒度是「服务者 × 模板」的一条记录**，不是整张表：不同服务者的发券互不影响，
所以本项目不需要分布式锁就能做对这件事。

**并发正确还需要一件事：事务隔离级别取 READ COMMITTED**（本切片的实测结论，不是理论推导）。

额度是「读出来的」（已核销 + 占用中），所以这些读必须看到**最新已提交**的数据，
再配上持有的行锁，串行关系才成立。MySQL 默认的 REPEATABLE READ 下，事务第一次一致性读
就定了快照，于是「先读模板 → 再锁贡献 → 再数券」会数到别人还没提交的那一版：
16 个并发请求对一条「承诺 5 张」的贡献发放，**14 个成功**（用例
`CouponQuotaTest.concurrentIssueNeverExceedsQuota` 就是这么红起来的，修完是 5 成功 11 个 40900）。

两处配套的写法，改动时别拆开：

- 发放的**第一条 SQL 是加锁读**（`SELECT ... FOR UPDATE` 取模板行，再取贡献行）：
  加锁读不建立快照，后面的计数自然读的是最新已提交的数据。顺带它也是平台补贴券
  发放上限（`issue_limit`）唯一的闸——那条路径没有贡献行可锁；
- 核销的失败分类也依赖它：条件更新没改到行时要回读「此刻的状态」才能区分
  「刚被别人核销」（80002）与「真的不可用」（80001），在 REPEATABLE READ 下回读会命在旧快照上，
  并发双击的败者会拿到 80001——错的分类，也是实测出来的。

**否决的选项**：

- **先查后写（check-then-act）**：两个并发请求同时读到「还剩 1 张」，各发一张——必超发。
  这是这一节存在的全部理由；
- **给贡献加一个 `issued_count` 计数列 + 乐观锁**：核销与过期都不改 `issued_count`，
  版本号会被无关的写放大成冲突，重试率不可控；而真正要判的
  「已核销 + 占用中」还是得从券表上数出来；
- **把额度算到内存里（查全量券再过滤）**：券会越积越多（过期的也留着参与对账），
  在真实体量上不成立。
- **在 `coupon_contribution` 上存 `issued_count` 并做乐观锁**：多一个需要同步的字段，
  而且核销 / 过期都不改 `issued_count`，乐观锁的版本号会被无关的写放大成冲突，重试率不可控；
- **数据库 CHECK 约束**：跨行（券数 ≤ 贡献额度）的约束在 MySQL 里要靠触发器，
  而触发器在回滚脚本、迁移审计里都是负担；应用层锁行 + 实时算已经够，且可测。

## 四、多个服务者都贡献同一种券时，按「先承诺先消耗」（决定）

平台的券池可能有 N 家服务者贡献了同一个模板。发券时按**贡献 id 升序**挑第一条还有余量的
（`pickContribution`）。选它的理由只有一条：**可预期**——服务者能估算自己的额度大概什么时候
用完，而随机分摊 / 按余量比例分摊都让这件事变得不可预测，服务者也就没法规划。

代价要写清楚：这是**服务者侧的公平**，不是用户侧的体验最优。见「待澄清」第 2 条。

## 五、成本归属只进统计，不产生任何资金（决定，照抄 ADR-0036 的口径）

- `cost_bearer`（1 服务者成本 / 2 平台补贴）在本切片只影响三处：**券池总览的拆分**、
  **服务者的核销统计与完成率**（考核「券」那一项的数据口径，ADR-0039 第三节）、
  **兑换与阶梯只能配平台补贴券**（ADR-0038 第四节）。
- 代码里没有任何余额、结算、打款、退款字段与接口。券只是**到店抵扣凭证**。
- 核销 ≠ 收款：核销接口（`CouponApi.redeem`）只把券转成「已核销」，
  不动金额、不记收款。
- 对账退化为**券的账**：`GET /admin/coupon-pool/overview` 的 `reconciliation`
  给出 `instances = issued = redeemed + reserved + expired` 与 `balanced`，
  不平即告警（没有资金流可对，这是唯一能对的东西）。

## 六、券实例存快照，模板改动不影响已发出的券（决定）

`coupon` 表自己存 `face_value` / `min_amount` / `scope_type` / `scope_codes`，
发放时从模板抄一份。

**与 `provider_service` 不存目录快照的取舍正好相反**，两者都刻意：目录项要的是
「目录只有一个真相」（改名后所有页面一起变），券要的是「发出去的就是承诺」
（用户手里的券不能因为运营改了模板面额而变值）。判断标准是**这份数据是平台的配置，
还是平台对用户已经作出的承诺**。

## 七、券的来源五种，第五种是月度阶梯（决定）

ADR-0037 说来源四种（邀请 / 打卡任务 / 积分兑换 / 平台补贴）。F018 的月度阶梯券
另立 `source=5`，理由：它的触发路径与前四种都不同（按上月积分累计自动发），
硬塞进「积分兑换」会让对账与排查看不清券从哪来。**四种是底线不是上限**（见「待澄清」第 3 条）。

## 八、收口点与可追溯

- 额度变动**全部**有流水：`coupon_contribution_log`（append-only：承诺 / 调整 / 撤回 / 过期释放，
  每条带动作后的承诺额度与可发放额度）。发放与核销不在这里——它们在 `coupon` 那一行上
  已经留了痕（`issued_at` / `redeemed_at` / `redeemed_by`），记两遍会让「哪一份是真的」变成问题；
- 券码是 12 位、去掉易混字符（0/O、1/I/L），**不是安全凭证**（ADR-0038 第二节的口径）；
  服务者侧看不到领券人身份，只有 `user_id`。

## 需要协调（不是待澄清，是接线）

**服务者侧接口需要「登录账号 → 服务者」的解析，而 ph-provider 没有暴露 api 接口。**

ADR-0006 禁止跨模块碰别人的表，本仓的既有形态是「跨模块只走对方的 `api` 包」
（`CatalogQueryApi`、`AiPetApi`、`FileUrlApi`…）。`provider_user` 的解析在 ph-provider 的
`ProviderAccess` 里，但那个类在 `service` 包，不能跨模块用。

本切片的做法：在 **ph-api** 加一个只读接口 `com.pethealth.api.provider.ProviderAccessApi`
（三个方法：`findProviderId` / `isAdmin` / `providerNames`，理由与 `AiConsultStatsApi` 同一处位置调整），
ph-privilege 经它取身份。**实现要由 ph-provider 补一个适配器**（约 12 行）：

```java
@Component
public class ProviderAccessAdapter implements ProviderAccessApi {
    private final ProviderAccess access;        // 现有的组件
    private final ProviderMapper mapper;        // 现有的 mapper
    // findProviderId → access.findBound(userId) == null ? empty() : of(provider.getId())
    // isAdmin        → access.findBound(userId) 的 ProviderUser 角色是 ROLE_ADMIN 且绑定启用
    // providerNames  → mapper.selectBatchIds(ids) 收成 id → name
}
```

在它落地之前：服务者侧的券接口会回 **50300「服务者身份解析尚未接线」**（而不是静默按
「没有门店」处理——后者会让服务者以为自己的门店不存在，那是查不出来的错）；
集成测试里用了一个等价的 stub（`PrivilegeTestSupport.StubProviderAccess`，读同一批表）。
`GET /admin/coupons` 的门店名在未接线时为空，不影响其余字段。

## 待澄清（需要甲方拍板）

1. **贡献额度的分配规则**：现在按「先承诺先消耗」。如果平台希望 N 家店的券大致均摊，
   就得换成按余量比例分摊或运营指定——那是产品选择，不是技术选择（第四节）。
   它还牵动一件用户可见的事：**服务者贡献的券只能在其本店核销**（ADR-0037），
   所以用户拿到的是一张「某某店的券」，而不是一张「任意店可用」的券；
2. **平台补贴券是否限一人一张**：本期运营手动发放**不做隐式去重**（重复发放是看得见的动作）。
   若要做「一人一券」，需要一个新的判据（按模板 + 用户），属 #121 的反刷范围；
3. **`source=5`（月度阶梯）要不要并回四类**：如果验收方要求「券的来源必须是四种」，
   把月度阶梯券标成「平台补贴」即可（成本归属本来就归平台），代价是对账里看不出
   「这是规则发的还是运营发的」；
4. **券码是否需要防转发**：核销码在订单上（6 位、到预约时间才可见，ADR-0038），
   券码只是排查用的标识。如果要防截图转发，那是订单凭证的设计问题，不是券的问题。

## Consequences

- 服务者后台的「营销中心」按交付文档做不了（没有余额与提现），退化为**券与推广码**；
  本切片给的是券那一半（贡献额度、核销统计、明细），推广码属邀请侧（C 端下一波）。
- 券池的模板与贡献都**不做物理删除**：模板停用只挡新的发放与新的贡献，
  贡献撤回只收回未发放的额度——已经发到用户手里的券照常有效。
- 考核（#58）现在拿得到「贡献额度完成率 × 核销数」这两个数（`completion_rate` 与
  `redeemed_count`），但**考核本身不在本切片**，本切片只提供口径。
