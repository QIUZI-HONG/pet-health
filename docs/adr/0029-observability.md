# 可观测性：日志只做「可检索」，聚合与告警在部署层接

交付文档 10.6 要求监控、告警、日志聚合、健康检查、业务监控五项，6.4 要求无状态多实例部署。
[ADR-0003](0003-lean-middleware.md) 已经砍掉 ES（ELK 的 E 与 K），本条定剩下几件事：
**日志要长成什么样、指标有哪些、什么情况该告警、traceId 怎么贯穿三方**。

## Considered Options

### 日志聚合用什么

- **Loki + Promtail（或 Grafana Agent）**：多机聚合与按标签检索最顺，但要再多一个常驻组件与一块存储；
  [ADR-0003](0003-lean-middleware.md) 的精神与之相悖——它砍掉 ELK 正是为了不背这套运维量。
- **云厂商托管日志**：最省事，代价是费用与数据出境（宠物健康数据 + 手机号，合规上要另论，见 #74）。
- **只落日志 + 按 traceId 检索**（选它）：应用只负责把每行日志写成**可检索的样子**，
  采集与聚合留给部署层（#122）。单机阶段 `docker logs` / 文件 + `grep <traceId>` 就够用；
  要多机检索时**加 Loki 是纯加法**（不动应用代码），所以现在不选它并不锁死。

**关键区别**：这个选择能不能成立，取决于日志行**本身**带不带 traceId——
所以下面第 3 节那条不是补充说明，它是这个选择的前提。

### 指标暴露在哪

沿用它已有的形态：`management.server.port` 走**独立端口 9090**，不随业务端口一起暴露。
理由写在 `application.yml` 的注释里（原先挂在业务端口上时，无凭证 `curl /actuator/prometheus` 直接 200）。

### 告警阈值

交付文档 10.6 给了三个（错误率 >1%、P95 >1s、磁盘 >80%）。**不能照抄**：本项目 AI 咨询的
P95 实测 7.4 秒（模型延迟主导，ADR-0017 有数据），一条「P95 > 1s」的全局告警会被 AI 接口刷成
永久噪音，然后被所有人忽略——那比没有告警更糟。所以按路径拆开：

| 指标 | 阈值 | 窗口 | 为什么是这个值 |
| --- | --- | --- | --- |
| 非 AI 接口 P95 | > 1s | 5m | 交付文档 10.6 的原值；口径限定在「不经模型」的路径上 |
| AI 咨询 P95 | > 5s | 10m | 交付文档 1.6 的目标是 3s，但实测均值 3.9s / P95 7.4s（模型延迟主导）。5s 是「比现状继续恶化就叫」的触发线，不是目标线 |
| 5xx 错误率 | > 1% | 5m | 交付文档 10.6 的原值 |
| 应用存活 | `up == 0` | 1m | 容器存活探针的第二道 |
| 磁盘使用率 | > 80% | 5m | 交付文档 10.6 的原值 |
| **AI 降级率** | > 20% | 10m | 提示词改坏、模型静默换版、上游抖动的最早信号（留痕里 `degraded`） |
| **审计写入失败** | > 0 | 5m | 审计失败不阻断业务，**没有任何面向用户的症状**（ADR-0028），只有这个指标会说 |
| **限流拦截占比** | > 50% 且持续 10m | 10m | 要么被刷、要么阈值配错了。两条都得人看 |

规则清单落在 `deploy/prometheus/alerts.yml`。**注意它还没在真实 Alertmanager 上验证过**——
那要等 #122 把 Prometheus 与告警通道（企微/钉钉机器人）部署起来。在此之前这份文件是**声明**，不是**已生效的能力**。

**未做**：Grafana 面板（#121 的一部分，等有真实流量再按需画，先画面板容易画成没人看的墙）；
业务监控里的「支付成功率」（ADR-0002 不做线上收款，该指标不存在，不列）。

## Consequences

### 1) traceId 的透传约定（已经跑着的那套，写下来免得各改各的）

```
前端（可选带 X-Request-Id）
  → 后端 TraceIdFilter：取该头，缺省则生成；写入 MDC；响应头回带同一个值
  → 日志每一行都带它（见下）
  → 调 AI 服务：放进请求体的 trace_id 字段（HTTP 头也带，见 AiServiceClient）
  → Python 侧落日志 + 回带
  → 落库 ai_consult.trace_id
```

为什么不是「HTTP 头一路透传」就够：AI 服务是**独立进程**，它的日志与 Java 的日志要在事后能对上，
所以那个 id 必须进请求体（Java 侧 `ConsultRequest.traceId`），而不是只留在传输层的头上。

前端已经支持：`RequestOptions.traceId`（`packages/shared` 的请求层），不过**目前没有任何调用方用它**——
排查用户报错时手动带一个即可（请求层注释里也写了这点）。

### 2) 每行日志都必须带 traceId（本轮补的缺口，实测过）

改之前的状态是：**Spring Boot 默认日志格式不含 MDC**，而本仓没有 `logging` 配置，
于是「按 traceId 检索」只在那些手工把 `traceId=` 拼进消息的日志行上成立。
实测一次真实启动 + 若干请求：**451 行日志，0 行带 traceId**。

修法是两件（缺一不可）：

**其一，给 `logging.pattern.console` 加上 `%X{traceId:-}`**（见 `application.yml` 的 `logging` 段）。
于是新代码**不必**再把 traceId 拼进消息（老代码里那些 `traceId=` 保留也无害）。

**其二，加访问日志：每个业务请求一行**（`RequestLogFilter`，只记 `/api/` 路径）。
只做第一件还不够——实测发现本仓**大多数成功路径压根不打日志**：一次成功的 AI 咨询、
一次成功的读档案，在该 traceId 下命中 **0 行**。那么「按 traceId 追一次请求」照样无从下手，
只是从「所有行都不带 id」变成「带 id 的行太少」。

一行访问日志要能回答三件事：谁（`caller` 是 `u:<id>` 或 `ip:<addr>`）、做了什么（`method` + `path`）、
多慢（`duration_ms` + `status`）。超过 1 秒的非 AI 请求额外记一条 WARN——
AI 咨询天然慢（模型延迟主导），单独有阈值，别混进来。

**为什么不用 Tomcat 自带的 access log**：它只能写文件（没有 stdout 模式），
而容器化部署要的是「写 stdout 交给采集」。

于是那条日志聚合选择（只落日志 + 按 traceId 检索）从「设计意图」变成**实际可用**。

### 3) 谁负责什么

- **应用**：把日志写成可检索的样子（每行带 traceId）、把指标暴露在独立端口、健康检查。
- **部署层（#122）**：采集、聚合、面板、告警通道。这一层没做之前，第 2 节的告警清单是声明而非能力。
- **不在应用里做的事**：不为了可观测性引入新的常驻进程（ADR-0003）。
