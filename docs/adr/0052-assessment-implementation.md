## 一、权重与分档的落点是「一张单行规则表 + 一张三行档位表」

`assessment_rule`（**单行**，`id = 1`）存三项权重、三项达标线（拉新目标数 / 券目标值 / 接单响应分钟数）；
`assessment_level_rule` 存三档（基础 / 优选 / 战略）的**进入阈值**与 `recommend_priority`。
两张表都是 ADR-0010 分层里的**业务可调项**（入库 + 运营后台可改），算法与判据留在代码里。

三条取舍：

1. **单行而不是多方案**：规则是「当前生效的那一份」。多行会立刻引出「哪一行生效」这个必须回答的问题，
   而这一期没有 A/B 的需求。将来真要做灰度，改的是 `requireRule()` 一处（一个查最新启用的查询）。
2. **每次算分把权重与达标线快照进分表**（`assessment_monthly_score` 的权重列、
   `assessment_item_score.target_value`）：规则可改，而历史账期必须解释得清「当时为什么是这个分」。
   没有快照，运营改一次阈值，去年十二月的分就再也算不出来——ADR-0039 §三的「跨月可对比」也就没了依据。
   覆盖重算时用的也是**明细里的权重快照**（`AssessmentCalculator.recalcTotal`），不读当前规则。
3. **等级与 `recommend_priority` 是「存储的映射」**：本切片只保证「等级、优先级存得下来、查得到」
   （分表 + `provider.level` / `provider.monthly_score` 写回），**推荐排序本身不在本切片**（见待澄清第 2 条）。

**种子里有两个值是占位，必须点名**（都写在 `V34` 的注释里，运营随时可改）：
优选 80 分 / 战略 90 分（阈值 80/90 没有规则依据）、接单响应达标线 30 分钟。
**拉新与券的达标线种子里留 0（未配置）**——40/40/20 的权重来自交付文档，而「月拉新 5 人」这类目标是
产品决策，编一个就是替甲方拍板（与 ADR-0046 第五节「阶梯奖励物留空是有效状态」同一条纪律）。

## 二、缺项判据：「该做而没做」与「平台侧无该维度要求」各自数得出来

ADR-0050 §四只给了两种口径的名字与一个例子（有必出券目录 vs 该品类根本没有券可出），
**「无要求」怎么判定是本切片定的**。判据全部落在**平台侧的事实**上，每一条都对应一个可查的数：

| 维度 | 该做而没做 → **记 0 分**（`participated=true, score=0.00`） | 平台侧无该维度要求 → **不参与并重算权重**（`participated=false, score=null`） |
| --- | --- | --- |
| 拉新 | 平台给了拉新入口（有效邀请数回 `0` 而不是 `null`）→ 一条没有就是 0 分 | 规则里 `invite_target = 0`（没定要求）；或事实源说「这个服务者还没有拉新入口」（`null`） |
| 券 | 券池里有可贡献的券 + 规则配了 `coupon_target` → 一张没核销就是 0 分 | `coupon_target = 0.00`；或**券池里一张可贡献的服务者成本券都没有**（ADR-0050 举的例子正是它） |
| 过程·接单响应 | 有订单而一单未接（单量 > 0 而响应均值为 `null`）→ 0 分 | 期内一单都没有（没有可响应的对象） |
| 过程·核销率 / 报工完整率 / 取消率 | 有分母时的比例分（核销率低、报工不完整、取消多都直接扣分） | 分母为 0（没有可算的对象）——**记 0 会冤枉「还没到那一步」的门店** |
| 过程·评价分 | —— | **评价体系未实现**（ADR-0039 §二）→ 本期恒不参与，明细里注明 |

三条实现上的配套，缺一条这条口径就会走样：

- **0 与 null 是两种形状，不是两种文案**：记 0 分写 `score = 0.00`，不参与写 `score = NULL`
  （明细表的列允许 NULL）。混成一个数，前端与服务者都读不出「这项到底算不算数」；
- **过程子项之间等权、未参与的子项不占权**（`PROCESS` = 参与子项的等权平均）；
  三项主项的权重按参与项**重算**：`总分 = Σ(得分 × 权重) ÷ Σ(参与权重)`。
  一项都没参与时总分写 `0.00` 并在每一项的 `note` 里写明原因——**不写 100，也不写「缺数据」**；
- **增长侧事实源未接线也是一种「无要求」**，但原因必须可区分：明细里写「数据源未接线」，
  而不是与「没定要求」共用一个说法（`growthWired=false` 是它的来源）。
  这一条是刻意的 fail-closed：**平台没给的数不记在服务者头上**，
  也绝不能让「未接线」洗成一次「没做」或者按满分过。

## 三、定时与幂等：唯一键即幂等键，不押在「只跑一次」上

- `AssessmentMonthlyJob` 用 Spring `@Scheduled`（ADR-0003 已去 XXL-JOB），
  **每月 1 日 04:00**（东八区）算**上月**：时间点与券过期（01:10）、资质到期（03:30）、
  月度阶梯（09:00）错开，免得几个批算在同一时刻抢连接；
- **幂等靠 `assessment_monthly_score` 的 `(provider_id, period)` 唯一键**：重跑、多实例并发、
  运营补跑，撞键的那次直接返回 `false`。**不做「先查后插 + 加锁」**——应用层的先查后插在并发下会
  双双通过（ADR-0044 记的正是这一类），而唯一键是数据库能给的最强保证；
- 批算**只遍历状态为「正常」的服务者**（待审核 / 驳回 / 冻结不算分：前两种还没有经营资格，
  冻结的那一批由运营的处置决定其归属，而「冻结该不该扣分」ADR 没定）；
- 业务逻辑不在 job 里（它只回答「什么时候算、算哪个账期」），所以测试直接调 `run()`——
  与 `QualificationExpiryJob` 同一取舍（批算没有 HTTP 入口，与其不测不如调它的入口）。

## 四、覆盖单项分：留痕是表，不是日志

ADR-0039 §三的原话是「谁、何时、理由、覆盖前后值都留，否则算法是黑箱，服务者无法申诉」。
落成 `assessment_override_log`（**append-only**，每次覆盖追加一条）+ 明细上的三个列：

| 要求 | 落点 |
| --- | --- |
| 谁 | 留痕行的 `created_by`（框架按 `CurrentUser` 填的 operatorId） |
| 何时 | `created_at` |
| 理由 | `reason`（必填；**随明细下发给服务者**，只对平台可见的留痕不能支撑申诉） |
| 覆盖前 / 后的值 | `before_score` / `after_score`（都是**当时的生效值**，可空——覆盖一个「未参与」的项时前面没有值） |

另外两条刻意的设计：

- **覆盖不覆盖算法原值**：明细的 `calculated_score` **永不改**，`score` 才是当前生效值。
  连续覆盖两次会得到首尾相接的两条留痕，而「想还原」只需要覆盖回原值——不需要一个撤销接口，
  也不需要把原值藏在审计表里；
- **只能覆盖三项主项**（`INVITE` / `COUPON` / `PROCESS`）：过程子项是过程分的**构成**，
  覆盖它们等于绕过算法。覆盖后**立刻重算总分与等级**并写回 `provider`，
  否则「总分与明细对不上」，而总分才是服务者与推荐侧真正在用的那个数。

**超管门禁的临时落点**：ADR-0037 §一把「考核规则配置」与「清退服务者」「删除目录项」一起划给超级管理员，
而本仓的运营后台**还没有角色体系**（ADR-0035 的「需要协调」）。本切片不沿用「admin 域一视同仁」，
而是加了一道 `AssessmentSuperAdminGuard`：登录域必须 admin，**且账号必须在
`app.assessment.super-admin-user-ids`（环境变量）名单里**；**名单未配置时谁都不能改**（fail-closed）。
让「谁能改分」成为运营后台里可自助修改的配置，等于把门禁的钥匙挂在门上，所以它是技术参数而不是业务配置
（ADR-0010 的分层）。**代价**：部署后必须先配名单，否则这两个动作没人能做——这条写进了「需要协调」。

## 待澄清（需要甲方拍板）

1. **区域保护规则**：ADR-0039 §三明说留白（「文档提了，但没有可执行的规则依据」）。
   本切片**连字段都不动**：`provider.region_code` 保持恒空，`AssessmentView` 里没有任何区域字段。
   要做它至少要定三件事：区域怎么划（行政编码？门店坐标半径？）、保护什么（同区域不重复推荐？
   同品类限量？）、与等级的联动方式（战略合作独占？）——**这三件都不是技术选择**。
2. **AI 推荐优先级怎么用**：本切片只把「等级 → 优先级」的映射存下来（分表 + `provider.level`），
   **没有改任何推荐逻辑**（F011 的规则版推荐在别处）。要用起来至少要先定：优先级影响的是排序权重、
   配额，还是召回门槛；以及它与「服务项上架状态、资质有效期」这些硬条件的先后关系。
3. **评价分缺失时的长期口径**：现在恒为「不参与」（评价体系未实现，ADR-0039 §二）。
   评价体系落地后要定的是它的**换算方式**：满意率直接 ×100，还是与评价数加权（只有 3 条评价的
   5 星门店不该和 300 条的一样）。前者能立刻上线，后者需要先定最少评价数。
4. **拉新与券的达标线取值**：种子里是 0（未配置 → 不参与）。运营配多少是产品决策：
   拉新目标按门店规模分档？券目标按贡献额度折算？在定下来之前，这两项对**所有**门店都不参与，
   总分实际只剩过程分的权重——这是一个**有效状态**（不是 bug），但要与验收方说明。
5. **分档阈值的取值依据**：优选 80 / 战略 90 与接单响应 30 分钟是本项目挑的占位值
   （交付文档只给了 40/40/20 的权重与「86 分 = 优选合作」的示例，没有阈值表）。
6. **冻结期的账期处理**：批算跳过非「正常」状态的门店。冻结门店当月已经发生的履约要不要计分、
   解冻后要不要补算，ADR 没定——现在的行为是「跳过，不补算」（补算会引入「哪一段算他的」这个新问题）。
7. **覆盖能否撤回**：现在的做法是「再覆盖一次写回原值」（留痕保留全部序列，原值在
   `calculated_score` 上）。如果甲方要一个明确的「撤销」动作，那是接口层的加法，不需要改表。

## Consequences

- **考核不再阻塞任何切片**：F022 是交付路线里最后一项未实现的功能，本切片之后
  「拉新 40 + 券 40 + 过程 20」的算法、月度分表、等级、覆盖留痕与两个后台的接口都在了；
  剩下的两处外部依赖（增长侧事实源、超管名单）都是**可独立接线**的，不影响其余功能。
- **默认状态下考核只算过程分**：拉新与券要到「运营配达标线 + ph-privilege 接线」之后才参与。
  这不是降级而是 ADR-0050 §四 的第二种口径，服务者侧看得到逐项的原因（明细里的 `note`）。
- **过程分的三项数据依赖订单的履约质量**：订单侧若没有核销 / 报工的动作，过程分只会拿到
  「一单未接 → 0 分」这类结果——它是**如实反映**，不是考核算错。
- **超管名单是一个临时机制**，它的存在本身就是「角色体系未落地」的一个可见欠账
  （与 `provider_review_log` 里运营 / 超管不分同一个来源），落地时要一并清掉。
- 交付文档 F022 的「流量加权」与「区域保护」两项，在本切片里的落点是**等级与优先级被存下来**
  （可被推荐侧读），而**具体怎么加权、怎么保护仍是留白**（待澄清第 1、2 条）——
  要与验收方说明：这两项没有被静默实现成某个猜测。
