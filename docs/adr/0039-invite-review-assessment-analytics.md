# 第六批裁决：裂变归因、评价体系、考核算法、埋点与看板

四条互不依赖，合并（同 [ADR-0024](0024-quota-care-community-tracking-packages.md)）。

## 一、邀请与归因（挡 [#54](https://github.com/QIUZI-HONG/pet-health/issues/54) → #111）

- **两个入口**：分享链接带 `?invite=CODE`（落地页记住 7 天）+ 注册表单可手工填邀请码。
- **归因时点是「注册那一刻」**：以用户填的码为准（链接只做预填），**不做事后补填**——补填是刷券的入口。
- **有效邀请 = 被邀请人完成建档**（BPM-2 的「完善档案（绑定邀请人）」）。阶梯 1/3/5/10/15 与积分都按**有效邀请数**计，不按注册数。
- **反作弊三层**：同设备/同 IP 多账号、自邀自（同手机号段 + 同设备）、被邀请人 24 小时内无行为则不发券。与 [#121](https://github.com/QIUZI-HONG/pet-health/issues/121) 合流。
- **K 因子指标退场**：交付文档的「邀请裂变 K 因子 > 1」建立在小程序的社交转发链上，三个端改成 Web 之后**没有这个传播路径**，指标不成立。替换为**有效邀请转化率**（注册 → 完成建档）与**有效邀请数**。这一条要与验收方说明。

## 二、评价体系（挡 [#79](https://github.com/QIUZI-HONG/pet-health/issues/79) → #108）

- **三个维度**：服务质量 / 价格透明度 / 准时（各 1–5 星）+ 文字（≤200 字）+ 预置标签。
- **聚合指标**：满意率（≥4 星占比）、**平均服务时长**（由报工的时间戳算出来，**不让用户填**——用户填的时长不可信）、评分分布。这三项支撑交付文档 P004 的「92% 满意、平均 45 分钟」。
- **「AI 评价总结」先做规则聚合**（标签与关键词计数 + 满意率），模型生成摘要等知识库接上（[#100](https://github.com/QIUZI-HONG/pet-health/issues/100)）再开——现在没有检索层，模型会编。
- **进考核**：等权进过程分（见本文第三节）；同设备/短时批量评价**降权**（判据与邀请反作弊同一套）。
- **晒单奖励**走积分（5 分/次、月上限 5 次，见 [ADR-0038](0038-order-redeem-rights-points.md)）。
- 评价是 **UGC**：进内容审核（机审敏感词 + 运营可下架）。

## 三、考核（挡 [#58](https://github.com/QIUZI-HONG/pet-health/issues/58) → #114）

- **总分 = 拉新 40% + 券 40% + 过程 20%**（交付文档 F022 的权重，不改）：
  - 拉新 = 有效邀请数（上节口径）；
  - 券 = 服务者贡献额度的完成率 × 核销数（口径写进迁移注释，依赖 [#53](https://github.com/QIUZI-HONG/pet-health/issues/53) 的三层对象）；
  - 过程 = 接单响应时长、核销率、报工完整率、评价分、**服务者取消率**（[ADR-0049](0049-trade-domain-rulings.md) §七 修订）。
  - **缺项口径**：该做而没做 → 记 0；平台侧无该维度要求 → 不参与并重算权重、明细注明「未参与」（[ADR-0050](0050-scope-and-metrics-rulings.md) §四 修订）。
- **每月 1 日计算上月**，落月度分表并保留历史（跨月可对比）。定时任务用 Spring Scheduler（[ADR-0003](0003-lean-middleware.md) 已去 XXL-JOB）。
- **等级**（基础 / 优选 / 战略）按分档映射，影响 AI 推荐优先级；**区域保护规则留白待定**（文档提了，但没有可执行的规则依据）。
- **允许超级管理员覆盖单项分，但必须留痕**：谁、何时、理由、覆盖前后值都留。否则算法是黑箱，服务者无法申诉。

## 四、埋点与看板（挡 [#86](https://github.com/QIUZI-HONG/pet-health/issues/86) → #119）

- **12 个核心事件**进 `analytics_event`：注册、建档、打卡、AI 咨询、下单、核销、报工、评价、邀请、领券、核销券、AI 降级。**不埋全量接口**——埋点的成本在口径，不在写入。
- **每日定时聚合成日表**，看板只读日表（不扫事件表）。
- **口径先行**：先写一份指标口径表（每个指标的分子、分母、去重口径、时间窗），再写看板。同一个「活跃用户」在三个报表里三个数，是最常见也最难修的问题。
- 不引入第三方埋点 SDK。**埋点是旁路**：写入失败不回滚业务、不影响主链路（与审计日志同一定位，见 [ADR-0028](0028-security-baseline.md)）。

## Consequences

- 交付文档的「K 因子 > 1」与「AI 评价总结」两项按上述降级/替换（都要与验收方说明）。
- 考核的「券」项依赖券池的额度模型；券池未落地时该项记 0 分并**在报告里注明未计入**（不静默按满分）。
- 埋点表与审计日志是两张表，**不要合并**：审计日志是安全设施（谁动了什么，不可丢），埋点是分析设施（可以丢）。混在一起会让两边的保留期与访问控制都做不对。
