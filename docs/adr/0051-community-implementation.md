# 社区的实现细节：卡片与来源记录的关联、匿名、审核状态机、权益门禁

实现切片：[#84](https://github.com/QIUZI-HONG/pet-health/issues/84)（F020 经验卡片 + 问答互助）。
上位决策是 [ADR-0041](0041-community-security-test-perf.md) §一（三种内容与嵌入位置、不做独立 Tab、
发文走权益码 `community.post`、内容进审核）、
[ADR-0050](0050-scope-and-metrics-rulings.md) §一（本期范围：**慢病社群后置**）、
[ADR-0037](0037-roles-console-boundary-coupon-pool.md) §一（内容审核归运营）、
[ADR-0038](0038-order-redeem-rights-points.md) §三（权益判定只有 `rights(userId)` 一个出口）。
**本 ADR 只记「怎么落的」，不重开上面那几条已经裁决过的规则。**

落地位置：`server/ph-content/**`（domain / mapper / service / web）+ DTO 在 `ph-api` 的
`com.pethealth.api.content` + 迁移 `V31` / `V32`（`db/undo/U31` / `U32`）+
契约 `contract/app.yaml`（`/community/**`）与 `contract/admin.yaml`（内容审核队列与词表）。

## 一、经验卡片：与来源记录**逻辑关联**，不重读档案

「一键生成卡片」写成**编辑动作**而不是导出动作：

- 请求带 `pet_id` + `source_type`（1 打卡 / 2 就医记录）+ `source_ref`（来源记录 id），
  三者落库成为**逻辑引用**（ADR-0006 不许 join 别人的表，也不做外键）；
- 服务端校验**宠物归属**（走 ph-record 已实现的 `PetQueryApi.existsOwnedBy`，
  不是自己的宠物 → 40400）；
- **正文由前端从那条记录预填、用户改完再提交**，服务端不重读档案正文。

理由有两条，第二条更要紧：档案模块没有「按 id 取一条记录」的对外接口，
为一个**展示用的关联**去扩它的对外接口不在本切片范围（见待澄清第 2 条）；
而即使有，也不该把用户档案的原文经社区再暴露一次——社区是公开场域，
档案是私域，两者的可见性口径相反。

**聚合靠卡片上的快照标签**：`species` / `breed` / `disease_tag`（慢病标签）随卡片落库，
之后宠物改名、品种登记被纠正、慢病标记被去掉，都不改写已经发出去的历史卡片
（与订单快照同一口径，理由见 `V29` 的注释；与目录项「现取不存快照」相反，因为那说的是**目录**）。
「同品种 / 同病聚合」于是退化成两个带索引的等值筛选，不需要任何跨模块查询。

## 二、匿名怎么落地：**恒匿名**，而不是「默认匿名」

ADR-0041 §一写的是「经验卡片**默认匿名**（交付文档 F020「录入即生成卡片（匿名）」）」。
实现把它**收紧成恒匿名**：

- 库里保留 `author_id`——它只服务三件事：越权判定（待审的卡片只有作者看得到）、
  「我的卡片」列表、审核追溯（运营端的 `ContentReviewItemView.author_id`）；
- **所有对外视图都不含任何身份字段**：`CommunityCardView` / `CommunityQuestionView` /
  `CommunityAnswerView` 里没有作者 id、昵称、宠物昵称，也没有 `source_ref`
  （来源记录 id 一旦下发，配上档案页就能反推是谁）。集成测试对字段名做了硬断言
  （`CommunityCardTest.cardIsAlwaysAnonymous`），因为这类承诺没有「看起来对不对」——
  只能靠「出现了就红」守住。

为什么不留一个「非匿名」开关：**没有需求支撑**（F020 的括号写的就是匿名卡片），
而任何开关都要额外落一条「谁允许看到什么」的规则，等于给这条隐私保证开一个口子。
真要放开时，`anonymous` 字段与 `author_label` 都是**纯加法**（不改已有字段的语义）。

## 三、审核状态机：默认待审，机审只做「拒」，人工做「放」

三态（`ContentStatus`）：`0 待审 / 1 已发布 / 2 已驳回（含运营下架）`。

- **新建一律 `0`**；**公开列表与详情只读 `1`**——「待审内容不出现在公开列表」是这一块
  对外最直接的承诺，也是集成测试里被单独钉住的一条；
- **机审在创建时就出结果**：命中敏感词直接落 `2`（并把命中的词记进 `machine_hits`），
  未命中留 `0`。机审**不直接放行**——放行是运营的动作（ADR-0037 §一的矩阵里
  「内容审核」归运营）。代价写在 Consequences 里；
- **运营只有三条迁移**：`0/2 → 1`（通过）、`0/1 → 2`（驳回 / 下架）、其余一律 **40900**
  （ADR-0038 §一的口径：非法迁移是状态冲突，不是参数错误）。三条迁移各有两条实现：
  一条**人话的预检**（给出「已经是已发布状态」这种可读原因）与一条**条件更新**
  （把目标状态写进 WHERE，受影响行数为 0 就报 40900）。只有条件更新是闸门——
  两个运营同时处置同一条内容时，先到的那条生效，后到的得到 40900；
- **改判的口子留着**：机审误伤是常态，运营可以把被机审驳回的内容改成已发布。
  改判**不清空** `machine_hits`：它是这次改判的依据（「为什么这条曾经被拒过」）。
  改判**不是**编辑内容：运营的动作是放行 / 拦住 / 下架，替用户改内容等于平台替用户表态；
- **驳回理由必填且只给作者看**：`CommunityCardView.reject_reason` 等三个视图里都有它，
  只有作者本人的那份读得到（公开列表里只会出现已发布内容，那些的这里恒为空）。
  机审命中时给的是「内容命中敏感词，未通过机审」，**不告诉作者命中了哪个词**——
  说了词表就会被绕开；运营若认为该说明，写在理由里；
- **回答数只数已过审的回答**：`community_question.answer_count` 只在
  「回答通过」时 `+1`、「已发布的回答被打回」时 `-1`，**只有 ContentReviewService 一处维护它**
  （与 `like_count` 同一口径：冗余计数只能有一处写入者，否则迟早会漂）。

## 四、权益门禁落点：service 层的 `PostingAccess`，只拦发文

- 判定**只有一处**：`PostingAccess.requirePostingRight(userId)` 调 ph-privilege 的
  `RightsApi`（ADR-0038 §三的 `rights(userId)`），社区**不 join `rights_grant`、也不自己拼规则**
  （ADR-0006 / ADR-0045）；
- 三个动作过门：**发卡片、提问、回答**（回答也是发文）；**点赞不过门**——它是互动不是发文，
  拿发文权限去卡点赞等于把最轻的互动也变成门槛；
- 失败码是 **40300**（与「未登录」的 40100 分开）：前者该引导去做任务 / 邀请，后者该引导去登录。
  两个码混用会让引导文案指向错误的方向；
- **顺序：权益 → 归属 → 内容**。没有权限时不回答「这只宠物是不是你的」——
  两件事不该互相成为探测对方的手段。

**与既有口径的一处张力（有意为之）**：docs/conventions.md 说「越权一律 40400」，
而这里是 40300。两者说的不是一件事：40400 守的是**资源归属**（别人的资源按不存在处理，
免得用 id 探测存在性），40300 守的是**能力**（登录了但没这项权益，与具体资源无关）。
采纳的越权仍然走 40400——它针对的是一条具体的提问。

## 五、问答互助：采纳的唯一真值在提问行上

- `community_question.adopted_answer_id` 是「这条问题被解决了没有」的**唯一真值**，
  回答行上**不存** `is_adopted` 副本（同一个事实存两处，迟早会出现「问题说采纳了 A、
  A 说自己没被采纳」）；回答视图里的 `adopted` 是从提问行派生的展示值；
- 唯一性不靠先查后判：`UPDATE ... WHERE adopted_answer_id IS NULL`，受影响行数为 0 → **40900**
  （先查后判在并发下会双通过——ADR-0044 记的同类教训）；
- **采纳不回退**：没有「取消采纳」这个动作（没有需求支撑，而它会让「已解决的问题」
  变成可以反复翻转的状态）；
- 可见范围的规则是「**已发布的 + 我自己写的**」：没审过的内容不进入任何人的阅读路径
  （提问者也不行），但作者自己要能看到自己的那条（否则「我明明答了」与「详情里没有」
  会同时成立）。**没对别人可见的提问不能被回答**（40400）：回答一条别人看不到的问题，
  回答本身也没有读者；
- **采纳的越权按 40400 处理**：只有提问者能采纳，判据是归属（`author_id == 当前用户`），
  不匹配与不存在同码。

## 六、点赞：幂等 + 只增不减的两处计数

- `(card_id, user_id)` 唯一键就是「一人一赞」这条不变量；
- **点赞幂等**：先把曾经取消过的那一行翻回来（`is_deleted 1 → 0`），翻不动才插一行，
  并发双击撞在唯一键上——被当作「已经点过了」，**不是错误**（点赞按钮的重试与双击是常态）；
- **取消点赞按「宠物名下的子资源」口径**：归属先校验（卡片不存在 / 没过审 → 40400），
  子资源自身删除幂等（本来就没点过也返回成功）——docs/conventions.md 的两分法；
- **计数只在真的改变了状态的那一次动**：`like_count` 是冗余值，真值以 `community_card_like` 为准；
  减的一侧用 `GREATEST(like_count - 1, 0)`——宁可少减一次也不能出现负数。

一条实测踩到的坑写在这里：**不要用 `INSERT ... ON DUPLICATE KEY UPDATE` 的受影响行数判成败**。
Connector/J 默认带 `CLIENT_FOUND_ROWS`，它对「行已存在且被写成原值」也报 1，
于是「新点赞」与「早就点过」分不开（ADR-0048 §二记过同一个坑，那次的表现是超卖）。
本切片的做法是**把状态写进 WHERE**：`is_deleted = 1` 才翻回来、`is_deleted = 0` 才删掉，
返回 0 就明确是「条件不成立」。

## 七、敏感词表：入库 + 运营维护，包含匹配

- 表 `content_sensitive_word`（运营后台可增改 / 启停）：按 ADR-0010 的分层，
  它是**业务可调项**——词表是随热点变的运营资产，写死在代码里等于没人会改；
- **判定只有一条规则**：小写化的**包含匹配**，不做正则、不做分词。运营要能肉眼预测
  「这句话为什么被拦」，这是词表能不能被信任的前提；正则的威力换来的是「谁也说不清
  哪条会被拦」，那正是误伤的来源；
- **不缓存**（与权益判定同一取舍，ADR-0045 §一）：词表决定内容能不能发出去，
  缓存漂移的代价是「运营刚停掉的词还在拦人」，而这里查的是一张几十行、带索引的小表；
- **停用不删**：留着它才能解释「昨天为什么拦了那条内容」。所以词表**没有删除接口**；
- 与 AI 侧的 `knowledge_guard_term` **不合并**：那张表管模型**输出**里的药名与越界表述
  （ADR-0021），这张表管**用户发进来**的内容（CONTEXT.md 的硬红线条目：敏感词属内容审核域，
  与红线词无关）。两张表的读者、判据与责任人都不同。

## 八、接口与迁移清单

契约（本轮归社区写入者，ADR-0047）：C 端 7 个路径（卡片列表 / 生成 / 详情 / 点赞 / 取消点赞、
问答列表 / 提问 / 详情 / 回答 / 采纳共 10 个动作）、运营端 5 个路径（队列、通过、驳回、
词表列表、加词、改词共 6 个动作）。
请求体一律 `*Request`、响应体 `*View`、路径参数 snake_case（`{card_id}` / `{question_id}` /
`{answer_id}` / `{content_type}` / `{content_id}` / `{word_id}`）。

迁移两张，各自一张回滚脚本（回滚代价写在脚本头部）：

| 迁移 | 表 | 回滚脚本 |
| --- | --- | --- |
| `V31__community_card.sql` | `community_card` / `community_card_like` | `U31` |
| `V32__community_qa_and_review.sql` | `community_question` / `community_answer` / `content_sensitive_word` | `U32` |

最要紧的一条回滚代价：**社区内容是用户原创，平台没有第二份副本**——
档案导出（`ProfileExportApi`）不含社区内容，`audit_log` 只记请求元信息、**不记正文**，
所以回滚后正文重建不了。V32 还额外丢掉运营维护的词表（尤其是**停用记录**：
被误伤后停掉的词会重新开始拦截，而运营不会记得自己停过哪几个）。

## Consequences

- **人工审核量 = 全部内容**：机审只拦明显违规的，其余全部进待审队列等人点。
  冷启动期没有量，这条不痛；一旦量上来，「机审通过即发布 + 抽样复核」会成为必需，
  那时改的是 `ContentSecurity` 的放行判据，**不是**状态机本身（三态不变，只是多一条
  `0 → 1` 的自动迁移）。
- **`community.post` 现在没有任何自动授予路径**：邀请阶梯的五个档位默认没配 `rights_code`、
  打卡阶梯不发权益，所以这道门**当前是关着的**——发卡片、提问、回答都会 40300，
  需要运营在 `POST /admin/rights/grants` 手动授予，或把某个阶梯档位配上这个码。
  这是「冷启动」在**权限侧**的表现，与内容侧的冷启动是同一件事的两面（见待澄清第 1 条）。
- **`source_ref` 不校验**：服务端不知道那条来源记录是否真的存在、是否真的属于 `pet_id`
  （见待澄清第 2 条）。关联的强度止于「作者声称它来自某条记录」，而卡片正文是作者自己写的——
  也就是说这条关联**不构成任何事实主张**，展示层也不该把它当作事实。
- **慢病社群仍然后置**（ADR-0050 §一）：本切片没有社群表、没有标签聚合的帖子流。
  将来补它时，`disease_tag` 这套快照标签可以复用，但**内容种子**这件事没有捷径。
- 社区不产出权益与积分：采纳、被采纳、点赞都**不发任何东西**（ADR-0038 §四把发放路径钉死了，
  社区这里不发明第三条）。要给「被采纳」发奖励时，改的是那一本账。

## 待澄清

1. **内容冷启动**：目前既没有内容，也没有能发内容的人（见 Consequences 第二条）。
   要冷启动至少需要两条决定：① 是否给某一批用户直接授予 `community.post`；
   ② 首批内容从哪来（运营代发？种子卡片？）。ADR-0050 §一已明确「先做就是一个没人发帖的
   空壳」是慢病社群后置的理由，同样的判断对本期的卡片与问答也成立——**只是它们至少
   还有用户自己的一键生成入口**。
2. **`source_ref` 的校验强度**：现在只做关联与追溯，服务端不校验「这条记录确实属于 `pet_id`」。
   要收紧的话需要档案模块开一个「按 id 取一条记录的归属与摘要」的对外接口（ADR-0006 之下
   这是唯一的合法路径），属档案侧的接口扩充，不在本切片范围。
3. **举报机制**：本期只有「机审 + 运营主动看队列」，**没有用户举报入口**。
   真实社区里举报是内容审核的主要来源（运营不可能看全），
   而举报要额外定的口径不止一条（谁能举报、重复举报怎么去重、恶意举报怎么处理、
   举报是否通知作者）——本切片不发明它。
4. **敏感词表来源**：V32 的六个种子词是本项目自己挑的（只放引流与虚假疗效表述，
   **刻意不放**品种名、疾病名、药名——它们在正常交流里都会出现，一放进去就会把真实用户拦在门外），
   **不引任何外部词库**。将来要么继续人工维护，要么接三方内容安全服务——
   后者会引入外部依赖与费用，需要单独裁决。
5. **「非匿名」卡片**：现在恒匿名（见 §二）。若产品确需实名展示（例如职业兽医背书），
   要定的是「谁可以实名、实名后展示什么（昵称？资质？）」——不是加一个布尔开关那么简单。
