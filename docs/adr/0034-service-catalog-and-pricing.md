# 标准服务目录两级、编码不可复用、价格区间由运营维护

平台的**标准服务目录**是服务供给的唯一口径：服务者只能从目录里勾选、在平台给的区间内定价。
这条对应交付文档 F010（目录由平台统一定义）、F012 与 2.5（「目录外服务须经平台审核」、
「商家定价 100% 区间校验」），以及地图上的 [#75](https://github.com/QIUZI-HONG/pet-health/issues/75)。

**本 ADR 的前七条是 2026-09-29 项目所有者对 #75 的裁决**（决策票在此前的对话里悬着），
写在这里以免下一个人再猜一次；其余几条是实现时按交付文档推出来的。

## 决定

**1. 两级结构：分类 → 项目。** 分类就是交付文档 5.2 的六大类（医院 / 洗护美容 / 训犬 /
寄养上门 / 食品用品 / 间接服务），项目是 5.2 逐行列出的那些（疫苗、体检、洗护、寄养…）。
不做第三级：5.2 的项目已经细到「剪指甲」这一层，再往下就是门店自己的服务说明，
那属于服务项（`provider_service`）的字段，不属于平台目录。

**2. 编码规则：大类两字母 + 三位序号**（`HE-001` 医院、`GR-001` 洗护、`TR-001` 训犬、
`BD-001` 寄养上门、`SP-001` 食品用品、`IN-001` 间接服务）。**发布后不可改、不可复用**：
`order_item.service_code`（交付文档 7.2）与券的适用范围都挂在它上面。
「下架」只改 `status`，**永不删行、永不换码**——排号时连历史上用过的码一起算
（`ServiceItemMapper.maxCodeWithPrefix` 是唯一一处故意不带 `is_deleted = 0` 的手写 SQL）。

**3. 价格区间随项目走，由运营维护。** 每个目录项一个 `[price_min, price_max]`，
**存库、不写死在代码里**（改区间不需要发版）。这是 2.5「100% 区间校验」的前提：
校验基准若存在服务者行里，服务者改一行就等于给自己放宽了区间。

**4. 区间初始值 = 该项目市场参考价的 ±30%**（`V21` 的每条 `INSERT` 注释里都写着参考价）。
**这是初始估计值，不是定价依据**——交付文档没给任何价格数据，这版种子值只保证
「服务者一开始能定价、不会一上来就被系统拒绝」，运营按实际供需调整。

**5. 区间校验只有一处实现**：`CatalogPricingApi.requirePriceInRange`（ph-catalog 的 api 包）。
两个调用点共用它——**选品定价时**（本切片，ph-provider 调）与**下单时**（#77 落地时调）。
越界返回业务码 `90001`（HTTP 200），`message` 就是交付文档 2.4 那句
「价格须在¥X-¥Y之间」，服务端与前端用同一句文案。

**6. 区间自身也要校验**：非负、最多两位小数（`decimal(10,2)`，禁止浮点）、**下限 ≤ 上限**。
写反了在运营的写入口就拦住（40001）——否则它会在某个服务者定价时以「越界」的形式暴露，
那时已经分不清是区间错还是价格错。

**7. 目录外服务不放开自由建项**：服务者只能提**提案**（名称 / 说明 / 建议区间 / 分类），
运营审核通过后由平台建正式项目，之后服务者才能在自己店里定价上架。
**最终区间由运营在审核通过时给出，不默认采纳服务者的建议值**——区间是平台规则（F010），
让申请方定义规则等于让区间校验自己批自己。

**8. 停用目录项、收窄区间都不自动下架存量。** 自动下架会打断已预约的订单，
而本项目没有推送通道去通知用户（只有站内消息中心，用户不盯着页面就收不到）。
存量服务项在下一次改价或重审时按新区间自然收敛。

**9. 服务者的服务项不存目录名称快照。** 名称、单位、区间都在目录侧，ph-provider 每次
按 code 批量取一次（`CatalogQueryApi.findItems`，一次查询而不是 N 次）。
快照的第一天就与目录不一致：平台把「基础体检」改名后，服务者页面与 C 端应该同时变。
依赖方向因此是单向的 **provider → catalog**（Maven 依赖不允许成环）。

## Considered Options

- **区间写死在代码常量里**：省一张列，但每次调价都要发版，且「谁改的、什么时候改的」
  查不出来。运营后台正是为此存在的（交付文档 P034）。
- **三级目录（大类 / 子类 / 项目）**：5.2 的分类清单本身就是两级；加一层只会让
  服务者选品时多两次点击，而我们没有任何一个功能需要中间层。
- **让服务者自建项目再收敛**：启动快，但收敛之前用户看到的价格口径就是乱的，
  而「价格透明」是产品的核心价值之一（Problem Statement 第 2 条）。不要。
- **允许多个服务者提案时自选编码**：编码进 `order_item`，自选等于让外部数据决定内部标识的
  唯一性。编码一律由平台排号，运营也可以显式指定（撞号就报错，不自动改号）。
- **给服务项存名称快照**：见决定 9。
- **区间收窄时自动下架越界的服务项**：见决定 8——打断已预约订单的代价更大。
  代价留在这里：运营收窄区间后，存量里可能有一段「价格已越界但仍在架」的窗口期。

## Consequences

- 目录项编码不可改意味着**服务者不能换分类**：编码的前两位就是分类前缀（`HE` 属于医院），
  换分类必然要换码。要换只能新建项目、旧项目停用（历史订单项仍指着旧码，那是对的）。
- `catalog_item_proposal`（提案单）与它的审核流水在 **ph-provider** 而不是 ph-catalog：
  提案是服务者的申请动作，与入驻申请、上架审核同属一类；审核通过时才由 ph-provider 调
  `CatalogItemApi.createFromProposal` 建正式项目。反过来放 catalog 的话，catalog 要展示
  「谁提的」就得回头依赖 provider，两个模块就成环了。
- 目录项**不做物理删除**：编码不可复用，删行会让历史订单项失去定义。
  ADR-0037 把「目录项删除」划给超级管理员，本切片只提供状态变更（下架语义）。
- 初始区间是估计值这件事**必须向服务者说明**：区间卡住一次定价时，
  服务者会以为平台在压价，而实际上是种子值还没被运营校准过。

## 待澄清

- **区域保护（`region_code`）与目录的关系**：交付文档 BPM-4 说等级决定「AI 推荐优先级 + 区域保护」，
  但没说区域保护的粒度（按分类？按项目？按服务者？）、也没说它与目录项的关系。
  `provider.region_code` 字段先留着，规则与 #58 考核一起定。
- **券的适用范围与目录项的关联方式**：券池（[#53](https://github.com/QIUZI-HONG/pet-health/issues/53)）
  的 `coupon_template.scope` 存的是服务编码或分类。本切片**没有**替它定关联表——
  券池落地时若需要「按分类发券」的索引，应当由券侧按编码规则（前缀即分类）自己拼，
  不要反过来要求目录提供 `category_id` 列表接口。接口留白在此。
- **组合套餐（#88）的骨架未做**：决策是「平台定骨架（哪些目录项可组合 + 套餐价区间），
  服务者在骨架内组包定价并提交审核」。本切片实现了「选品定价上架」的完整链路，
  套餐的骨架（`package_template` + `provider_package`）**没有实现**，见实施报告。
- **C 端浏览目录的接口未做**：`contract/app.yaml` 由另一个切片负责（本切片不碰它），
  `GET /api/v1/app/catalog/**` 的浏览接口留到下一波。目录数据本身已经就绪。
- **初始区间的复核**：这版 ±30% 的种子值需要运营按同城实际价复核一遍，
  尤其是「绝育手术」「宠物殡葬」这类跨度极大的项目（±30% 之后的区间仍然很宽）。

## 与交付文档的关系

- 表名与字段名按 CONTEXT.md 的术语纪律改名：`merchant` → `provider`、
  `merchant_service` → `provider_service`；这是术语要求，不是格式偏好。
- 交付文档 7.2 的 `merchant_service.status` 只有「1 上架 / 0 下架」，本切片扩成四态
  （待审核 / 已上架 / 已下架 / 已驳回）：2.2 的权限矩阵把「审核商家/服务」给了平台运营，
  而 BPM-4 又写服务者自己上架——**两者只有加上审核环节才能同时成立**。
- 文档 7.2 没有目录自身的表结构（F010 只给了要求），`service_category` / `service_item`
  与 `catalog_item_proposal` 是按该要求补齐的。
