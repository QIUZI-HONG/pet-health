# 专项照护模式：一个派生状态，一处推导，三处生效

回答地图 [#92](https://github.com/QIUZI-HONG/pet-health/issues/92)，并作为切片 [#116](https://github.com/QIUZI-HONG/pet-health/issues/116) 的依据，同时收口交付文档 F009。

[ADR-0024](0024-quota-care-community-tracking-packages.md) 第二节已经定了**形态**：「是否处于专项照护」是个**派生事实**——按生日实时算、慢病解除即退出，不落任何「已开启」的状态位。这一票定的是**派生规则与开启后到底改变什么**——否则「专项照护模式」只是一个没有行为的标签。

## 决定

> **本轮由项目所有者拍板的三条**（与本文其余推断不同）：
> ① 开启后**必须有四项真实变化**，否则它就是个空标签（决定二）；
> ② **用户可以手动关闭**，关闭后历史保留但老年维不再计入总分（决定二之一 / 决定三）；
> ③ 提醒阈值收紧**必须走 `reminder_rule` 的配置项**，不允许在代码里写死新的阈值数字（决定三）。

### 一、触发与退出：唯一判据 = 「年龄 ≥ 阈值」或「有慢病标记」，外加一个用户开关

```
派生照护状态  ⟺  (birthday 非空 且 实足年龄 ≥ 阈值)  或  pet.is_chronic = 1
最终是否生效  ⟺  派生照护状态 且 用户没有手动关闭（pet.care_mode_disabled = 0）
```

- **年龄实时算**：`Period.between(birthday, 今天).getYears()`，用 `AppTime.today()`（Asia/Shanghai）。**不用任何缓存的 `age` 字段**——生日一到就该开启，缓存字段必然晚一天或永远不更新（09-19 评估报告点过这条）。
- **慢病以用户录入为准，不要求凭证**（本轮拍板，见决定四）。
- **用户可以手动关闭**（本轮拍板）：关闭是**覆盖在派生状态之上的用户意愿**——它是唯一无法从生日与慢病推导出来的东西，所以只有它需要落库（`pet.care_mode_disabled`，V17）。**重新打开 = 清除这枚覆盖**，回到派生结果。
- **退出/关闭后**：历史数据全部保留（分项记录、评分行、报告都不删不回改），**老年维不再计入总分**，并且**重算当日 `health_score` 行**（否则趋势图上会留着一条按「四维平均」算出来的点，与新口径对不上）。
- **判定只有一处实现**：`CareMode.of(pet, 阈值, 今天)`（`com.pethealth.record.domain.CareMode`）。评分（`HealthScoreService`）、提醒的数据源（`ReminderSourceService`）、AI 上下文（`PetService` 实现 `AiPetApi`）、C 端接口（`CareModeService`）**都从它取**。原先「年龄 ≥ 7 岁或有慢病」这句话在 `HealthScoreService` 与 `ReminderGenerator` 里各写了一遍，两处判据已经开始漂移（后者硬编码 7、且不看阈值配置）——本票把它们收成一处，**这比新增任何功能都重要**。
- **年龄阈值入库可调**：`care_mode_rule` 表（V17），按物种一行（犬 7 / 猫 7，首版都取交付文档 F009 的「7 岁以上」），运营可改。ADR-0024 记过调研的占位是「犬 7 / 猫 10」，**本票没有按物种分离**——见待澄清第 1 条：那是兽医定稿的事，现在把它做成「改一行数据」而不是「改一次代码」。

> **对 ADR-0024 第二节的一处修订**：那里定的是「不落任何状态位」。**派生事实仍然不落状态位**（年龄与慢病不存），但**用户的开关意愿必须落一枚位**（`pet.care_mode_disabled`）——「用户明确关掉了」这件事既不能从生日推导，也不能从慢病推导，不存就丢失了。这是本轮拍板要求「用户可手动关闭」的必然结果，不是把状态位又请回来。

### 二、开启后改变什么：四项真实变化（本轮拍板，缺一项就是空标签）

| # | 变化 | 落在哪 | 状态 |
| --- | --- | --- | --- |
| 1 | **提醒阈值收紧**：走 `reminder_rule` 的配置项（照护档的提前量、宽限期与体重变化阈值），**不在代码里写死新的数字** | V17 写入配置键；`ReminderSourceApi.PetBrief` 增 `careMode` / `careReason`；**`ph-reminder` 的 `ReminderGenerator` 已接线**（照护档优先、缺键回落普通档） | ✅ |
| 2 | **老年维计入总分**（未开启不计入）；开关变化后**重算当日行** | `health_score.elderly`（ADR-0018 已实现）+ 本票的单一判据 + 开关变更时 `recalculate(today)` | ✅ |
| 3 | **AI 咨询带专项上下文**（照护已开启 + 老年/慢病信息） | `AiPetApi.PetSnapshot` 增字段 → ph-ai 组装进 `PetContext.recent_records`（该字段**已在 `ai/app/prompts.py` 里渲染**，所以不需要改 `ai/`，模型调用边界仍在 `ai/`） | ✅ |
| 4 | **档案多出「老年专项」分项入口** | ADR-0030 的 `category=12`；`GET /pets/{id}/archive-sections` 里 `elderly` 的 `enabled` 随照护状态变 | ✅ |

**专项分项记什么**（第 4 条的内容，字段清单在 ADR-0030）：复查、用药、慢病观察三类——都是「一个标题 + 一个取值 + 可选的下次日期 + 备注」。**不给剂量模板、不给用药建议**：用户自己填的处方信息是用户数据，平台不提供、也不推荐任何用药（CONTEXT.md / 交付文档 9.5 的三个绝不）。

### 三、提醒阈值收紧：数据 + 接口 + 接线都已完成

本轮拍板要求「提醒阈值收紧，走 `reminder_rule` 配置项，不许写死」。三件事都落了：

1. **数据**：V17 往 `reminder_rule.config` 写入照护档的配置键——疫苗/驱虫的 `careAdvanceDays`（30 天）与
   `careOverdueGraceDays`（60 天）、趋势的 `careWeightChangePercent`（3%）。**代码里没有新的阈值数字**，
   改数据即生效（运营可调，ADR-0010）。
2. **接口**：`ReminderSourceApi.PetBrief` 增加 `careMode` 与 `careReason`，由 `ph-record` 按决定一的**单一判据**填充——
   提醒模块**读一个布尔值**就能切档，不需要自己算年龄（原先那句「年龄 ≥ 7 岁」在提醒模块里硬编码，
   与 `care_mode_rule` 里的运营阈值没有关系，两处判据已经在漂移）。
3. **接线**：`ph-reminder` 的 `ReminderGenerator` 在读阈值处按 `pet.careMode()` 分档（照护档优先、
   **缺键回落普通档的默认值**）。这一处是**协调者授权的越界改动**（本切片的写入边界不含 ph-reminder），
   授权范围限定为「只做这一件事、向后兼容、补一条集成测试钉住」。接线后：
   **非照护宠物的提醒行为与改动前逐字节一致**（同样的键、同样的默认值，只多读一个布尔值），
   照护宠物走配置里的照护档阈值；集成测试 `CareModeTest.careModeTightensReminderThresholds`
   同时钉住两侧（照护宠提醒、普通宠不提醒、普通档阈值本身不变）。

**`type=6`（慢病/老年）没有另立 `careIntervalMonths`**：那条规则**只对处于照护模式的宠物生成**
（ADR-0019 已实现），它的 `intervalMonths` 本身就是照护档——再加一个键只是多一处要同步的配置。

### 四、慢病是**用户自述**，不要求凭证

#92 问「慢病是用户自述还是需要凭证」。**决定：自述**（`pet.is_chronic` + `chronic_desc`，建档/编辑时填），本轮拍板确认「不要求凭证」。

理由：交付文档 F009 写的就是「录入慢病触发」，没有任何凭证要求；而要求凭证意味着一条审核链路（谁审、审什么、不通过怎么办），服务者资质（[#104](https://github.com/QIUZI-HONG/pet-health/issues/104)）都没落地，用户侧更不该先跑。**用户想留凭证**可以往「证件与合规」分项传照片（ADR-0030），但平台**不核验、也不展示「已核验」字样**。

**慢病描述是必填**（`is_chronic=true` 时）：一个光秃秃的「有慢病」标记带不出任何上下文，AI 上下文与档案展示都是空的。这条已在 `PetService` 与契约里，本票把它与照护模式连起来，并在**慢病标记/生日变更时重算当日评分**。

### 五、权益：照护模式**不拦人**

交付文档 2.2 写「专项照护模式：注册用户邀请体验 / 付费用户可用」。与 ADR-0031 的决定五同一条口径：**权益引擎（#112）落地前不拦截**，照护模式对所有注册用户生效，`/care-mode` 的响应里如实给出「完整的照护提醒与权益阶梯见权益中心」的说明。理由同上：现在拦住的是一扇没有出口的门。**付费路径不存在**（ADR-0002）。

## Considered Options

**落一个 `pet.care_mode` 状态位**：省一次计算，但引入「状态与事实不一致」的两种经典故障（生日到了没开、慢病取消了还开着），而这状态没有任何独立性可言——完全由生日与慢病推导。ADR-0024 已排除，本票不改。
**在 `pet` 表加 `is_elderly`**：同上，且它是时间的函数，存下来必然会过期。
**照护模式完全由用户手动开关**：可控制，但交付文档说的是「自动开启」；纯手动还会立刻制造出「用户没开但确实 9 岁」的语义矛盾。本票取的是中间形态：**自动开启 + 允许手动关闭**（本轮拍板），关闭意愿存一枚位，派生事实不存。
**每处各写一遍判据**（现状）：两处已经漂移（阈值写死在提醒模块里）——这正是本票要收掉的东西。

## Consequences

**判据集中后，改阈值只需改数据。** `care_mode_rule` 是按物种一行的配置表（业务可调项，ADR-0010），评分、分项可见性、AI 上下文、C 端接口四处自动跟；照护档的提醒阈值同理落在 `reminder_rule.config` 里。
**分数在开启/关闭当天会变化**：老年维度一计入，总分从「三维平均」变成「四维平均」，可能出现总分下降。这是**口径变化**而不是宠物变差，所以 `/care-mode` 的响应里带一句说明，前端在照护模式开启的提示里一并展示（避免用户把它读成健康恶化）。**关闭时同一条路径重算当日行**，趋势图上不会留下按旧口径算的点。
**手动关闭是用户意愿，不是状态位复辟**：只落 `pet.care_mode_disabled` 一枚位，派生事实照旧不存。重新打开就是清掉它。
**`PetBrief` 多两个字段，提醒模块暂不读**：这是**为下一步留的接线口**（决定三最后一条），不是死代码——`ph-reminder` 的下一个切片会读它。记在这里免得被当成未使用的字段删掉。

## 待澄清

1. **年龄阈值要兽医定稿**：现取交付文档 F009 的字面值「7 岁以上」（犬猫同值）。63 号调研的占位是「犬 7 / 猫 10」，两者不一致；本票把它做成**数据**（改一行即可生效），但**取值仍待兽医确认**。
2. **慢病长期未复诊时的提醒强度**（本轮点名）：照护模式现在只有一条「复查提醒」（`type=6`）。若宠物标记了慢病却**连续几个周期没有新的复查记录**，要不要升级提醒强度（提到黄色 / 更密的间隔 / 进强提醒流）？升级意味着提醒从「体验」进入「安全」区间，也与 ADR-0019 的「红色不可关闭」挂钩——需要甲方与兽医一起定，不能由工程顺手加。
3. **兽医凭证在合规上是否必须留档**（本轮点名）：本票按「用户自述、不要求凭证」实现。若合规要求「慢病照护必须留诊断凭证」，那就需要一条凭证上传 + 审核链路（#74 合规与 #104 审核链路一起看），并明确不通过时的降级行为。
4. **慢病是否需要分期**：若要「慢病已确诊 X 个月」才开启照护，需要新增确诊日期字段与判定口径。
5. **照护模式的具体动作清单要兽医背书**：本票提供的是「复查/用药/观察」三类记录容器与一条复查提醒。真正有临床含义的照护计划（多久复查一次、老年犬要查什么指标）平台**不产出**，需要兽医定稿后作为内容（而非代码）补进来。
6. **照护模式是否影响 AI 的检索范围**（#92 的提问之一）：需要 `ai/` 侧按年龄分流知识（老年宠物常见问题与成年不同）。本切片把照护信息放进了上下文（决定二第 3 项），**检索范围的分流属 `ai/` 的能力**，与知识库运营（#100/#101）一起定。
