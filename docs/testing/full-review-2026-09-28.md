## 一、整体结论

**功能完整度：已实现的切片按契约范围基本完整，主链路端到端可用。** 注册登录、宠物建档、打卡、健康评分、
防疫记录、提醒与消息中心、AI 咨询（含红线预检与降级）、文件上传、合规三块（文档／导出／注销）都能在
浏览器里从头走到尾，前后端联调正常（含令牌静默刷新、限流、越权拦截、下载导出）。

**质量水位：工程纪律明显高于同阶段的个人项目**——真实 MySQL/Redis 上的接口测试、契约单一源头、
迁移与回滚脚本成对、错误的领域术语零出现、注释普遍在解释「为什么」。但**验收维度上存在 4 个真实缺陷带**：

1. **打卡体重没有任何校验**，能把 `abc` / `0` / `-5` / `99999` 写进档案，并算出给用户看的
   「体重下降了 2000080%」这种提醒（P1，已复现）；
2. **「撤销某一项 → 重新填」这条必然路径直接 50000**（P1，已复现）；
3. **AI 的两条安全网漏判为「绿」**：模型返回布尔 `risk_level` 被当成绿（P1，已复现）、
   红线词表为空时仍报 `red_flag_check=ok`（P1，已复现）；
4. **CI 实际上已经失效**：三条流水线只在 2026-09-27 的骨架提交上跑过，此后 25 个提交从未推送；
   而 AI 测试依赖本地 `.env`，在 CI 环境实测 10 条失败（P1）。

**前端已按授权修掉 12 处**（含 1 个会写脏数据的时区缺陷、1 处非法 HTML 嵌套、会话清态不完整等），
测试从 60 条升到 66 条全绿，提交 `7809a6e`。

**注释合规性：整体合格，按「大厂规范」的四条硬指标（职责说明／解释为什么／无废话与死代码／术语一致）
均在「好」到「一般」之间；不达标的是 4 处「注释与实现相反」**（详见第八节）——这类问题比没有注释更危险。

### P1（核心功能错误／数据可被写坏）

| # | 缺陷 | 证据与复现 | 状态 |
| --- | --- | --- | --- |
| D1 | **打卡体重无任何校验，脏数据会变成给用户看的健康提醒** | 【已复现】`POST /pets/{id}/check-ins` 传 `value` 为 `0`/`-5`/`abc`/`99999` 全部返回 200；库里 `numeric_value` 分别为 `0.00`/`-5.00`/`NULL`/`99999.00`。随后首页出现提醒：**「豆豆的体重下降了 2000080%　近 7 天体重从 -5.00 kg 变化到 99999.00 kg」** | **前端已加一道校验**（见第六节）；**后端仍开放，建议按建档口径（0.01–999.99 + 两位小数）在 `CheckInService` 拒绝** |
| D2 | **撤销某一项后再提交同一项 → 50000** | 【已复现】① 打卡饮食 → ② `DELETE /pets/{id}/check-ins/item?date=&category=2` → ③ 再打卡饮食 → `{"code":50000,"message":"服务器内部错误"}`。根因：撤销是逻辑删除，而 `uk_checkin_slot` 生成列不含 `is_deleted`，upsert 查不到就 insert → 唯一键冲突未接 | 待修（后端） |
| D3 | **首页「和昨天一样」在东八区取成前天的值**（会写脏打卡数据） | 【已复现】`TZ=Asia/Shanghai node`：`dayBefore("2026-09-28")` → `2026-09-26`（期望 27）；`TZ=UTC` 下正确——老代码 `new Date(...T00:00:00)` + `toISOString()` 的经典时区错 | ✅ 已修（`shiftDate`，附回归测试） |
| D4 | **AI 布尔 `risk_level` 被当成「绿」** | 【已复现】`{"risk_level": true, ...}` 通过校验并转成 `risk_level=1`；`2.0` 同理被收下（Python `True in (1,2,3)` 为真） | 待修（AI 服务，一行 `isinstance` 判断） |
| D5 | **红线词表为空时仍报 `red_flag_check=ok`** | 【已复现】把 `_query()` 置空后 `load_rules()` 返回 `LoadResult(rules=(), available=True)`。表被清空／迁移未跑／运营误关 `enabled` 时，这层机械安全网静默失效，且对外显示「已检查」 | 待修（AI 服务：`available=bool(rules)`） |
| D6 | **AI 降级通道不过输出层护栏，且降级原因直出用户** | 〔代码审查〕`degrade_reason` 拼入 `java_client: <异常类名>` 与上游原始响应前 160 字；C 端 `AiConsultView.vue:76` 直接渲染 `{{ result.degrade_reason }}`。降级路径的模型原始输出也不经 `guardrails.review` | 待修 |
| D7 | **AI 图片链路端到端不成立**（相对地址交给模型供应商） | 〔代码审查〕Java 给 AI 服务的是 `/api/v1/open/files/{id}?token=…`（相对路径），Python 原样塞进 `image_url.url`，供应商取不到；而现有测试把「相对路径」当成期望断言（`AiConsultTest`），缺陷被固化。当前 C 端尚未发图，属**潜在缺陷** | 待修 |
| D8 | **CI 实际已失效** | 【已复现】`gh run list` 仅 3 条骨架运行；把 `ai/` 拷到无 `.env` 的目录跑 `pytest` → **10 条失败**（测试用 `settings.internal_token` 做鉴权头，缺配置即 401）。即推上去必红 | 待修 |
| D9 | 消息中心惰性补算并发撞 `uk_dedup` → 500 | 〔代码审查〕`ReminderGenerator.upsert` 是 `selectOne` → `insert`，读路径写库；首页并发拉「列表 + 强提醒流」时两边都查不到就都 insert，异常未被捕获 | 待修 |

## 七、异常与错误处理评估

**做得对的（实测／审查均确认）**：统一 `BusinessException` + `ErrorCode` → HTTP 映射；错误码语义分层
（40100 未登录 / 40101 过期 / 40400 越权与不存在一律同码）；JDK 级校验注解给出整句中文；
AI 通路「失败一律降级、返回 200 + `degraded` + 免责声明」，不让用户看到技术错误；外部调用的超时、
令牌轮换（Refresh 一次性 + 重放整族吊销 + 按手机号限流）、上传签名的用途绑定与常量时间比较；
注销幂等且手机号可重新注册；审计字段由 `MetaObjectHandler` 统一填充。

**薄弱点**：① 用户可见的 `message` 里混入内部细节（字段英文键名、异常类名、上游原始响应）——
D6／D25；② 唯一键冲突未兜底的地方有 3 处（D2／D9／D19），表现都是「本该 400 或幂等，却 50000」；
③ 日期类字段用字符串 parse，格式对但语义非法就 500（D11）；④ 安全网类配置（红线词表、预算、熔断）
「没接上也看不出」，属静默失效（D5／D26）。

## 八、中文注释合规性评估（按大厂规范）

判定标准用的是这六条：类/接口职责说明；公共方法关键参数说明；解释「为什么」而非复述代码；
无废话注释与注释掉的死代码；TODO 带上下文；术语一致（`CONTEXT.md`，禁用「商家/商户/店铺/merchant」）。

| 模块 | 评分 | 说明与代表证据 |
| --- | --- | --- |
| `server/ph-common` | **好** | 类级 Javadoc 齐全且写边界（`FieldCipher` 连密文格式与轮换口子都写了）；扣分项：全模块仅 1 处 `@param` |
| `server/ph-account` | **好** | 注释解释取舍（为何按手机号而非 IP 限流、为何登录失败不说原因）；`User.avatar` 的 `FieldStrategy.ALWAYS` 坑写清了 |
| `server/ph-record` | **一般** | 密度全仓最高、评分口径可解释；但 1 处注释与代码**相反**（`ReminderSourceService` 说走聚合查询，实为全量拉内存）、2 处 Javadoc 错位 |
| `server/ph-reminder` | **好** | 把「uk_dedup 是物理键、软删行仍占键」这个踩过的坑写清；缺 `package-info`、1 处 Javadoc 错位 |
| `server/ph-ai` | **好（有一处不实）** | `AiServiceClient` 构造器那段「静态工厂拿不到全局 Jackson → 分级静默退化成 0」是全仓最有价值的注释之一；但 pom/package-info 声称含「熔断」而实现没有 |
| `server/ph-file` | **好** | 本组最佳：`ImageSniffer` 的「魔数对但内容已损坏」、`LocalFileStorage.resolve` 的目录穿越巡检，都把为什么讲透了 |
| `server/ph-api` | **一般** | DTO 注释写了「为什么是这个形状」；`package-info` 与 `AGENTS.md` 相反（称 DTO 是生成物、不手写） |
| `server/ph-boot`（迁移） | **好** | 9 条迁移 + 9 条 undo 严格配对，注释详尽到可当评审材料；但 `U4` 在真实数据下可能因重复键执行失败 |
| `ai/` | **好** | `config.py` 每个魔法值带实测出处；`model_client.py` 文件头四条纪律全是「为什么」；`README` 与实现矛盾（红线预检写成未完成） |
| `packages/shared`、`packages/ui` | **好** | `http/client.ts` 把五步链路与「为什么单飞刷新」写清；`tokens.css` 的取色出处与「4.2 旧值已失效」 |
| `apps/c-web/components` | **好** | 每个组件顶部说明职责 + 关键约束；`HealthScoreCard` 阈值的出处缺失 |
| `apps/c-web/views` | **一般** | 页面注释交代排布理由；`ProfileView` 的编辑事故（本次已修）与 `components/README` 过期是扣分项 |

**结论：注释合规性整体合格。** 「解释为什么」这条做得比多数商业项目好（大量注释记录了踩过的坑与
被测试逼出来的收紧决策）。不达标的是 **4 处「注释与实现相反」**（D29）——这类注释会让后来者
按错误的前提改代码，建议提为下一次整理的优先项。

**术语合规**：`商家 / 商户 / 店铺 / merchant` 在**代码目录零命中**（`grep` 覆盖 Java/TS/Vue/Python）；
仅 ADR-0001/0002 在引用交付文档原文时出现（必要引用），`contract/provider.yaml` 顶部还写明了命名纪律。

## 九、前后端联调结论

**结论：联调正常，可以认为「HTTP → 领域 → 数据库」这条链在已实现范围内是通的。** 证据：

- 前端 dev server 的 `/api/v1/app/**` 代理确实打到后端（同一 Spring 404／401 语义）；
- 令牌链路完整：过期令牌 → 自动 `POST /auth/refresh` → 重放原请求（用户全程无感，实测）；
- 限流闭环：第 11 次失败返回 42900，前端展示「尝试次数过多，请 15 分钟后再试」；
- AI 链路：Java → Python → 模型供应商全程可用（真模型 4167ms 返回结构化三段 + 免责 + 额度计数）；
  红线短路路径 0ms、留痕写明「模型未参与」；
- 导出：浏览器真的收到文件（`pet-health-account-export.json`，4151 B），字段与契约一致；
- 三处联调层面的偏差需注意：`degrade_reason` 的内部细节外露（D6）、图片相对地址（D7）、
  错误 `message` 带英文键名（D25）。

**关于「用插件模拟真实用户」**：本环境下浏览器插件的后端为**空列表**（`agent.browsers.list()` 返回 `[]`），
因此按本项目既有的替代做法，用 `/tmp/ph-e2e` 下的 Playwright harness 以真实 Chromium 驱动页面
（点击、填表、切宠物、下载文件、观察控制台错误与网络请求）。所有结论均来自真实页面行为，
不是接口层的等价推断。脚本清单：`review-a-auth` / `review-b-pet` / `review-c-ai-msg` /
`review-d-compliance` / `review-e-auth-edge` / `review-f-token-refresh` / `review-g-regression`。
